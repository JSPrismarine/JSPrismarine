Asks the client to shove the player, rather than shoving them.

The one entity the server cannot simply move. A player's position comes from their own client and is stored here as reported, so writing to it is overruled by the next movement packet and shows up as rubber-banding. A velocity is a request the client honors, and it runs the shove through the same physics as everything else the player does.

sendSettings() ​

sendSettings(): Promise<void>

Defined in: packages/prismarine/src/Player.ts:503

Sends this player's gamemode, adventure settings and abilities where each belongs.

The two halves have different audiences, and sending both to everyone was a bug. UpdateAdventureSettingsPacket carries no target actor - it describes the client receiving it and nothing else - so pushing one player's settings to every session made a single spectator set worldImmutable on everybody else's client. It goes to this player alone. UpdateAbilitiesPacket does carry targetActorUniqueId, so it is genuinely about this player and belongs with everyone who can see them.

enable() ​

enable(): Promise<void>

Defined in: packages/prismarine/src/Player.ts:253

On enable hook: loads what the server knows about this player and marks them connected.

Returns ​

Promise<void>

Remarks ​

Sends nothing. This runs from LoginHandler, before the client has been told its login succeeded, and a retail client at protocol 2193 that is handed game packets in that state drops the connection with InitialConnection-90 (bad packet). It used to send the gamemode, adventure settings and abilities from here, and a MovePlayer for every other player in the world - the first three now go out from the join burst after StartGame, and the last was never needed: AddPlayer carries each player's position when they come into view.
