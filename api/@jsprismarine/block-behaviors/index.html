JSPrismarine / @jsprismarine/block-behaviors

@jsprismarine/block-behaviors ​

What a block does. @jsprismarine/blocks says what a block is: its components, its states and its place in the palette. Every component factory there returns {}, so all 1477 vanilla blocks resolve with no behavior at all until this package registers one.

A behavior is a named set of handlers over BlockHooks, attached by family rather than by block, so 50 families cover the whole palette. One call wires them up:

typescript
import { BehaviorRegistry } from '@jsprismarine/content';
import { type BlockHooks, resolveBlocks } from '@jsprismarine/blocks';
import { registerVanillaBlockBehaviors } from '@jsprismarine/block-behaviors';

const behaviors = new BehaviorRegistry<BlockHooks>();
registerVanillaBlockBehaviors(behaviors, world);

resolveBlocks(definitions.blocks.values(), { behaviors });

The vanilla overlay writes each block's family into jsprismarine:behavior, and the selector reads that value when the definition resolves. A later pack can assign a registered family to a block by setting the same component. Definitions without it receive no vanilla behavior, so callers that resolve blocks directly must include the jsprismarine_vanilla overlay when they want vanilla block families.

world is the second argument because a handler has to reach the world and no hook event carries one. It is a BlockWorld, described below.

The world interface ​

WorldActions is everything a block does to the world, and the whole of what a family may use:

GroupMethods
BlocksgetBlock, setBlock, propertiesOf, lightDampeningOf, flammabilityOf, hasBlockTag, hasSturdyTopFace
Items and entitiesdropItem, destroyBlock, spawnEntity, removeEntity, entitiesAt
EffectsplaySound, spawnParticle
SchedulingscheduleTick(position, delay, kind?, priority?), willTickThisTick
Block entitiesgetBlockData, setBlockData
UpdatesnotifyNeighbors, redstonePower, redstoneSignal, redstoneDirectSignal, redstoneConductor, lightLevel
Environment and chancedifficulty, weather, isRainingAt, canFireSpreadAround, random, randomInt, randomFloat

Several of those are there for reasons worth stating. propertiesOf returns another block's jsprismarine:block_properties, which is how the piston and the falling blocks read push_reaction instead of carrying a list. random is on the interface rather than inside the families so a test flammabilityOf reads the resolved state's minecraft:flammable component, so a pack can change fire odds in a permutation. Fire uses the loaded minecraft:infiniburn_* block tags to decide which fuel keeps it burning forever. hasSturdyTopFace lets the host answer from the block's collision shape. destroyBlock is how a family takes a block out that it is not itself: the host raises its onBreak and rolls Java's loot table for it, where this package would otherwise have to guess that the block drops one of itself. It is optional, and a host that leaves it out gets that guess, which is what the test voxel world does. Fire passes drops: false so a burned block leaves no loot while still running its break hook. popBlock is the one rule that uses the default drop behavior, and the piston's popped block, a block that lost its support and a block a falling anvil cleared out of the way all go through it.

lightDampeningOf can read a block state's vanilla minecraft:light_dampening value, so rules can check how much light a cover blocks without treating every support block as opaque. When a host cannot report dampening, the shared rule treats it as unknown and does not convert the ground block.

Scheduled hooks run from the active block state before the engine fallback. Observer pulses, redstone torch burnout, repeater transitions, comparator output updates, and fire spread run through their family hooks. kind selects the block or fluid tick list and defaults to block; water and lava use the fluid list so their family tick shares the engine's existing liquid schedule.

A BlockWorld is a set of dimensions, and at(dimension) returns the WorldActions for one. Each handler receives the actions for its own event's dimension already resolved, so the dimension never appears in a family's code. A server with one world passes singleDimensionWorld(actions).

Nothing here names a server class. The events are structural, the world is an interface, and the package depends on @jsprismarine/blocks, @jsprismarine/content, and @jsprismarine/mapping.

Testing a family ​

VoxelWorld is a real implementation of the interface over a map of positions, not a mock: writes read back, and every drop, sound, particle, scheduled tick, spawned entity and neighbor notice is recorded in order. bindFamily binds one family to one identifier through the same create path the registry runs, and gives a method per hook, including entityEvent(position, name, source):

typescript
const harness = bindFamily(doorFamily, 'minecraft:wooden_door');
harness.dimension.set({ x: 0, y: 0, z: 0 }, 'minecraft:stone');
harness.dimension.set({ x: 0, y: 1, z: 0 }, 'minecraft:wooden_door', { open_bit: false });

harness.interact({ x: 0, y: 1, z: 0 });

harness.dimension.stateAt({ x: 0, y: 1, z: 0 }, 'open_bit'); // true

heldItem and silkTouchTool build the HookItem the hooks carry, so a test for waxing, shearing or silk touch names an item the same way a server passes one:

typescript
harness.interact(position, { itemStack: heldItem('minecraft:honeycomb') });
harness.breakBlock(position, { itemStack: silkTouchTool() });
harness.place(position, { face: 'north', faceLocation: { x: 0.5, y: 0.9, z: 0 } });

Both ship in the published package, because a plugin writing its own family wants the same harness.

The held item and the clicked face ​

onPlace, onBreak and onPlayerInteract carry itemStack, a HookItem with an identifier and a component reader, and onPlace carries the clicked face and faceLocation as well. Together they are what lets a block behavior answer a question about the hand rather than deferring it:

rules/heldItem.ts owns the item questions and rules/placement.ts the placement ones, so an item name or an enchantment id is written down once. Neither imports @jsprismarine/items: a HookItem is whatever the server hands the hook, and that package's ItemStack satisfies the interface structurally.

The interaction hook also receives whether the player was sneaking. Sneaking with a placeable block skips the block hook so the block can be placed against a chest or door. Other items reach the hook: a copper door opens before an axe can scrape it normally, while sneaking lets the same axe scrape it.

Values come from the block ​

Where a behavior needs a number, it reads it off the block rather than carrying its own copy. jsprismarine:block_properties is the source for push_reaction (the piston and the falling blocks), requires_correct_tool (the drop rule) and random_tick. Reading it goes through the component factory in @jsprismarine/blocks, so an absent component reads as that schema's defaults and a malformed one does too rather than failing the load. friction is published for the movement code and no family reads it, because friction is a decision the entity makes, not the block. Families emit candidate drops. The content break host checks requires_correct_tool against the held item's minecraft:tool rules and merged block tags before releasing loot or family drops.

The state names are the palette's. geometry.test.ts checks CARDINAL_DIRECTIONS against the captured palette's minecraft:cardinal_direction domain, and rules/weathering.test.ts walks every copper block in the palette and asserts that each name the three transitions produce is a block that exists.

Portals ​

rules/portal.ts is the block half of portals: the pure geometry over WorldActions, with the constants Java's PortalShape, PortalForcer and EndPlatformFeature use. portalFamily calls it from four hooks.

Two more functions are for the server's travel code rather than for a hook. portalCreationSite is Java's search for where a new portal goes: every column within 16 blocks of the target, a replaceable run on a solid floor with room for the 4 by 5 frame, the footprint plus a block on each side in the first pass and the footprint alone in the second, closest by 3D distance. When nothing fits the site is forced one block back from the target with y clamped to [70, maxY - 10]. writeNetherPortal writes the frame with corners and six portal blocks, and for a forced site an obsidian platform with four netherrack blocks on each side as Bedrock does. writeEndPlatform writes the 5 by 5 obsidian platform and three rows of air above it, destroying what is in the way.

The block list comes from PORTAL_BLOCK_NAMES in @jsprismarine/blocks, which is the same list the jsprismarine:portal family rule matches on, so the family and the geometry agree on what a portal, a frame and a fire are.

What is deliberately partial ​

The remaining limits need a world event or data this package does not own, or behavior from another runtime.

  • Family drops are fallbacks. An active minecraft:loot component selects a behavior-pack table, and mapped blocks without one use Java's table. Family-supplied drops remain for blocks without either table and for hosts with no content runtime; ore experience remains a separate block effect because loot tables do not carry it.

The rest are scoped to this phase:

  • Tree growth. A sapling grows a trunk with a two-layer canopy, not the species feature. The real trees belong to the feature runtime; this is enough for the sapling's own rule to be observable, and it is the one provisional piece of the package.
  • The sculk catalyst. Its charge comes from a mob death within eight blocks, and no block hook reports a death. The shrieker and the sensor are implemented.
  • Portal travel. The geometry is here (below), but which world is "the Nether", the 8:1 coordinate link, the destination search and the client's dimension change belong to the server, which owns the dimension list. @jsprismarine/prismarine's DimensionTravel is that half; docs/data-driven/dimensions.md describes the whole trip. The end gateway is claimed by the portal family and has no hook, so it teleports nobody.
  • Redstone wire topology. A wire fades one step per block from its neighbors. Stepping up and down over blocks, and the strong and weak distinction a solid block makes, need the solidity column the overlay is still missing.
  • Workstation screens. The crafting table, the loom, the smithing table, the enchanting table and the anvil open a screen. The block side is here; the screens are the item runtime's.
  • Bed and bamboo pairing. A bed finds its other half from the facing it was placed with, which no state carries afterwards, so a neighbor change falls back to the support check.
  • Education chemistry. Five blocks with no hooks, on purpose. A vanilla server does not run Education Edition screens.

MAX_LEAF_DISTANCE ​

const MAX_LEAF_DISTANCE: 6 = 6

Defined in: block-behaviors/src/rules/growth.ts:110

How far a leaf block may be from a log, through other leaves, before it decays.

Java's number, read out of LeavesBlock in the pinned 26.3 server jar. DECAY_DISTANCE is 7 there and decaying removes a leaf whose distance state has reached it, so 6 is the last distance that survives. Java carries distance as a block state and propagates it: updateDistance sets it to one more than the smallest of the six neighbors', counting a block in #minecraft:prevents_nearby_leaf_decay as 0 and anything that is not a leaf as 7. That tag resolves to #minecraft:logs, which is every _log, _wood, _stem and _hyphae and their stripped forms. The fixed point of the propagation is the breadth-first distance from the nearest log through leaves, so the search below computes the same answer without a state to store.

It was 4, which is Bedrock's. The trees here are built from Java's worldgen/feature data, and Java's TreeFeature.updateLeaves writes distances out to 6 from the trunk, so 4 condemned the outer rings of every canopy the generator placed.
