API reference / @jsprismarine/engine-systems

@jsprismarine/engine-systems ​

Shared world-system primitives that do not come from Bedrock data: tick scheduling, neighbor update ordering, redstone signal calculations, random tick selection, explosions, and the weather cycle. Resolved block families own block behavior, including fluid flow, fire, redstone state changes, and piston movement.

The Java-derived rules in this package are based on the pinned 26.3 server jar in node_modules/.cache/jsprismarine/java-server/. Source comments name the Java classes behind the transcribed behavior.

World access ​

The engine reads and writes blocks through a small WorldAccess interface. Block tick scheduling lives in TickScheduler, and explosions use a separate ExplosionWorld interface.

typescript
import { block, createEngine, createTestWorld } from '@jsprismarine/engine-systems';

const world = createTestWorld();
const engine = createEngine(world);
engine.setBlockAndUpdate({ x: 0, y: 0, z: 0 }, block('minecraft:stone'));

setBlockAndUpdate writes the block, runs the six neighbor updates in Java's CollectingNeighborUpdater order, and reports resulting signal power to the content bridge. It does not implement individual block behavior. The active block family's hooks handle placement, neighbor changes, scheduled ticks, and state transitions.

Hosts can pass shouldComputeRedstoneUpdate to createEngine to skip power scans for states with no onRedstoneUpdate hook. updateAround runs the same notifications after a host has already written the block.

Tick scheduling ​

TickScheduler owns the block and fluid tick lists. A scheduled tick carries a trigger tick, a priority, and insertion order. Ticks drain by trigger tick, then priority, then insertion order; the per tick budget defaults to Java's 65536 for each list. The host drains the scheduler and dispatches each tick to the active block family's onTick hook. TickList.snapshot() and TickScheduler.snapshot() return copies of pending work in stable order for diagnostics and replay comparisons; they do not restore a queue.

TickList uses one queue for the whole world. Java shards each list by chunk and merges those shards while draining, so a backlog can produce a different order. This queue runs the oldest due ticks first.

Redstone signals ​

This package calculates weak and strong signal, conductor re-emission, and wire connections for the Bedrock block identifiers the content families use. WorldSystems reports the resulting power to onRedstoneUpdate; @jsprismarine/block-behaviors owns the redstone components' state changes and scheduled behavior. The engine no longer owns their scheduled ticks or state transitions; it keeps the signal output rules needed to calculate the shared network.

Resolved minecraft:redstone_conductivity values override the Java full-cube conductor default. The vanilla overlay supplies the 28 exceptions extracted from Java's block registrations, and data-driven packs can declare the same component for their blocks. Collision shapes are not published, so the full-cube fallback remains an approximation for partial blocks.

Random ticking ​

The driver draws random_tick_speed positions from each selected section using Java's Level.getBlockRandomPos step, state * 3 + 1013904223. Positions are drawn with replacement; a position whose block does not take random ticks still consumes its draw. Block behavior comes from the active family's random tick hook. BlockRandomPositions.snapshot() reads the signed 32-bit generator state without drawing another position, and restore() reinstates a captured state without drawing. Replay harnesses can restore the counter at a recorded segment boundary when setup work before that segment was not captured.

Explosions ​

explode traces Java's 1352 rays from the surface of a 16 by 16 by 16 grid. It returns affected positions and entity hits; the host applies damage, knockback, drops, and entity callbacks. Blast resistance is read from the mapping table. Exposure treats full cubes as the only occluders because neither edition publishes collision shapes.

Weather ​

advanceWeatherCycle, resetWeatherCycle, and weatherCommandState model Java's saved rain and thunder counters. They are pure functions: the host stores the returned state, applies game-rule and dimension checks, and sends any client updates.

advanceWeatherCycle() ​

advanceWeatherCycle(state, randomInt): WeatherState

Defined in: engine-systems/src/weather.ts:107

One game tick of the cycle, Java's ServerLevel.advanceWeatherCycle.

The three counters run down in order of precedence. A clear spell outranks everything and pins the other two to one tick, so when it ends the next tick flips both. Otherwise each of thunder and rain either counts down - flipping its flag and booking the opposite stretch when it reaches zero - or, if it was already at zero, books its first stretch without flipping anything. That last branch is why a fresh world's weather does not change on tick one: the counters start at zero, and the first tick only decides how long to wait.

The caller decides whether to run this at all. Java gates it on the doWeatherCycle game rule and on whether the dimension can have weather, and neither is this function's business.

calculateExplodedPositions() ​

calculateExplodedPositions(world, center, radius): readonly BlockPosition[]

Defined in: engine-systems/src/explosions.ts:351

Every position a ray reached with intensity left, Java's calculateExplodedPositions.

One ray per cell on the surface of the 16-cube, which is 1352 of them: the interior cells are skipped because their direction is already covered by a surface cell. Each ray draws its own starting intensity, so two blasts of the same radius at the same spot do not carve the same hole.
