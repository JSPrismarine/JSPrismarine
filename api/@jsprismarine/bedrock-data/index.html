JSPrismarine / @jsprismarine/bedrock-data

@jsprismarine/bedrock-data ​

Minecraft Bedrock game data exported in a nodejs friendly way.

Where the data comes from ​

  • src/jsp/ is captured from a Bedrock Dedicated Server 1.26.51.1 by pnpm run dump:bedrock. The item table and the three payloads a client refuses to join without live at the top level, the Script API registries under src/jsp/bedrock/, the raw engine tables under src/jsp/packets/, and the reference world in src/jsp/reference_world.json.
  • src/resources/ is a link to a pinned download of CloudburstMC/Data, the Apache-2.0 dumps of the Bedrock tables. utils/build.js reads the creative menu, the actor identifiers, and the two item columns the capture does not record: each item's version and its component NBT. See Pinned upstream sources for how to fetch it and how to pick a Bedrock version.
  • src/vendor/ is data neither of the two carries, copied from projects that do. See its README for the source and license of each file.
  • src/jsp/java/ is dumped from the Java Edition 26.3 server jar, which Mojang ships unobfuscated since 26.1. block_properties.json holds the per-state block properties no Mojang report carries (hardness, blast resistance, friction, light, map color, sound type, push reaction, instrument, fire odds and the rest), with state-invariant values once per block and per-state differences under stateOverrides. entity_attributes.json holds the default attribute values, dimensions and category for the 93 entity types with an attribute supplier. See the next section for how to refresh them.

Refreshing the Java goldens ​

pnpm run dump:java is a capture-time task, run on a Java version bump rather than as part of the build. It downloads the pinned server jar through the piston-meta manifest chain, verifies its sha1, unpacks the bundler, compiles utils/java-dump/DumpJavaData.java against the server classes, runs it, and rewrites the two files under src/jsp/java/. Everything downloaded stays under node_modules/.cache/jsprismarine/java/.

The pinned version, its sha1 and the manifest URL are constants at the top of utils/java-dump/run.mjs. The dumper needs a JDK matching the jar's class file version (Java 25 for 26.3); the script finds one through JSP_JAVA_HOME, JAVA_HOME or, on macOS, /usr/libexec/java_home. src/javaGoldens.test.ts checks the shape of both files and the counts measured in docs/research/java-code-only-behavior.md; a version bump updates those counts with the goldens.

The root test command and @jsprismarine/worldgen test and vector commands prepare the inner server jar automatically. They download and verify the pinned outer jar, then cache its inner server jar under node_modules/.cache/jsprismarine/java/. This step does not run Java or change captured data. Set JSP_JAVA_SERVER_JAR to use an existing inner jar, or run pnpm --filter @jsprismarine/bedrock-data run ensure:java-server to prepare it separately.

Refreshing the Bedrock captures ​

pnpm run dump:bedrock is the other half of the same capture-time task, run on a Bedrock version bump and weekly rather than as part of the build. It copies the fetched server into node_modules/.cache/jsprismarine/bds-run/<version>/, makes the binary executable, turns the content log on, and drives four passes over the console, each with a world of its own:

PassWhat it doesWhat it writes
dumpRuns the dump behavior pack, which walks every Script API registrysrc/jsp/v<protocol>/bedrock/<table>.json
refworldGenerates the reference region through ticking areas, then reduces the saved worldsrc/jsp/v<protocol>/reference_world.json
packetsLogs a client in and records what the server sends itsrc/jsp/v<protocol>/*.json, *.nbt, packets/*.bin
palettePlaces every block type, then asks the game which values each property takespackages/minecraft/datagen/snapshot/v<protocol>/block-palette.json

Run one pass with --pass, and pass --force to copy the server again:

sh
pnpm run dump:bedrock --pass refworld

Where the capture can run ​

Mojang publishes the server for Linux x86-64 and Windows, and sources.json pins the Linux zip. On a Linux x86-64 machine dump:bedrock starts that binary directly, which is also what .github/workflows/capture.yml does on its ubuntu-latest runner. On any other host, an Apple Silicon Mac or a Linux arm64 box, it starts the same staged copy inside a Linux x86-64 container instead. You get the same four passes and the same files in the same places; only the thing that executes the binary changes.

The container path needs a container runtime whose daemon is running. The capture tries docker and then podman, and it asks each one for its server version rather than just looking on your PATH, because an installed Docker CLI with Docker Desktop stopped is the common case and it cannot start anything. If neither answers, the capture stops before it stages anything and tells you what to install or start.

Nothing is built or pulled that contains Mojang's binary. The container mounts the run directory under node_modules/.cache/jsprismarine/bds-run/<version>/, which already holds the copy the capture staged from the fetch cache, and runs ./bedrock_server out of the mount. The image is a stock docker.io/library/ubuntu:24.04, chosen because the server is dynamically linked against the glibc and libstdc++ of a recent Ubuntu and because redistributing the server in an image of our own is not something this project does. The server's UDP ports are published on 127.0.0.1 only, for the packets pass's client, and the container is removed when the run ends or when you interrupt it.

On an arm64 host the image is an emulated linux/amd64 one, running under Rosetta or qemu. Expect it to be several times slower than a native run, and refworld, already the longest pass, to be the one you wait on. The capture prints a warning when it starts under emulation, and it multiplies every stage timeout by four so that a slow run reports a stall only when something is genuinely stuck.

Four environment variables steer this, alongside the rest of the pipeline's JSP_* overrides:

VariableWhat it does
JSP_BDS_RUNNERauto (the default), native, or container. docker and podman also select container.
JSP_BDS_CONTAINER_CLIThe CLI to use instead of probing for one, for anything that takes docker run arguments.
JSP_BDS_CONTAINER_IMAGEA different base image, if the stock Ubuntu is missing a shared object your server version wants.
JSP_BDS_PATHAn unpacked server to capture, instead of the fetch cache. Works on either runner.

Forcing a runner is for diagnosis. JSP_BDS_RUNNER=container on a Linux x86-64 machine is how you reproduce a container-only problem, and JSP_BDS_RUNNER=native makes the capture fail loudly rather than quietly fall back when you expected the host's own CPU to be used.

The reference world ​

src/jsp/reference_world.json is what packages/parity/ compares a generator against, and utils/bedrock-dump/region.ts is the definition of "the reference region": a fixed seed, the Overworld, and 400 chunks at the world origin. Per chunk the file carries a sha256 of the stored heightmap, of the 3D biome arrays, of the topmost non-air block name per column, and of the layer 0 block states; plus the chunk's sorted block identifiers, its block entity count and its FinalizedState. Sixteen chunks at the origin are also kept whole, as plain arrays, so a failing digest can be read rather than guessed at, and one block histogram covers the region.

The four digests are the four rows Phase 4 of the plan exits on. A generator that produces the same world reproduces every one of them exactly.

Pinned upstream sources ​

sources.json pins the upstream publications the data pipeline reads: the Bedrock Dedicated Server zip, Mojang/bedrock-samples, the Java Edition server jar, SpyglassMC/vanilla-mcdoc, GeyserMC/mappings and CloudburstMC/Data, each with a version, URL and hash.

pnpm run fetch:sources downloads each source into node_modules/.cache/jsprismarine/<source>/<version>/, verifies its hash before unpacking, and skips sources whose verified content is already cached. It then writes pack-hashes.json, a sha256 per top-level folder of each source, so a version bump shows which folders changed. For offline work, JSP_BDS_PATH, JSP_JAVA_JAR_PATH, JSP_BEDROCK_SAMPLES_PATH, JSP_VANILLA_MCDOC_PATH, JSP_GEYSER_MAPPINGS_PATH and JSP_CLOUDBURST_DATA_PATH point at local copies and bypass the download.

Picking a Bedrock version ​

CloudburstMC/Data is pinned once per Bedrock protocol version, under versions in sources.json. Each version caches under its own cloudburst-data/v<protocol>/ directory, so several versions' dumps sit side by side.

pnpm run fetch:cloudburst fetches the version in defaultProtocolVersion and links it to src/resources; pnpm run fetch:cloudburst -- --protocol 2225 picks another. pnpm run generate fetches before it builds, so a fresh clone needs no extra step. Only the files under extract are unpacked, LICENSE among them: the dumps are Apache-2.0 and the license travels with them.

Running the Java data generator ​

pnpm run datagen:java runs Mojang's own data generator against the fetched server jar, after re-checking the jar's sha1 against sources.json. One run produces both halves of the Java data the rest of the repository reads, under the same gitignored cache:

  • vanilla-datapack/<version>/, the vanilla datapack. @jsprismarine/packs loads it as the Java member of the pack stack, the overworld generator reads its worldgen/* registries and block tags, and the loot, advancement, predicate, enchantment and feature corpus suites read it.
  • java-reports/<version>/generated/reports/, the data reports. The mapping and item table generators read them, and the overworld generator reads biome_parameters from them.
  • java-structures/<version>/, the 1511 structure templates. The data generator writes no NBT, so these come straight out of the jar; pnpm run extract:structures does that step on its own, for a checkout with no JDK.

The templates matter for speed rather than for correctness. The world generator can read them out of the jar, but that means inflating all 17655 of its entries on the first template a world places, inside chunk generation. The extracted directory is read one file at a time instead.

The generator writes no pack.mcmeta, so this step writes one from the pack_version the jar declares in its version.json; that file is what marks the directory as a loadable datapack. The same version.json names the JDK the jar needs, found through JSP_JAVA_HOME, JAVA_HOME, the java on PATH or, on macOS, /usr/libexec/java_home. The pinned Java Edition 26.3 jar asks for JDK 25 or newer; an older java earlier on PATH is skipped rather than used.

A second run is a no-op once all three directories hold the files the step checks for. Pass --force to regenerate:

sh
pnpm run datagen:java -- --force

The output is about 53 MB of Mojang's content and is never committed. JSP_VANILLA_DATAPACK and JSP_JAVA_REPORTS point consumers at a copy produced elsewhere.

Doing it in one step ​

pnpm run ensure:worldgen is the same work arranged for somebody who just wants a server running. It checks the three directories, and only if something is missing does it download the jar and run the generator. pnpm dev at the repository root runs it first, which is what makes pnpm install && pnpm dev enough on a clean clone.

On a complete cache it compares file names and exits, so repeat runs cost a fraction of a second and touch no network. When it cannot finish it prints one line saying why rather than a stack trace: no JDK, no network, or a generator that failed. It asks about the JDK before downloading the jar, so a machine without Java finds out immediately.

pnpm install deliberately does not do this. The jar is a 62 MB download that only somebody running a server needs, and builds, tests and CI arrange their own data.

Installation ​

To install @jsprismarine/bedrock-data, use the following command:

pnpm install @jsprismarine/bedrock-data --save

Item name to its Item Component Data, as network NBT, for every item that has any.

item_table ​

const item_table: Record<string, ItemTypeEntry> = item_table_data

Defined in: index.ts:49

The item table: every name the client can be told about, and the number it travels as.

The authority on the mapping - the client builds its registry from what we send, so everything naming an item has to agree with this one file.

Captured from a Bedrock Dedicated Server 1.26.51.1, not taken from a third party: the server sends it as ItemRegistryPacket, so a client that can log in can simply record it. packages/client/tools/capture-server-data.mjs is that client, and its output is jsp/v<protocol>/required_item_list.json. It stays under jsp/ rather than moving to resources/ because a capture of the version this server targets is the thing nothing else can promise.

The capture records no version. utils/build.js takes that one column from the submodule's runtime_item_states.json, a dump of 1.26.50 at the same protocol, and refuses to generate the table unless the two agree on every name, id and component flag. They do.

The version matters more than it looks. Against the 1.21.40 table this has 240 names it did not, and - the part that breaks quietly - 528 items whose number changed. A server on the old table does not fail; it puts the wrong number on the wire for a quarter of the items it knows, and the client shows something else.
