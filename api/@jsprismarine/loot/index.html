JSPrismarine / @jsprismarine/loot

@jsprismarine/loot ​

The Java Edition loot table evaluator. It parses the 1447 vanilla tables of Java 26.3 once into closures and rolls them against a context, reproducing Java's draw order, weight formula and random sequence seeding.

Java conditions and item modifiers are implemented by @jsprismarine/predicates, and this package composes them. It also reads Bedrock behavior-pack tables for data-driven entity equipment and interactions, applying the Bedrock set_count and set_data_from_color_index functions.

Install ​

bash
pnpm add @jsprismarine/loot

Rolling one table ​

typescript
import { createLootContext, lootSequenceRandom, parseLootTable, rollLootTable } from '@jsprismarine/loot';

const { value: table, diagnostics } = parseLootTable(json);

const context = createLootContext({
    parameterSet: table.parameterSet,
    parameters: { origin: { x: 0, y: 64, z: 0 }, block_state: { name: 'minecraft:coal_ore' }, tool },
    random: lootSequenceRandom(worldSeed, table.randomSequence)
});

rollLootTable(table, context);

Parsing never throws. Every fault lands in the returned diagnostics and the table rolls to whatever is still well formed, which is the same contract @jsprismarine/predicates has. Pass strict: true to get a LootGrammarError instead, listing every error, for a host that would rather refuse a table than roll it half-read.

Most servers will use the registry instead, because it already knows the world seed, the pack stack and each table's own context key set:

typescript
import { LootRegistry, javaLootTables } from '@jsprismarine/loot';
import { load } from '@jsprismarine/packs';

const { definitions } = load(stack);
const loot = new LootRegistry(
    { ...definitions, lootTables: javaLootTables(definitions.lootTablesJava) },
    { worldSeed: 1234n }
);

loot.validate(); // compiles every table and reports reference cycles
loot.roll('minecraft:blocks/coal_ore', { parameters: { origin, block_state, tool } });

The nine entry types are item, tag, loot_table, dynamic, slots, empty, group, alternatives and sequence. The original brief for this package listed eight and left the ninth open; the ninth is slots, which 26.3 added with the slot_source registry. Vanilla ships no slot source files and uses no slots entry, so this package parses the entry and hands its slot_source JSON to an injected view rather than implementing a slot model it has nothing to check against.

dynamic is the other entry whose body lives outside this package. Java calls these dynamic drops and uses them for contents a block entity carries into its own drop, such as a shulker box's inventory. There is one in vanilla, minecraft:blocks/decorated_pot for its sherds.

Counts come from the corpus test described below, and agree with the registry research note section 3.

What 26.3 renamed ​

If you are reading older loot documentation, four field names have moved, and this package follows the 26.3 jar rather than the wiki:

  • functions is now modifier, on the table, the pool and the entry alike.
  • conditions is now condition.
  • A loot_table entry names its target in value, not name, and the value may be an inline table, an id, a list, or a #tag.
  • A tag entry names its items in items, not name.

A table with no type falls back to the generic context key set, which is what LootContextParamSets.ALL_PARAMS is registered as.

What an unread key does ​

A loot table is gated data, so the two ways a gate goes missing both matter here, and both used to go unreported.

A key the grammar has no case for is an error. Nothing reads it, so it changes the file's meaning and not the roll, and a condition list sitting unread beside a pool is indistinguishable from a pool with no gate at all. The report names the key and the level it sat at:

pools[0].conditions: the java loot pool grammar has no conditions member, so nothing reads it

The table still rolls everything it could read, so one stray key does not empty a chest. The 1447 vanilla tables report nothing, which is what keeps the rule honest: every key they use is a key this package acts on.

A condition the grammar cannot compile closes its gate. 26.3's composition rule folds a condition field with and, and a term that fails to compile drops out of the fold, so a field holding one unimplemented condition folds to an empty and and passes. That is the wrong direction for loot to fail in. Any error raised while compiling a condition field closes that gate for good, at the pool and at the entry alike, and the error that closed it is already in the diagnostics.

The Bedrock dialect ​

Bedrock's behavior packs carry loot tables of their own, in the spelling Java used before 26.3 renamed four fields. bedrockLootTables reads that spelling. Java's path is untouched, because the 1447 datapack tables are this project's gameplay source.

typescript
const equipment = new LootRegistry(
    { ...definitions, lootTables: bedrockLootTables(definitions.lootTables) },
    { worldSeed }
);

equipment.roll('loot_tables/entities/zombie_equipment.json');

The dialect is a member of the source rather than an option beside it, and there is no third way to build a source. Both editions' tables are ReadonlyMap<string, unknown>, so while the two were stated separately nothing could tell a host that had paired the wrong two — and one had: the Bedrock map went into a field named lootTablesJava, and only a dialect: 'bedrock' written six lines away kept it right. Pairing them in the value is what makes that a compile error.

Reviewed gaps ​

BEDROCK_REVIEWED_CONDITIONS lists twelve condition types that read an entity or biome this roll cannot provide, and BEDROCK_REVIEWED_FUNCTIONS lists the 17 item functions still unimplemented. Each entry names what a result comes out as without it. A listed condition closes its gate and warns; a listed function is skipped and warns. BEDROCK_IMPLEMENTED_FUNCTIONS names the two functions already applied: set_count and set_data_from_color_index. anything unlisted is an error, because a reviewed gap has a bounded effect and an unreviewed one does not. That is the same rule the unread-key report applies, and it is what lets strict refuse a pack carrying something new without refusing a stock Bedrock server: over all 309 vanilla tables the registry reports 1484 warnings and no errors.

The runtime rolls Bedrock equipment tables and interaction tables such as the sheep's shearing table. It applies stack counts and copies minecraft:color into Bedrock item auxiliary data, so a sheared sheep drops the correct wool color and count. Other functions remain reported gaps; for example, mob equipment still skips enchant_random_gear and looting_enchant, so a skeleton's bow arrives unenchanted.

tiers reproduces Java's Mob.populateArmor. The draw lands in initial_range counted from the first entry, then climbs one rung per bonus_rolls that beats bonus_chance, stopping at the last entry. zombie_equipment.json states a range of 3 over six armor sets with three bonus rolls at 0.1087, so leather, copper and gold are common and diamond needs all three bonuses.

The two difficulty-scaled conditions read a LootDifficultyView. Without one they see normal difficulty in a fully ramped region, which makes a table's stated max_chance its actual chance: zombie_equipment.json arms one zombie in twenty from its 0.05, measured at 99 of 2000.

Evaluation order ​

One roll walks the table in Java's order, and the order is observable, so it is worth stating exactly.

  1. The table's pools run in file order.
  2. A pool whose condition fails is skipped whole.
  3. A pool rolls rolls plus floor(bonus_rolls * luck) times. The multiplication happens in 32-bit float arithmetic and is floored afterwards, so bonus_rolls of 0.6 adds nothing at luck 1 and two rolls at luck 4.
  4. Each roll expands every entry container in the pool into candidates. A container whose own condition fails contributes none. alternatives stops at the first child that contributes, sequence stops at the first child that does not, and group runs all of them.
  5. A candidate's weight is floor(weight + quality * luck), clamped at zero, again in float arithmetic. Candidates of weight zero are dropped before the draw.
  6. One candidate is drawn in proportion to weight. With a single candidate, Java skips the draw and takes it, which matters because it consumes no randomness.
  7. Each stack the candidate produces passes through the entry's modifier, then the pool's, then the table's. A modifier that discards a stack ends it there.
  8. Results above the item's maximum stack size are split into whole stacks and a remainder, which is what Java's public roll does. Pass split: false for the raw list.

The seeding rule ​

A table names a random_sequence, and Java keeps one stream per sequence id for the world. The stream is a Xoroshiro128++ generator seeded from the world seed upgraded to 128 bits, exclusive-ored with the MD5 hash of the sequence id, then mixed with Stafford variant 13 on both halves. That is reproduced bit for bit here, and random.test.ts checks the draws against Java oracle vectors.

Two consequences a server has to get right. Two worlds with the same seed break the same ore into the same drops, and two tables in one world never share a stream. Rolling one table twice must not replay the same draws, so LootRegistry creates each stream once and lets it advance, the way Java's RandomSequences does. Tables that name no sequence share one unkeyed stream, standing in for Java's level random.

typescript
import { lootSequenceRandom } from '@jsprismarine/loot';

lootSequenceRandom(1234n, 'minecraft:blocks/coal_ore'); // the stream that table draws from
lootSequenceRandom(1234n); // the fallback for a table with no sequence

Injectable seams ​

Every seam is optional. A table that reaches one the host left out reports a diagnostic and produces nothing there, rather than failing the roll.

  • The random source. Rolling uses only context.random, so a scripted or seeded source reproduces a draw exactly. That is what makes the distribution tests here exact counts rather than samples.
  • ItemStackOps, from @jsprismarine/predicates, owns stack construction, optional Bedrock auxiliary data, the stack size limit, and component writes. The splitter in step 8 asks it for maxStackSize.
  • DynamicDropSource answers a dynamic entry, keyed by the name the entry carries.
  • SlotSourceView answers a slots entry from its raw slot_source JSON.
  • LootContentOptions fills the content view described in the next section.

References and cycles ​

26.3 removed the reference condition and function and made every composable field accept an inline value, a namespaced id, a list mixing both, or a #tag. A loot_table entry's value goes through the same rule, so one entry can name several tables at once, and expand: true turns each into its own weighted candidate instead of rolling them all.

A reference that leads back to the table it started from reports a cycle instead of recursing. The registry finds cycles two ways. During a parse, the composition helper catches a reference already on the stack and reports it at the field that closed the loop. Separately, LootRegistry.cycles walks the raw JSON without compiling anything and gives each cycle as the chain that closes it, which validate() turns into a diagnostic:

loot table reference cycle: minecraft:a -> minecraft:b -> minecraft:a

The vanilla stack has 57 loot_table entries pointing at other tables, and no cycles.

Translating to Bedrock ​

A rolled result carries Java item identifiers. mapLootToBedrock translates it through an injected lookup, and javaItemToBedrock from @jsprismarine/mapping satisfies that lookup as it is. The mapping package stays a development dependency here, so this package never learns that two editions exist.

typescript
import { javaItemToBedrock } from '@jsprismarine/mapping';
import { mapLootToBedrock } from '@jsprismarine/loot';

const { stacks, losses } = mapLootToBedrock(loot.roll(id, request), javaItemToBedrock);

Nothing is dropped silently. A reviewed loss keeps the fallback item listed in @jsprismarine/mapping and reports one entry with the reason and its reference; an identifier the pinned Java version does not have is dropped and reports a loss of kind unknown. Losses come back one per affected stack, in the order the roll produced them, so a report can name the table that produced each.

Data component payloads ride along untouched. Translating a component to its Bedrock form belongs to the item layer, not to the loot evaluator.

Corpus test ​

corpus.test.ts loads the real Java 26.3 vanilla datapack through @jsprismarine/packs, which also checks the pack-stack adapter against the real loader rather than a hand-built double. It measures:

  • 1447 tables over 1589 pools, parsing with no diagnostic at all, neither errors nor warnings, and no reference cycles.
  • Six of the nine entry types in use: item 2556, alternatives 87, loot_table 57, empty 39, dynamic 1, tag 1.
  • Every table rolled 20 times from world seed 1234, throwing nowhere, with 1335 of the 1447 producing at least one stack.

The 112 that produce nothing produce nothing in the game either for that subject. They are the doors, beds and tall plants whose match_block wants a half or part the fixed block state does not carry, the genuinely empty tables (fire, spawner, budding amethyst, armor stand, most passive mobs), and the shearing tables that want a sheep color.

The test needs the cache that pnpm --filter @jsprismarine/bedrock-data run fetch:sources populates, so it only runs with JSP_VANILLA_DATAPACK set and CI without the cache skips it.

bedrockCorpus.test.ts is the same measurement for the Bedrock half, over the 309 tables of the composed BDS vanilla layers, behind JSP_VANILLA_BEHAVIOR_PACK. It pins the defect and its fix as numbers: the Java grammar arms 2000 zombies of 2000 from zombie_equipment.json, the Bedrock dialect arms 99. All 18 tables a minecraft:equipment component names parse with no error and roll something. The whole 309 report 400 unapplied functions, 71 untyped { min, max } providers, and 12 unimplemented condition types, counted so the gap cannot grow unnoticed.

Decisions worth knowing ​

The random sequence generator is implemented here rather than imported. It is the same Xoroshiro128++ that @jsprismarine/worldgen uses for terrain, but loot has no business depending on the terrain stack for sixty lines of arithmetic. If a third package needs it, the generator should move to a shared package and both should import it from there.

Cycle detection is a parse-time report, not a runtime guard. Java detects the loop at roll time with a visited set and logs "Detected infinite loop in loot tables". Reporting at parse time gives the same outcome, nothing produced at the point of recursion, and tells a pack author about it before a player opens the chest.

The table's declared context key set is checked against the roll's. rollLootTable reports when they disagree, because a table attached to the wrong context is the failure mode that otherwise looks like a table that quietly drops nothing. LootRegistry.roll takes the set from the table, so it never trips on its own.

The Bedrock loot conditions this package does not evaluate, each naming what it reads.

All twelve want the same two things and this package has neither for a Bedrock roll: the entity the table is being rolled for, and the world around it. A roll here carries a random source and a parameter set, so there is no killer to ask about, no variant to read off a mob and no biome under it.

Being on this list changes the report, not the roll: the gate still closes, because a condition nothing evaluates must not pass. It drops from an error to a warning for the reason reportUnreadKeys already applies to keys — what is lost is known and bounded, which is the whole difference between a reviewed gap and an unreviewed one. None of the twelve appear in the 18 equipment tables, which are the only Bedrock tables this server rolls. All 79 uses are on entity death drops and chest tables, and the server draws both from the Java registry.
