The End dragon fight: the chunks ​

The specification is docs/research/end-dragon-fight.md ("the fight note"); read it before any chunk, with the section numbers cited below. The target: a player can reach the End, see the ten spike pillars with crystals and the dragon with its boss bar, kill it (no flight AI needed; the placeholder goals that hold it in place are enough as long as it is visible, damageable and killable), watch the exit portal open with the egg on the first kill, enter the portal, see the credits, return to their spawn point, and respawn the dragon with four crystals on the portal's edges. Gateway teleports are deferred (fight note section 10): the blocks are placed, the teleport is a later slice.

Each chunk is sized for one agent, lands as one or a few Conventional Commits (type(scope): subject, imperative, 72 characters), and leaves the tree typechecking and green. Chunks in one wave touch disjoint packages or files; a chunk may start when its dependencies have landed. Follow commit discipline, run pnpm run lint:custom after the last edit of every chunk, and add a Changeset per published package changed (every package here is below 1.0.0: breaking is minor, feature or fix is patch).

The checks, as in data-driven-dimensions.md: package (pnpm --filter <pkg> run test and typecheck), types (pnpm run typecheck), custom (pnpm run lint:custom), corpus (pnpm --filter @jsprismarine/parity run test then dashboard). The Overworld corpus must stay byte-identical in every chunk; chunk 5 changes End chunk contents on purpose, which no corpus pins today, and extends the worldgen.dimensions parity test to pin the new End output instead.

Project-wide roadmap status and the current milestone are maintained in the data-driven vanilla plan; this file tracks the End fight execution details.

Open questions needing a real client ​

Record answers in docs/data-driven/dimensions.md (or the page chunk 9 adds) when found.

  1. Does the retail client keep the boss bar when the dragon is outside its tracking range? The bar binds to a tracked actor and PowerNukkitX resorts to a dummy actor (fight note section 9). If the bar drops, follow the dummy-actor pattern in chunk 6.
  2. Which Bedrock events render Java's level events 3001 (summon roar), 3000 (gateway spawn) and 1028 (dragon death sound)? No verified mapping exists; chunk 7 and 8 ship candidates (ActorEvent.DRAGON_START_DEATH_ANIM = 37, LevelEvent.PARTICLES_EXPLOSION = 2025, LevelSoundEvent.EXPLODE = 48, the mob.enderdragon.* sound names) and a run against a retail client decides.
  3. Does the client draw the crystal beam from BLOCK_TARGET actor data alone? The vanilla render controller suggests yes (fight note section 9); verify with a retail client.
  4. Does the retail client accept ChangeDimension while the credits screen is up, or must the server hold the transfer until the serverbound EndCredits reply? Chunk 4 holds the transfer as the safe default, matching Java's PERFORM_RESPAWN exchange.
  5. Bedrock's egg-on-second-kill quirk (MCPE-51345) and its podium self-repair are wiki claims. This plan follows Java (first kill only, no self-repair); revisit only if a retail client comparison shows players expect the quirk.

Chunk 1: seed-derived spikes and crystal options in @jsprismarine/features ​

Goal. Verify end_podium against the exact shape in fight note section 2 and fix any difference.

Files. New packages/features/src/features/endSpikes.ts with test; packages/features/src/features/structural.ts (endSpike at 1041-1099 uses the seed list when spikes is empty and forwards the crystal options at 1092-1094; end_podium at 983-1010); packages/features/src/world/FeatureWorld.ts (spawnEntity at 147 gains options, and the interface exposes the world seed if it does not already); packages/features/README.md.

Public API.

ts

export const endSpikesForSeed: (seed: bigint) => readonly EndSpike[];
// FeatureWorld

    yaw?: number; beamTarget?: { x; y; z }; showBottom?: boolean; invulnerable?: boolean;

endSpikesForSeed ports Java's two-step derivation: key = Java-LCG(seed).nextLong() & 65535n, then Fisher-Yates over 0..9 with Java-LCG(key) (nextInt(i) swaps as the fight note says), positions floor(42 * cos/sin(2 * (-PI + 0.3141592653589793 * i))), radius 2 + n/3, height 76 + 3n, guarded at n 1 and 2. Reuse an existing Java Random port if one is importable (the worldgen package has the LCG); otherwise implement the 48-bit LCG locally with a JSDoc citing SpikeCacheLoader.load.

Tests. The ten positions match the fight note's list for any seed; radius, height and guarded per shuffled index; one pinned seed's full spike list asserted (compute once, cite the derivation); empty spikes in the config produces the seed list; crystal options reach spawnEntity; the podium test covers the 16 rim cells, 20 portal cells when active and air when inactive, the 4-high pillar and the 4 torches.

Chunk 6: the DragonFight service: state, scan, dragon, bar ​

Goal. The End world owns a persistent fight: it knows whether the dragon is alive, keeps the exit portal location, spawns the dragon when needed, and runs the boss bar.

Files. New packages/prismarine/src/world/end/DragonFight.ts with test (and worldFeatureAdapter.ts if placing the podium needs a FeatureWorld over a live World); packages/prismarine/src/world/World.ts (a lazy getDragonFight() like getPortalIndex() at 1915, created only when the dimension type has hasEnderDragonFight; ticked from World.update beside portals at 751); packages/prismarine/src/world/WorldPersistence.ts (interface at 43-51, parser at 62-78), packages/prismarine/src/world/providers/leveldb/LevelDB.ts (writeWorldData whitelist at 186-196), their tests.

Public API.

ts
export interface DragonFightState {   // persisted as WorldPersistenceData.dragonFight
    dragonKilled: boolean; previouslyKilled: boolean; needsStateScanning: boolean;
    dragonUniqueId?: bigint; exitPortalLocation?: { x; y; z };
    gateways: number[];               // remaining indices, seed-shuffled on first init
    respawnStage?: 'start' | 'preparing_to_summon_pillars' | 'summoning_pillars' | 'summoning_dragon';
    respawnTime: number; respawnCrystalIds: bigint[];
}
export class DragonFight {
    constructor(world: World, state: DragonFightState | undefined, seed: bigint);
    tick(): void;
    onCrystalDestroyed(entity, source): void;   // chunk 8 wires the caller
    tryRespawn(): boolean;                      // chunk 8
    setDragonKilled(dragon): void;              // chunk 7
    state(): DragonFightState;                  // for persistence
}

Behavior in this chunk (fight note sections 1 and 2): persist through WorldPersistenceData.dragonFight (three edits: interface, parser, whitelist; round-trip test); on first init shuffle gateways 0..19 with the Java LCG over the world seed (reuse chunk 1's LCG); tick runs only while a player is within 192 of (0, 128, 0) (the arena ticket is approximated by "a player is near"; note the simplification in a JSDoc); scan once: find an exit portal by the bedrock ring pattern within 8 chunks of (0, 0) or place the inactive podium through the end_podium feature and record the location (heightmap at (0, 0), stepping down through bedrock while y > 63); spawn the dragon through EntityRuntime.spawn('minecraft:ender_dragon', (0, 128, 0)) when !dragonKilled and none exists (re-check every 1200 ticks); run a BossBar named entity.minecraft.ender_dragon (pink, progress): add and remove players on the 192 radius every 20 ticks, percent from the dragon's health component. Dragon healing from crystals (+1 per 10 ticks while one is within 32) is included; it is ten lines and changes how beatable the fight feels.

Tests. Over the LevelDB harness with a void End stem and hand-written blocks: a fresh fight scans, places the inactive podium at the heightmap and persists the location; a saved state is not rescanned; the dragon spawns once and its unique id is kept; the bar adds a near player and removes a far one; health updates the percent; state() round-trips through WorldPersistence.test.ts; the gateway shuffle is stable for a pinned seed.

Changeset. @jsprismarine/prismarine patch.

Verify. package on prismarine, types, custom.

Chunk 8: respawning the dragon with four crystals ​

Goal. Placing four end crystals on the exit portal's edges runs the full respawn: beams, pillar reset with new invulnerable crystals, dragon summon, crystal destruction, with aborts. Fight note section 6.

Files. packages/item-behaviors/src/behaviors/placement.ts (112-130: the minecraft:end_crystal path gains Java's placement rules: obsidian or bedrock base, empty block above, no entities in (x..x+1, y+1..y+3, z..z+1), spawn centered at (x + 0.5, y + 1, z + 0.5) with showBottom: false, then a host hook); the item host adapter in packages/prismarine/src/item/contentAdapter.ts:210-217 (route the hook to world.getDragonFight()?.tryRespawn()); packages/prismarine/src/world/end/DragonFight.ts (tryRespawn, the stage machine, onCrystalDestroyed); the crystal death path notifies the fight (EntityRuntime removal hook from chunk 2); tests beside each.

Public API. None new outside DragonFight; the item-behaviors hook follows the existing host-action pattern (ask the host before spending an item on an action).

Behavior. tryRespawn requires dragonKilled and no stage, finds crystals in the four cells at exitPortalLocation.above(1).relative(dir, 3), rewrites the old podium's bedrock and portal blocks to end stone, rebuilds the inactive podium, and starts the stages. The stages run in tick with Java's numbers: START (beams to (0, 128, 0)), 100 ticks of roar events (open question 2's candidates), 40 ticks per pillar in endSpikesForSeed order (beam to the pillar top, clear the ±10 box, explosion power 5, re-place that spike through the chunk 1 feature with crystalInvulnerable: true and beam (0, 128, 0)), 100 ticks of summoning (beams to center; at the end reset pillar crystals to vulnerable with no beam, explode and remove the four respawn crystals at power 6 with no block damage, spawn the dragon, clear dragonKilled). Destroying a respawn crystal aborts: stage cleared, pillar crystals reset, active podium restored. respawnStage, respawnTime and the crystal ids persist, and a reload with missing crystals aborts.

Tests. Item placement accepted on obsidian and bedrock and refused elsewhere or when blocked; placement on a non-fight world spawns a crystal and nothing else; four crystals start the sequence and three do not; the stage timeline over a fake clock (beam targets per stage, pillar re-place order and invulnerability, the summon at the end, totals 601+ ticks); abort on crystal death mid-sequence restores the active podium; state round-trips mid-sequence.

The order, and what it buys ​

After waveWhat works
0Spikes derive from a seed in a harness; crystals explode and show beams; a boss bar class exists; the credits round trip works over today's End exit.
1A generated End has pillars and crystals; the End world has a dragon, a bar and persisted fight state.
2The dragon dies properly: open portal, egg, gateway, XP. Four crystals bring it back.
3A parity row and a client test prove it; the docs describe it.

Risks, worst first ​

  1. The death race in chunk 2. The crystal fix touches the shared death path (EntityRuntime.ts:916-941); a regression there affects every data-driven mob. Keep the change to "run a zero-fuse explode queued by the killing hit before removal" and lean on the live tests.
  2. The fight's block writes run inside a tick. setDragonKilled and the respawn stages write dozens of blocks and one explosion per pillar; batch through the normal block write path and spread nothing across ticks that Java does not (the stages are already paced at 40 ticks per pillar).
  3. Boss bar visibility (open question 1). If the retail client drops the bar out of range, chunk 6 needs the dummy-actor fallback; design BossBar so the actor id is a constructor input, not a hard bind to the dragon.
  4. The End generation change in chunk 5. New End chunk bytes are intended, but the worker plumbing touches ProtoChunk and the pipeline; the Overworld corpus run is the guard that nothing else moved.
  5. Respawn-state persistence. A save mid-sequence with entity references is the only place the fight stores entity ids; resolve them leniently and abort when they are gone, as Java does, rather than crashing a load.
