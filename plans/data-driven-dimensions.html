Data-driven dimensions: the chunks ​

The decision is ADR 0004. This file is the execution order. Each chunk is sized for one agent in its own git worktree, lands as one or a few Conventional Commits, and leaves the tree typechecking, the tests green and the parity dashboard free of new red rows. Chunks are grouped into waves. Chunks in one wave touch disjoint packages or disjoint files and can run concurrently; a chunk may start when every chunk it depends on has landed on the integration branch.

Project-wide roadmap status and the current milestone are maintained in the data-driven vanilla plan; this file tracks the dimensions execution details.

Before any chunk ​

Read ADR 0004, then the research note the chunk cites. The three notes are the specification:

  • data-driven-dimensions.md (below, "the dimension note"): sections 1 and 2 for the data shapes, 4.3 for the proposed types, 4.6 and 4.7 for config.
  • dimension-storage-network-config.md ("the storage note"): section 1 for disk fields, 2 for the worker pool, 3 for packets, 5 for the test order.
  • portals-and-dimension-travel.md ("the portal note"): sections 1 and 2 for the rules with Java's constants, 3 for the wire sequence, 6 for the design and test plan.

Two corrections to the notes, found while verifying paths for this plan:

  • @jsprismarine/mapping keeps its data under packages/mapping/src/tables/ and types them in packages/mapping/src/tables.ts, not under src/data/. The overlay file is packages/mapping/src/tables/dimensions.json.
  • Protocol-gated fields are declared with gated(SINCE_2225, ...) from packages/protocol/src/wire/wireGates.ts in a declarative layout, as addActor.ts and animate.ts do. DimensionDefinition is still a hand-written NetworkStructure class whose serialize(stream) has no protocol version, so chunk 4 moves it to a declarative structure.

Warm the Java data cache before any chunk that generates terrain:

sh
pnpm --filter @jsprismarine/bedrock-data run ensure:worldgen
node scripts/real-data-env.mts

Run corpus in every chunk that touches packages/prismarine/src/world/generators/, packages/chunkgen or packages/worldgen. No chunk in this plan changes generated Overworld blocks; a corpus diff is a defect in the chunk.

Every chunk that changes a published package adds a Changeset with pnpm changeset, choosing the bump from the versioning policy: every package here is below 1.0.0, so a breaking change is minor and a feature or fix is patch. The Changeset file is part of the chunk's commit. Where a chunk edits a package README or a docs/ page, that edit is in the same commit as the code it describes.

Commit messages follow the repository's Conventional Commits rules (type(scope): subject, imperative, lowercase, 72 characters, identifiers in backticks).

Open questions an implementer must verify against a real client ​

Record the answer in docs/data-driven/dimensions.md (chunk 23) when found.

  1. Does Mojang's retail client accept ChangeDimension to a Dimension ID of 1000 or more, and then accept LevelChunk with that id? The client-e2e suite verifies both with its pinned Cinnabar 1.26.60 client, and player travel is enabled. Test the retail client before claiming compatibility with it.
  2. Does the client keep inventory, effects and attributes across ChangeDimension? Geyser re-sends attributes and relies on the Java server for effects. Chunk 16 re-sends attributes and inventory after EndLoadingScreen as the safe default; measure whether it is needed.
  3. Does the client honor StartGame.generator = 3 (Nether) or 4 (End) when the spawn dimension is not the Overworld, or must generator always describe the Overworld stem? Chunk 17 sends the Overworld stem's generator type as the dimension note's section 4.8 says.
  4. Does a 2225 client accept a DimensionDefinition with Cloud Height and Render Clouds appended, and a 2193 client one without? Chunk 4 round-trips both layouts; only a live client proves the field order.
  5. How many chunks around the arrival position must arrive before the client closes the loading screen? Geyser sends empty chunks in radius 3 when it has none. Chunk 16 sends the real arrival chunks first; if the screen hangs on a slow pipeline, fall back to Geyser's empty chunks.

Risks, worst first ​

  1. The World constructor change in chunk 14 touches every World*.test.ts. There are more than thirty. Build fakeLevel() first and migrate tests by search and replace; do not weaken any assertion to get there.
  2. Custom ids above 999. Cinnabar 1.26.60 accepts custom id 1000 in client-e2e. Mojang's retail-client behavior remains unverified; track that compatibility separately from server travel support.
  3. The shared pool in chunk 12 changes DataDrivenGenerator's cache shape. The corpus is the net; a byte difference there is a bug, not a re-capture.
  4. Chunk 2's composite worldgen registry id is a judgment call about Definitions' key space. If the identifier report or the mcdoc validator in packages/packs assume one directory per registry, split into one id per kind instead and say why in the commit.
  5. The portal note's Bedrock-only rules (128 search radius both ways, player-only creation, netherrack flanks, no passengers) are in DIMENSION_TRAVEL and PORTALS as data. Keep them there; a condition in code is how the next person loses track of which edition a rule came from.
