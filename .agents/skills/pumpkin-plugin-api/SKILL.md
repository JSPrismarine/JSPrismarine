# Pumpkin plugin API

The API is a WIT world. A plugin is built against the upstream commit pinned in
`tools/pumpkin-api/wit.lock.json` and runs on the Pumpkin release the integration tests download. Don't code
against the upstream branch head, docs or memory: the API changes between releases, and a call that doesn't
exist in the pinned version fails at build time or, worse, at load time.

## Find the definition

1. **Versions.** `tools/pumpkin-api/wit.lock.json` pins the WIT repository, branch and immutable commit;
   `PUMPKIN_RELEASE` in `tools/test-harness/src/pumpkin-version.ts` pins the server. Verify their plugin
   ABI compatibility; the API package version and server release tag use different version identifiers.
2. **The WIT**, which is the source of truth: run `pnpm --filter @pumpkin-plugins/pumpkin-api typecheck` to
   fetch the locked `v0.1` package, then inspect `.cache/pumpkin-api-wit/<lock-digest>/v0.1/*.wit` in the
   repository root. The build caches by the full `wit.lock.json` digest, so confirm the digest before
   comparing files. `event.wit` lists events and payloads; `command.wit` and `permission.wit` describe their
   respective APIs.
3. **The types your code compiles against**: `build/types/bindings/` in the plugin's folder, generated by
   `pnpm typecheck`. Trust these over the package's own `.d.ts`. The build preserves WIT `u64`/`s64`
   as JavaScript `bigint` in both directions. Use those types for raw host calls; convert to `number`
   only within the safe integer range. See [Runtime caveats](../../../docs/building.md#runtime-caveats).
4. **The SDK classes** (`Plugin`, the event and command helpers): resolve the API package's entrypoint
   from its `package.json` (`main`/`types`). Read a helper before using it and check its arguments
   against the generated bindings.

## Check what the server does

The WIT says what you can call, not when an event fires, what canceling it does, or which permission names
exist. For that, read the Pumpkin source at the pinned release tag (the value of `PUMPKIN_RELEASE`, which is
also the tag name):

| Question | Where, in Pumpkin |
| --- | --- |
| The WIT as the server sees it | `crates/pumpkin-plugin-wit/v0.1/` |
| What a host call does | `crates/pumpkin/src/plugin/loader/wasm/` |
| Where and when an event fires, and what canceling it skips | `crates/pumpkin/src/plugin/api/events/`, then search for where the event is fired |
| Permission names and defaults | `crates/pumpkin/src/plugin/permissions.rs` |

Read files at the tag without cloning:

```sh
gh api "repos/Pumpkin-MC/Pumpkin/contents/crates/pumpkin/src/plugin/api/events?ref=$RELEASE" --jq '.[].name'
curl -sL "https://raw.githubusercontent.com/Pumpkin-MC/Pumpkin/$RELEASE/crates/pumpkin-plugin-wit/v0.1/event.wit"
```

`$RELEASE` is URL-encoded in the `gh api` form (`+` becomes `%2B`). A local Pumpkin checkout may be on
`master`. Use it to find your way around and search, then confirm the details at the pinned tag, because
`master` is often ahead of the pinned release.

## Use the repo's wrappers first

Before calling the raw API, check whether a package in `tools/` already wraps it. They exist because the raw
calls require correct resource ownership, task IDs and callback IDs, and the wrappers have fakes for unit tests.
Scheduler wrappers accept safe integer tick counts and pass `bigint` delays/periods to the host;
handler and task IDs remain `u32` (`number`).

| Need | Use |
| --- | --- |
| Commands and their permissions, documented in the README from the same declaration | `defineCommands` from `@pumpkin-plugins/docs`, `registerCommands` from `@pumpkin-plugins/plugin-kit/register-commands` |
| Logging, repeating tasks, command callbacks | `@pumpkin-plugins/plugin-kit/host`; wrap `hostLogger` with `taggedLogger` from `/logger` so every line names the plugin |
| The plugin's data folder | `@pumpkin-plugins/plugin-kit/data-dir` (behind the `DataFiles` interface in `/files`) |
| Messages to other plugins | `@pumpkin-plugins/plugin-kit/ipc` |
| Errors from WASI calls | `@pumpkin-plugins/plugin-kit/wasi-error` |
| Socket steps that report `would-block`, and IPv4 socket addresses | `@pumpkin-plugins/plugin-kit/wasi-socket` |
| Monotonic time in milliseconds; WASI `u64` values as numbers | `@pumpkin-plugins/plugin-kit/wasi-clock`, `/wasi-number` |
| Parsing and formatting IPv4 addresses | `@pumpkin-plugins/port-mapping/ipv4` |
| Settings | `@pumpkin-plugins/config` ([Plugin config](../../../docs/plugin-config.md)) |
| Opening a router port | `@pumpkin-plugins/upnpumpkin-api` ([Port forwarding](../../../docs/port-forwarding.md)) |
| Fakes of all of the above for unit tests | `@pumpkin-plugins/plugin-kit/testing` |

The exports are listed in each package's `package.json`. If a second plugin needs something you are about to
write against the raw API, put it in one of these packages instead.

## Files and network

A plugin can only use the filesystem or sockets when its `pumpkinPlugin.wasi` in `package.json` asks for them
(`"filesystem"`, `"sockets"`, `"udp"`, `"http"`). See [Files and network access](../../../docs/creating-a-plugin.md#files-and-network-access).
Keep that code in a thin adapter behind an interface, as `WasiDataDir` does for `DataFiles`, so the logic can be
tested without a server.

## Permissions

Pumpkin asks the operator to approve a plugin's permissions on the server console unless its plugin config
pre-allows them or turns `ask_permission_confirmation` off. It remembers the answer for that plugin file and
permission list, so a rebuilt `.wasm` or a changed list asks again. A hot reload can't show the prompt, so a
plugin that would need one is denied and skipped; test with a restart. Names in `info.permissions` are typed
against `PUMPKIN_PERMISSIONS`. Command permission nodes are declared with the command and must start with
`<PluginName>:` ([Plugin info and READMEs](../../../docs/plugin-info-and-readmes.md)).

## When the API doesn't have what you need

Explain the missing capability with the closest WIT definition. Continue any independent work and use a
supported design if it satisfies the request. Don't rely on undocumented host behavior. Change the pinned
versions only when the task calls for an API upgrade; the API package, server release and integration tests
move together.
