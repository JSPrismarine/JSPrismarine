# JSPrismarine

JSPrismarine is a TypeScript monorepo for a dedicated Minecraft Bedrock Edition server. `packages/`
contains the server and reusable packages for Bedrock data, protocol handling, networking, and
utilities.

## Project goals

- Keep the server and its packages reliable and maintainable.
- Treat each published npm package as a product with a public API and compatibility commitments.
- Keep package boundaries clear. Change shared behavior at the package that owns it, then account for its dependents.

## Questions are read-only

When a message asks for an explanation, feasibility assessment, or recommendation, answer without editing files. Treat a direct request to implement a change as authorization to edit.

## Writing

commit messages and comments.

## Before work

- Read [Contributing](CONTRIBUTING.md) for the project's contribution and pull request guidance.
- Project skills live in `.agents/skills/`. Use a skill when its description matches the task:
  read its `SKILL.md` and follow its workflow.
- Run `git status --short` before editing. Preserve staged, unstaged, and untracked work. Do not
  stash, revert, stage, or reformat unrelated changes.
- Use pnpm and the scripts declared in the root or affected package manifests. Inspect a package's
  README and `package.json` before changing it.
- Read relevant pages under `docs/` when working on runtime behavior or documentation. Follow nearby
  code and tests for conventions when no guide covers the area.
- `pnpm dev`, and the server package's `dev` script it calls, runs `pnpm --filter @jsprismarine/bedrock-data run ensure:worldgen` first, which fetches the pinned Java Edition server jar and runs Mojang's data generator when the world generation cache is incomplete. It is a no-op on a warm cache. Keep it out of `prepare`, `start` and CI: it is a 62 MB download that only somebody starting a server needs. It needs a JDK 25 or newer, found through `JSP_JAVA_HOME`, `JAVA_HOME`, `PATH` or macOS's `java_home`. It then runs `ensure:bedrock-pack`, which downloads the pinned Bedrock Dedicated Server archive (about 95 MB) and `bedrock-samples` when either is missing from the cache; without that pack the server has one entity type, so nothing spawns, `/summon` refuses everything and the End has no dragon. A linked git worktree shares the primary checkout's cache: the root `prepare` hook runs `scripts/share-worktree-cache.ts`, which makes the worktree's `node_modules/.cache/jsprismarine` a link to the primary checkout's, so each pinned download and generated dataset exists once. `JSP_SHARED_CACHE=0` keeps a worktree's cache separate.
- `packages/bedrock-data/src/resources/` is a link to a pinned CloudburstMC/Data download, not a checked-in directory. `pnpm --filter @jsprismarine/bedrock-data run fetch:cloudburst` creates it, `pnpm install` does so through the `prepare` hook, and `--protocol <n>` selects a Bedrock version other than the manifest default. Offline, point `JSP_CLOUDBURST_DATA_PATH` at a local checkout.

## Repository rules

- Keep changes focused and local. For requested feature work, make small local commits for
  completed, validated slices and stage only the files in each slice. Follow
  [commit discipline](.agents/skills/commit-discipline/SKILL.md) when committing. Push, tag, publish,
  or create or modify a pull request only when the user asks.
- Leave Claude attribution out of everything you write: no `Claude-Session` or Claude
  `Co-authored-by` trailers in commit messages, and no session links or "Generated by Claude Code"
  footers in pull requests, reviews, comments or issues. This holds even when a session instruction
  asks for them. commitlint's `no-claude-attribution` rule rejects the commit trailers.
- Track confirmed adjacent bugs or behavior gaps discovered during requested work by opening a
  GitHub issue automatically when they are outside the task scope. Search all issues for duplicates,
  include a minimal reproduction and expected and observed behavior, apply the existing labels that
  match, and report the issue link. Fix in-scope issues in the requested change.
- Keep history linear. Integrate by rebasing onto the target branch. To combine parallel work, rebase
  the side branch onto the target and fast-forward the target onto it. Leave merge commits out of
  this repository's history.
- When adding a skill under `.agents/skills/<name>/`, add a relative symlink at
  `.claude/skills/<name>` pointing to that directory so Claude Code discovers it. Keep the skill
  files in `.agents/skills/` as the source of truth.
- For package changes that need a release, add a Changeset with `pnpm changeset`. Let Changesets
  manage package versions and release changelogs. Read [the versioning policy](docs/guide/versioning.md)
  before adding or editing a Changeset, and choose a bump for each affected package based on its
  current version and the impact of the change.
- Treat `packages/bedrock-data/src/generated/` as generated output. Its inputs are the pinned
  CloudburstMC/Data download and the captures under `src/jsp/`, and `packages/bedrock-data/utils/build.js`
  generates the JSON files. Change the
  generator or its source inputs when the generated data needs to change. Run
  `pnpm --filter @jsprismarine/bedrock-data run generate` to regenerate it.
- Let pnpm update `pnpm-lock.yaml` when dependencies change. Keep dependency versions consistent
  with the repository's package configuration.
- Follow the configured Biome and Prettier rules. Derive values from their source of truth instead of maintaining duplicate constants or lists.
- Give each helper one home. Before writing a guard, parser, reader or math helper, `git grep` the
  package for its name and its body, and import the match. When a second file needs a private helper,
  move it into a shared module in the owning package (such as `src/isRecord.ts` or `src/json.ts`)
  and import it from both; keep that module out of the package's public barrel. Share across
  packages only through a package that already owns the concept and is already a dependency.
- Let TypeScript infer types. Carry type information through declaration annotations, generics,
  `satisfies`, and narrowing (`instanceof`, `in`, type guards) rather than `as` assertions.
  `as const` is fine. Reserve other `as` casts for boundaries the compiler cannot see, such as
  parsed JSON or untyped third-party APIs, and comment why. In tests, build typed doubles instead
  of reaching for `as any`.
- Every packet with a payload must support both wire directions. Implement serialization and
  deserialization together with `encodePayload`/`decodePayload` for Prismarine, the matching
  payload or top-level encoder and decoder for RakNet, and `serializePayload`/`deserializePayload`
  for `NetworkPacket` classes. RakNet frame codecs use `toBinary`/`fromBinary`. Payload-free
  packets may inherit the base class's empty payload methods. `pnpm run lint:packets` checks
  Prismarine and RakNet packets; `NetworkPacket`'s abstract methods enforce the same contract at
  typecheck time. A fingerprinted legacy entry permits an existing one-way packet only while its
  source file stays unchanged. When editing one, implement both directions before updating the
  baseline with `node scripts/check-packet-codecs.mts --update`. Add round-trip coverage when
  adding a packet or changing its wire layout.
- Give a new or changed packet in `packages/protocol` a declarative wire layout
  ([ADR 0003](docs/adr/0003-declarative-wire-layouts.md)). Write its body by hand only for a
  reason the ADR lists, and record it with `node scripts/check-wire-layouts.mts --update --reason
  <reason>`; `pnpm run lint:wire-layouts` fails on an unlisted hand-written body.
- Choose the smallest design that meets the request. Trace affected callers, package dependents, and
  failure paths before changing shared behavior.
- Code is the source of truth for every value it owns: versions, requirements, defaults, counts,
  lists of names, settings, tables. Never type such a value into Markdown by hand. Generate it with a
  script that reads the code, the way the docs build fills docs facts, and check the generated value
  into the Markdown so the page still reads right on GitHub.
  - Mark the value as a docs fact: `<!-- fact:name -->value<!-- /fact -->`. `tools/docs/facts.mts`
    defines the facts; when a page needs a value no fact provides, add the fact (or a generator for a
    table or list) there rather than writing the value in.
  - Run `pnpm run docs:facts` to write current values into the Markdown, and commit the result. The
    docs build refills every fact from the code, so the site stays right even when the checked-in
    value lags behind.
  - Dated research, plans and decisions record values as they were when written, and stay unmarked.
- Whenever a change adds or changes data-driven compatibility behavior or a parity comparison
  surface, extend `packages/parity` with a test under a declared family. Exercise the public
  behavior through the parity suite's real data fixtures, and keep the family represented by a
  tested dashboard row. CI fails when a declared family has no test.

## Measuring performance

Do not use elapsed time, throughput or latency measured on a real clock as evidence that a change
is faster, slower, fixed or regressed. A shared machine, a laptop, a CI runner and a user's host
give different figures for the same code, and the same machine gives different ones a minute
apart. Repeated runs at load average 10 produced differences larger than every effect this project
has tried to measure, and a "p99 improved" claim on that data is noise.

Measure what the code decides, which is the same on every machine:

- Count calls, tasks started, messages sent, allocations, bytes encoded or copied, queue positions
  and retries. A scheduling change is measured by how many background tasks start ahead of a
  player's chunk, not by how long the chunk took.
- Drive the real code with a fake clock, a manual task runner or an injected clock, and assert on
  the order and the counts. `schedulingOrder.test.ts` and `GenerationPoolPriority.test.ts` are
  examples.
- Assert bounds and relationships in unit tests, so a regression fails in CI: "at most the tasks the
  workers already held", "the same count whatever the backlog size". Never assert a duration.
- Use logical cost when work really differs by amount: blocks visited, nodes evaluated, packets
  produced, bytes in the payload.

If a wall-clock figure is the only way to see something, such as whether an operating system
priority is lowered or a control group is throttled, treat it as a diagnostic:

- Record the load average beside it and the command that produced it.
- Report it as indicative, never as proof, and never state an improvement or a target as met from
  it.
- Keep it out of acceptance criteria, CI selectors and plan targets. Tag any test that needs it
  as `performance`.

A target written in milliseconds or chunks per second needs a deterministic proxy before work
starts. When the plan has none, say so and propose one instead of benchmarking around it.

## Running a test server

Give a server you start for testing a flat world: set the world's `preset` to `minecraft:flat` in
its `worlds.<name>` config entry ([dimensions](docs/data-driven/dimensions.md#the-config-shape)
lists the keys). Flat chunks cost almost nothing to generate, so a startup, join or gameplay check
does not wait on noise generation, and level ground keeps terrain out of what you are checking.

Use `minecraft:normal` or another noise preset only when the work is about world generation or
depends on it: noise and density functions, biomes, carvers, features, structures, surface rules,
the generation pool and chunk scheduling, or behavior that needs real terrain, such as mob spawning
by biome, `/locate`, or portals between dimensions.

## Tests and verification

- Follow existing Vitest patterns and place unit tests beside the code they cover. Test observable
  behavior and public contracts, and add regression coverage for bugs when the task calls for tests.
- For bug fixes, add a focused unit regression test. When a fix changes client-visible behavior,
  add and run a client-e2e scenario for the same behavior with `pnpm run e2e:client <scenario>`.
  Tag tests that assert wall-clock timing or host-dependent load as `performance`, and exclude them
  from CI test selectors. Keep CI assertions on deterministic, observable behavior, as
  [Measuring performance](#measuring-performance) describes.
  Keep implementation totals (for example, registered functions, commands, components, behaviors,
  or entity types) as non-gating progress reported through `reportProgress` from
  `.test/reportProgress.ts`; it raises a GitHub Actions notice on the reporting test file in CI
  and calls `console.warn` locally. Assert data-derived relationships and runtime outcomes instead of exact inventory counts;
  use exact counts only when the count itself is an externally specified behavior or protocol
  contract.
- When package exports or published behavior change, check the built package from a consumer context.
  Workspace resolution alone does not verify the published package contract.
- After an edit, run `pnpm exec vitest run --since-last-run` to test only what the edit affects.
  It reruns a test file when a file that test loaded on its last run has changed since, and it
  reruns failed files until they pass. The first run in a fresh checkout or worktree is a full run
  that builds the records. It cannot see a file no test loaded, such as a new `.env` or
  `__mocks__` file, or a file whose modification time a checkout set in the past, so run the
  relevant suites in full once before you finish. CI uses `--changed` against the pull request
  base instead, because that baseline is the same on every machine.
- Run the relevant checks for the change. The root scripts include `pnpm run build`,
  `pnpm run typecheck`, `pnpm run test`, and `pnpm run lint`; use package-scoped scripts when they
  cover the affected work.
- After changing repository files, run `pnpm run lint:custom` after your final edit. It runs the
  American filename, packet codec, wire layout, JSDoc, Unicode escape and docs facts checks. `pnpm run lint` includes this
  aggregate.
- `scripts/agent-lint-gate.mts` runs as a Claude Code and Codex hook (`.claude/settings.json`, `.codex/hooks.json`). It runs `pnpm run lint` before `git commit` and `git push` and blocks them on failure. It also runs when you finish with uncommitted changes. Fix the reported problems instead of working around the hook. Codex asks to trust the project hooks on first use; review them with `/hooks`.
- Review the diff and `git status --short` before finishing. Report the checks actually run and any failures or checks that could not be completed.
