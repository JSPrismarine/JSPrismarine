# JSPrismarine

JSPrismarine is a TypeScript monorepo for a dedicated Minecraft Bedrock Edition server. `packages/`
contains the server and reusable packages for Bedrock data, protocol handling, networking, and
utilities.

## Project goals

- Keep the server and its packages reliable and maintainable.
- Treat each published npm package as a product with a public API and compatibility commitments.
- Keep package boundaries clear. Change shared behavior at the package that owns it, then account for its dependents.

## Questions are read-only

When a message asks for an explanation, feasibility assessment, or recommendation, answer without editing files. Treat a direct request to implement a change as authorization to edit.

## Writing

Use American English spelling in prose and documentation. Do not use British spellings.

Apply the [unslop skill](.agents/skills/unslop/SKILL.md) to all prose you write, including docs,
commit messages and comments.

## Before work

- Read [Contributing](CONTRIBUTING.md) for the project's contribution and pull request guidance.
- Project skills live in `.agents/skills/`. Use a skill when its description matches the task:
  read its `SKILL.md` and follow its workflow.
- Run `git status --short` before editing. Preserve staged, unstaged, and untracked work. Do not
  stash, revert, stage, or reformat unrelated changes.
- Use pnpm and the scripts declared in the root or affected package manifests. Inspect a package's
  README and `package.json` before changing it.
- Read relevant pages under `docs/` when working on runtime behavior or documentation. Follow nearby
  code and tests for conventions when no guide covers the area.
- `pnpm dev`, and the server package's `dev` script it calls, runs `pnpm --filter @jsprismarine/bedrock-data run ensure:worldgen` first, which fetches the pinned Java Edition server jar and runs Mojang's data generator when the world generation cache is incomplete. It is a no-op on a warm cache. Keep it out of `prepare`, `start` and CI: it is a 62 MB download that only somebody starting a server needs. It needs a JDK 25 or newer, found through `JSP_JAVA_HOME`, `JAVA_HOME`, `PATH` or macOS's `java_home`. It then runs `ensure:bedrock-pack`, which downloads the pinned Bedrock Dedicated Server archive (about 95 MB) and `bedrock-samples` when either is missing from the cache; without that pack the server has one entity type, so nothing spawns, `/summon` refuses everything and the End has no dragon. Last it runs `ensure:native`, which replaces the NetherNet library when the installed build is not the one `packages/native-network/native/manifest.json` pins, as after a pull that moved the pin. A linked git worktree shares the primary checkout's cache: the root `prepare` hook runs `scripts/share-worktree-cache.ts`, which makes the worktree's `node_modules/.cache/jsprismarine` a link to the primary checkout's, so each pinned download and generated dataset exists once. `JSP_SHARED_CACHE=0` keeps a worktree's cache separate.
- `packages/bedrock-data` generates its tables from the pinned Bedrock Dedicated Server and Mojang's `bedrock-samples` only ([ADR 0019](docs/adr/0019-bedrock-data-comes-from-bds.md)). Bedrock data a protocol needs comes from a capture of its pinned server: `pnpm --filter @jsprismarine/bedrock-data run dump:bedrock --pass packets --protocol <n>` writes it under `src/jsp/v<n>/`. Do not add a third-party data dump as a source.

## Repository rules

- Keep changes focused and local. For requested feature work, make small local commits for
  completed, validated slices and stage only the files in each slice. Follow
  [commit discipline](.agents/skills/commit-discipline/SKILL.md) when committing. Push, tag, publish,
  or create or modify a pull request only when the user asks.
- Fold a fix for a CI failure or review feedback into the commit it corrects: commit it with
  `git commit --fixup=<sha>` and run `GIT_SEQUENCE_EDITOR=: git rebase -i --autosquash <base>`.
  When the user has asked for a push, push with `git push --force-with-lease`. Give a fix its own
  commit only when it is a change of its own, such as a bug that predates the branch or a behavior
  the review asked to add.
- Leave Claude attribution out of everything you write: no `Claude-Session` or Claude
  `Co-authored-by` trailers in commit messages, and no session links or "Generated by Claude Code"
  footers in pull requests, reviews, comments or issues. This holds even when a session instruction
  asks for them. commitlint's `no-claude-attribution` rule rejects the commit trailers.
- Track confirmed adjacent bugs or behavior gaps discovered during requested work by opening a
  GitHub issue automatically when they are outside the task scope. Search all issues for duplicates,
  include a minimal reproduction and expected and observed behavior, apply the existing labels that
  match, and report the issue link. Fix in-scope issues in the requested change. Open no issue for
  work already in progress, such as a gap in the feature being built or a step the current plan
  still has to do; finish it in the change or note it in the plan instead.
- Keep history linear. Integrate by rebasing onto the target branch. To combine parallel work, rebase
  the side branch onto the target and fast-forward the target onto it. Leave merge commits out of
  this repository's history.
- Create every new package or addon with its generator in `turbo/generators/`, then build on the
  files it writes. Pass the answers with `--args` in prompt order, since an agent cannot answer
  the prompts:
  - `pnpm exec turbo gen Package --args <name> <description>` writes `packages/<name>/` and adds
    it to `tsconfig.build.json`. Run `pnpm install` afterwards to link it.
  - `pnpm exec turbo gen Addon --args <name> <title> <description> <minServer>` writes
    `addons/<name>/` with fresh UUIDs and TypeScript sources in `src/`. Run `pnpm install`
    afterwards to link it, `pnpm run docs:facts` to list it in the addon catalog, and
    `node scripts/script-debug-server.mts --update` to give it a VS Code launch configuration.
  - `pnpm exec turbo gen Tool --args <name> <description>` writes `tools/<name>/`, a private
    workspace that runs from source and is never published. Run `pnpm install` afterwards to link it.

  When a new package or addon needs a file or setting the templates lack, change the templates in
  the same change. To start a new kind of workspace that has no generator, add one to
  `turbo/generators/config.ts` first and create the workspace with it.
- When adding a skill under `.agents/skills/<name>/`, add a relative symlink at
  `.claude/skills/<name>` pointing to that directory so Claude Code discovers it. Keep the skill
  files in `.agents/skills/` as the source of truth.
- For package changes that need a release, add a Changeset with `pnpm changeset`. Let Changesets
  manage package versions and release changelogs. Read [the versioning policy](docs/guide/versioning.md)
  before adding or editing a Changeset, and choose a bump for each affected package based on its
  current version and the impact of the change.
- Treat `packages/bedrock-data/src/generated/` as generated output. Its inputs are the captures
  under `src/jsp/`, and `packages/bedrock-data/utils/build.js` generates the JSON files. Change the
  generator or its source inputs when the generated data needs to change. Run
  `pnpm --filter @jsprismarine/bedrock-data run generate` to regenerate it.
- Let pnpm update `pnpm-lock.yaml` when dependencies change. Keep dependency versions consistent
  with the repository's package configuration.
- Follow the configured Biome and Prettier rules. Derive values from their source of truth instead of maintaining duplicate constants or lists.
- Give each helper one home. Before writing a guard, parser, reader or math helper, `git grep` the
  package for its name and its body, and import the match. When a second file needs a private helper,
  move it into a shared module in the owning package (such as `src/isRecord.ts` or `src/json.ts`)
  and import it from both; keep that module out of the package's public barrel. Share across
  packages only through a package that already owns the concept and is already a dependency.
- Let TypeScript infer types. Carry type information through declaration annotations, generics,
  `satisfies`, and narrowing (`instanceof`, `in`, type guards) rather than `as` assertions.
  `as const` is fine. Reserve other `as` casts for boundaries the compiler cannot see, such as
  parsed JSON or untyped third-party APIs, and comment why. In tests, build typed doubles instead
  of reaching for `as any`.
- Every packet with a payload must support both wire directions. Implement serialization and
  deserialization together with `encodePayload`/`decodePayload` for Prismarine, the matching
  payload or top-level encoder and decoder for RakNet, and `serializePayload`/`deserializePayload`
  for `NetworkPacket` classes. RakNet frame codecs use `toBinary`/`fromBinary`. Payload-free
  packets may inherit the base class's empty payload methods. `pnpm run lint:packets` checks
  Prismarine and RakNet packets; `NetworkPacket`'s abstract methods enforce the same contract at
  typecheck time. A fingerprinted legacy entry permits an existing one-way packet only while its
  source file stays unchanged. When editing one, implement both directions before updating the
  baseline with `node scripts/check-packet-codecs.mts --update`. Add round-trip coverage when
  adding a packet or changing its wire layout. A Java Edition packet's `defineJavaPacket` fields
  read and write, and each custom field type must read back what it writes:
  `packages/protocol/src/java/packet/javaPackets.test.ts` fails until every definition has a
  sample payload that writes, reads back equal and writes the same bytes again, since the server
  and `@jsprismarine/client`'s Java client each use the other end of every packet.
- Give a new or changed packet in `packages/protocol` a declarative wire layout
  ([ADR 0003](docs/adr/0003-declarative-wire-layouts.md)). Write its body by hand only for a
  reason the ADR lists, and record it with `node scripts/check-wire-layouts.mts --update --reason
  <reason>`; `pnpm run lint:wire-layouts` fails on an unlisted hand-written body.
- Throw only errors defined in `@jsprismarine/errors`. Add an entry to the throwing package's
  catalog there (`packages/errors/catalog/<package>.ts`), run
  `pnpm --filter @jsprismarine/errors run generate`, and throw `new <Package>Errors.<Key>({ ... })`;
  its [README](packages/errors/README.md) covers templates, bases and fields. The JSDoc on an entry
  is its text in the error reference, so explain the cause and the fix there. Biome's
  `no-raw-errors` plugin rejects `new Error(...)` and `extends Error` in package source. Run
  `pnpm run docs:facts` after changing a catalog.
- Add no barrel files and no `export *` ([ADR 0010](docs/adr/0010-no-barrel-files.md)). Import
  from the module that defines a symbol. `pnpm run lint:barrels` runs Biome's `noBarrelFile` and
  `noReExportAll` rules and fails when a file fires either more often than
  `scripts/barrel-baseline.json` allows, or less often, so the baseline only shrinks. After removing
  a barrel or an `export *`, lower the baseline with `node scripts/check-barrels.mts --update`,
  which never adds an entry.
- Biome cannot run JavaScript rules, so Oxlint runs the testing and structure rules from
  [`@interfere/landmines`](https://github.com/interfere-inc/landmines) that `.oxlintrc.json`
  enables, with Oxlint's own rules off. `pnpm run lint:landmines` fails when a file breaks a rule
  more often, or less often, than `scripts/landmines-baseline.json` records. Follow the rule's
  message rather than raising the baseline, and lower it with
  `node scripts/check-landmines.mts --update` after fixing a finding. `pnpm exec oxlint <path>`
  prints the full messages. The check counts a `package-exports` finding against the package's
  `package.json`, but Oxlint reports it on the package's source files, so pass the package
  directory rather than the manifest.
- Choose the smallest design that meets the request. Trace affected callers, package dependents, and
  failure paths before changing shared behavior.
- Code is the source of truth for every value it owns: versions, requirements, defaults, counts,
  lists of names, settings, tables. Never type such a value into Markdown by hand. Generate it with a
  script that reads the code, the way the docs build fills docs facts, and check the generated value
  into the Markdown so the page still reads right on GitHub.
  - Mark the value as a docs fact: `<!-- fact:name -->value<!-- /fact -->`. `tools/docs/facts.mts`
    defines the facts; when a page needs a value no fact provides, add the fact (or a generator for a
    table or list) there rather than writing the value in.
  - Run `pnpm run docs:facts` to write current values into the Markdown, and commit the result. The
    docs build refills every fact from the code, so the site stays right even when the checked-in
    value lags behind.
  - Dated research, plans and decisions record values as they were when written, and stay unmarked.
- Keep user docs in step with the code. A change that finishes, removes or changes a feature also
  updates every page that describes it: search `docs/`, the READMEs and the addon READMEs for the
  feature's name, its commands and settings, the issue numbers the change closes, and words like
  "in progress", "not yet", "planned", "untested" and "until". Guides and READMEs say what the code
  does now. Status and future work belong in `docs/plans/`, and a gap that stays open gets an
  issue the page links to.
- Whenever a change adds or changes data-driven compatibility behavior or a parity comparison
  surface, extend `packages/parity` with a test under a declared family. Exercise the public
  behavior through the parity suite's real data fixtures, and keep the family represented by a
  tested dashboard row. CI fails when a declared family has no test.
- Code that copies a Java method, field or constant out of the jar names it in its JSDoc with
  `@javaSource Class.member`; a comment that only names a Java member uses `@javaSee`
  ([ADR 0031](docs/adr/0031-copied-java-code-names-its-source.md)). Name an overloaded member with
  its JVM descriptor, as in `@javaSee RandomSource.nextInt(I)I`. With the pinned jar cached,
  `pnpm run lint:java-sources`, and so the commit gate, resolves every tag in the jar and fails on
  one that names no member or several. After adding or removing a
  `@javaSource`, stamp it with `pnpm --filter @jsprismarine/bedrock-data run java:sources --update`.
  After tagging a citation, lower the untagged-citation baseline with
  `node scripts/check-java-sources.mts --update-baseline`.
  When `java.transcriptions` reports a changed member, read its new bytecode
  (`java:sources --list <spelling>`) against the copy, fix the copy if Java's behavior changed,
  and restamp with `--reviewed <spelling>`.
- When you find a Java parity gap, fixed or not, add a parity test that exercises it: a scenario
  under the matching family in `packages/parity` whose row fails while the gap exists. Record a gap
  you leave open in `packages/parity/goldens/behavior-gaps.json` (run the family with
  `PARITY_UPDATE_BEHAVIOR_GAPS=1`) as `deferred` or `defect`, with its issue as the reference, so the
  dashboard shows it and the fix fails the run until the row is removed.

## Measuring performance

Do not use elapsed time, throughput or latency measured on a real clock as evidence that a change
is faster, slower, fixed or regressed. A shared machine, a laptop, a CI runner and a user's host
give different figures for the same code, and the same machine gives different ones a minute
apart. Repeated runs at load average 10 produced differences larger than every effect this project
has tried to measure, and a "p99 improved" claim on that data is noise.

Measure what the code decides, which is the same on every machine:

- Count calls, tasks started, messages sent, allocations, bytes encoded or copied, queue positions
  and retries. A scheduling change is measured by how many background tasks start ahead of a
  player's chunk, not by how long the chunk took.
- Drive the real code with a fake clock, a manual task runner or an injected clock, and assert on
  the order and the counts. `schedulingOrder.test.ts` and `GenerationPoolPriority.test.ts` are
  examples.
- Assert bounds and relationships in unit tests, so a regression fails in CI: "at most the tasks the
  workers already held", "the same count whatever the backlog size". Never assert a duration.
- Use logical cost when work really differs by amount: blocks visited, nodes evaluated, packets
  produced, bytes in the payload.
- For the AOT executables, count the slow paths Bun's `--explain` report lists with
  `node scripts/check-aot-explain.mts`, and lower its baseline with `--update` after a fix.

If a wall-clock figure is the only way to see something, such as whether an operating system
priority is lowered or a control group is throttled, treat it as a diagnostic:

- Record the load average beside it and the command that produced it.
- Report it as indicative, never as proof, and never state an improvement or a target as met from
  it.
- Keep it out of acceptance criteria, CI selectors and plan targets. Tag any test that needs it
  as `performance`.

A target written in milliseconds or chunks per second needs a deterministic proxy before work
starts. When the plan has none, say so and propose one instead of benchmarking around it.

## GitHub workflows

Every job a pull request push starts waits for a runner of its own, and on a busy day that wait is
longer than most of the jobs run. When you add or change a job in `.github/workflows/`, count what
the change does to one pull request push, and keep each count level or lower:

- Jobs started. Add a step to a job that already checked out and installed, and start a new job
  only for another runner OS or for work long enough to be worth splitting across runners.
- Jobs in a row before a check reports. Each `needs:` hop waits for a runner again.
- Runs of the same test. Reuse a result an earlier job or master already produced, such as a blob
  report, an artifact or a cache entry keyed by commit.
- Windows and macOS jobs, which draw on a smaller pool of runners. Run them on pull requests only
  for behavior that differs by platform.

Gate work on what the diff reaches, through path filters and `vitest --changed`. Work that only has
to pass once before a merge, such as every protocol, every platform and the Bedrock Dedicated
Server suites, belongs in the merge group: `ci.yml` runs every tier in full on `merge_group`, and
a push to master reuses the group's results for the same tree. Put the before and after counts in
the pull request description, as [Measuring performance](#measuring-performance) asks.
[The CI speed plan](docs/plans/ci-speed.md) records the current counts and the changes under way.

## Running a test server

Give a server you start for testing a flat world: set the world's `preset` to `minecraft:flat` in
its `worlds.<name>` config entry ([dimensions](docs/data-driven/dimensions.md#the-config-shape)
lists the keys). Flat chunks cost almost nothing to generate, so a startup, join or gameplay check
does not wait on noise generation, and level ground keeps terrain out of what you are checking.

Use `minecraft:normal` or another noise preset only when the work is about world generation or
depends on it: noise and density functions, biomes, carvers, features, structures, surface rules,
the generation pool and chunk scheduling, or behavior that needs real terrain, such as mob spawning
by biome, `/locate`, or portals between dimensions.

## Tests and verification

- Follow existing Vitest patterns and place unit tests beside the code they cover. Test observable
  behavior and public contracts, and add regression coverage for bugs when the task calls for tests.
- For bug fixes, add a focused unit regression test. When a change alters client-visible behavior,
  add a loopback scenario under `packages/client/src/scenarios/`, which joins `@jsprismarine/client`
  to an in-process server and runs with the unit tests. Add a cinnabar scenario under
  `tools/client-e2e/src/scenarios/` only for what needs a real client: rendering, screens, client
  physics or the wire codecs the two ends share ([its README](tools/client-e2e/README.md#where-a-scenario-belongs)).
  The merge group plays every cinnabar scenario, and a pull request's Client E2E job plays the ones
  its changes reach.
  Do not run `pnpm run e2e:client` or its `ensure` build locally, and do not tell a subagent to:
  the cinnabar build is slow and a shared host's load fails real-clock scenarios. Check that the
  job's path filters and scenario selection reach the new scenario, and read the job's result and
  artifacts on the pull request. Run a scenario locally only when the user asks for it.
  Tag tests that assert wall-clock timing or host-dependent load as `performance`, and exclude them
  from CI test selectors. Keep CI assertions on deterministic, observable behavior, as
  [Measuring performance](#measuring-performance) describes.
  Keep implementation totals (for example, registered functions, commands, components, behaviors,
  or entity types) as non-gating progress reported through `reportProgress` from
  `.test/reportProgress.ts`; it raises a GitHub Actions notice on the reporting test file in CI
  and calls `console.warn` locally. Assert data-derived relationships and runtime outcomes instead of exact inventory counts;
  use exact counts only when the count itself is an externally specified behavior or protocol
  contract.
- After changing `packages/leveldb`, run the suite that checks it against the pinned Bedrock
  Dedicated Server in both directions:
  `JSP_BEDROCK_SERVER_TESTS=1 pnpm exec vitest run packages/bedrock-data/utils/bedrock-dump/leveldbCompat.test.ts`.
  It needs the pinned server that `pnpm --filter @jsprismarine/bedrock-data run fetch:sources`
  fetches, and takes several minutes. CI runs it in its own job.
- When package exports or published behavior change, check the built package from a consumer context.
  Workspace resolution alone does not verify the published package contract.
- Run locally only what your change reaches, and no check twice on the same files. CI runs
  everything a diff reaches before a merge, so a local run earns its time only by catching a
  failure sooner than CI would.
- After an edit, run `pnpm exec vitest run --since-last-run` to test only what the edit affects.
  It reruns a test file when a file that test loaded on its last run has changed since, and it
  reruns failed files until they pass. In a fresh checkout or worktree, which has no records yet,
  `scripts/vitest-seed-dependencies.ts` writes them from the static import graph before the first
  run, so that run tests only what changed since the merge base with `origin/master`. A change to
  a file in `forceRerunTriggers` in `vitest.config.ts` still makes that first run a full one, as
  in CI. It cannot see a file no test loaded, such as a new `.env` or `__mocks__` file, or a file
  whose modification time a checkout set in the past, so run the test files that read such a file
  by path. Put those paths before the flag: in `vitest run --since-last-run <path>`, the flag takes
  the path as its value and runs every affected file. Do not run `pnpm run test` or whole suites: CI uses
  `--changed`, against the pull request base or, on master, the last master commit whose tests
  passed, because those baselines are the same on every machine. A nightly run tests every suite.
- Typecheck the packages you changed and their dependents with
  `pnpm exec turbo run typecheck --filter='...[origin/master]'`, not `pnpm run typecheck`, which
  checks every package. Build only when the change touches build configuration, package exports or
  published output.
- `pnpm run lint` and `pnpm run format` run Prettier and Biome on the files that differ from the
  merge base with `master`, including staged, unstaged and untracked files. A change to the
  formatters' configuration checks every file; the root `package.json` and the lockfile are
  checked as changed files, and CI's `lint:all` covers a formatter upgrade.
  `pnpm run lint:all` and `pnpm run format:all` always cover every file; the CI workflow's plan job
  runs `lint:all`. Do not run these, or `pnpm run lint:custom`, yourself: the lint gate below runs
  what your change reaches when you commit and when you finish. To iterate on a failure it
  reports, run that one check's script.
- `scripts/agent-lint-gate.mts` runs as a Claude Code and Codex hook (`.claude/settings.json`, `.codex/hooks.json`). It lints the uncommitted changes before `git commit` and when you finish, and blocks either on failure. Prettier and Biome check only files that differ from `HEAD`, and of the `lint:custom` checks it runs only those whose inputs those files reach (`scripts/lint-gate-checks.mts` maps each check to its inputs; add an entry when you add a check). A clean tree skips the lint, and changes that already passed are not linted again. `lint:custom` also typechecks the root scripts project (`pnpm run typecheck:scripts`, `tsconfig.scripts.json`), which no package typecheck covers: a script that imports a package's source pulls that source into its NodeNext rules, and the gate catches the break before CI's typecheck does. `git push` is not gated, since each commit passed the commit gate. Fix the reported problems instead of working around the hook. Codex asks to trust the project hooks on first use; review them with `/hooks`.
- Review the diff and `git status --short` before finishing. Report the checks actually run and any failures or checks that could not be completed.
