### Minor Changes

- [#2628](https://github.com/JSPrismarine/JSPrismarine/pull/2628) [`01cfa14`](https://github.com/JSPrismarine/JSPrismarine/commit/01cfa14ed39c4875e71524eb7e6dda18a6f8deb0) Thanks [@filiphsps](https://github.com/filiphsps)! - Record what the chunk generator produces today, so the rewrite can prove it changed nothing.
  
  `goldens/worldgen-corpus.json` is a recording of this server's own chunk output: 22 chunks at three
  seeds, four of them kept block by block and the rest reduced to seven digests each, one of those per
  sixteen block section so a divergence is located in y. Every chunk carries a census of how many
  blocks of each state it holds, and a dense 48 by 48 chunk scan per seed records 20 structure starts
  across 9 structure types with their origins, boxes and piece counts. The file carries its own
  provenance: the commit, the date, the pinned Java data version, and any uncommitted file under the
  packages that decide what a chunk holds. `loadGenerationCorpus` refuses a golden captured against a
  different Java version rather than comparing against a stale recording.
  
  Four rows read it. `worldgen.corpus` regenerates every chunk and diffs it, naming the chunk, the
  sixteen block band of y and, for the chunks kept whole, the first differing block by coordinate with
  both state names. `worldgen.features` stops reporting `not measured` and compares the block census
  of the decorated chunks. `worldgen.structures` compares the placements. `worldgen.determinism` asks
  whether a chunk is a function of its seed and coordinates alone.
  
  It is not, and that is the finding. Generating a chunk after its four neighbors gives different
  blocks from generating it first, and a chunk already handed back changes when a neighbor is
  generated afterwards, because the generator keeps neighbor terrain and cross-border feature output
  in a per-seed cache and replays it. Both are allow-listed as defects: the chunk status ladder cannot
  preserve them across worker threads. It is also why each corpus chunk is generated by a generator
  that has produced nothing else, which is the one protocol a rewrite can reproduce.
  
  These rows measure change rather than parity with Java. `worldgen.terrain` is still the row that
  compares against Java Edition, and a comparison against Mojang's own feature distribution still
  waits on the Bedrock reference world. `pnpm --filter @jsprismarine/parity run capture:corpus`
  rewrites the golden when a generation change is deliberate.

- [#2628](https://github.com/JSPrismarine/JSPrismarine/pull/2628) [`3cf1140`](https://github.com/JSPrismarine/JSPrismarine/commit/3cf114028ad0ce779ca157ed6352b5d431e91f00) Thanks [@filiphsps](https://github.com/filiphsps)! - Measure the phase exit criteria the plan names, and report honestly when nothing stands behind a row.
  
  Seventeen new dashboard rows join the five that existed. `mapping.blocks`, `mapping.items`, `mapping.entities` and `mapping.registries` run Chunker's totality property per domain against independent references and carry the mapping package's reviewed losses as allow-list rows, derived from its own loss list. `blocks.properties` compares all 15952 Bedrock block states against the Java 26.3 jar dump, ten property fields each. `items.components` checks Java's 1658 items and 122 component types against the Bedrock item capture. `recipes.registry` and `loot.tables` parse Java's 2042 recipe files and 1447 loot tables and compile the recipes through the mapping. `entities.stats` compares mob health against Java's attribute dump and `entities.addactor` checks a packet row per advertised actor type. `worldgen.biomes` replays Java's own biome lookups and `worldgen.terrain` generates the nine Java columns the oracle dumped. `commands.tree` checks the published command tree against Mojang's Bedrock command metadata. `conformance.classification` and `conformance.exclusions` are the two honesty tests plan section 8 requires.
  
  A row is now green only when its comparison had reference data to stand on. `src/references.ts` declares where each body of reference data comes from, and a family whose sources this checkout lacks registers one skipped test naming what is missing, which the dashboard renders as `not measured`. `worldgen.features` reports that permanently: no reference world and no sampled ore and feature distribution exist. Allow-list entries gain a `kind`, so a defect the suite found cannot pass for an accepted gap, and the dashboard counts the two in separate columns.

- [#2628](https://github.com/JSPrismarine/JSPrismarine/pull/2628) [`b2d1ddc`](https://github.com/JSPrismarine/JSPrismarine/commit/b2d1ddc0adeb49184594dc2f7a1e8826924003c5) Thanks [@filiphsps](https://github.com/filiphsps)! - Consume the entity stat decision, measure the loot distribution, and wire the feature row to a source that will exist.
  
  `entities.stats` compared health alone and carried the armor stand and the wither as defects. It now spawns each mob the way the server spawns one, with the Java stat table in the environment, and compares all nine stats both editions publish: 438 rows over the 93 types the Java dump holds, reached through `javaEntityTypeToBedrock`. Each surviving disagreement goes through `statRuling` from `@jsprismarine/entities`, so the dashboard row carries the decision's own verdict and reason rather than a second copy of it. 103 are stats Bedrock decides and 15 are the reviewed exceptions, which become accepted gaps; a `java` ruling becomes a defect. The two old defects close, and two new ones appear: `javaAttributeBases` looks an entity up in the Java dump by the identifier it spawned under, so the evoker and the villager, which keep Bedrock's legacy identifiers, never find their Java row and still run the pack's follow range.
  
  `loot.distribution` is a new row, the half of phase 2's loot exit that did not exist. It rolls every table whose draws its own file determines, counts the stacks by item identifier and runs Pearson's chi-squared test against the probabilities the declared weights and roll counts imply: 54 tables with a real choice to make, 175 counting the ones that draw a single item a declared number of times, over 400000 draws from a fixed world seed. The row measures the roller against Mojang's numbers, not against rolls sampled from a running Java server, and `declaredDistribution` refuses any table whose distribution its weights alone do not fix. Both limits are stated on the row and in the README. `chiSquared.ts` carries the test and its tail function, checked against published critical values.
  
  `worldgen.features` required a separately captured feature distribution on top of the reference world, and nothing was ever going to produce one: the distribution is the reference world's own `blockCounts`. The row would have stayed not-measured after the golden landed, so it now stands on that single source, with `loadReferenceWorld` checking the golden's format version and a type-only import of the capture job's own `ReferenceWorld` failing the build if the file the job writes stops being the file the rows read. The row still reports not measured, because no run has committed a golden.
  
  `blocks.properties` goes green: the property table generator now keeps the retracted piston's light dampening, so both defect entries report stale and leave the list.

### Patch Changes

- [#2628](https://github.com/JSPrismarine/JSPrismarine/pull/2628) [`2955838`](https://github.com/JSPrismarine/JSPrismarine/commit/2955838a6992751dfccd8c523196744fa7abe47e) Thanks [@filiphsps](https://github.com/filiphsps)! - Close the entity stat defects, measure two more mapped registries, and add a row for the registries nothing publishes a pairing for.
  
  `entities.stats` carried the evoker and the villager as defects, because `javaAttributeBases` looked an entity up in the Java dump by the identifier it spawned under and the five legacy-named types found no row. `@jsprismarine/entities` now resolves that through `javaEntityTypeToBedrock`, so both follow ranges come from Java and the two entries leave the allow list. 118 disagreements survive, 103 on a stat Bedrock decides and 15 reviewed exceptions, with nothing left for the decision to give to Java. The exception count comes off `JAVA_STAT_EXCEPTIONS` and the Java-ruling check prints the entity, the stat and both numbers, so a Mojang retune that opens a new one says what moved.
  
  `mapping.registries` walked four registries against a corpus guard that expected two. It now counts per registry, 67 biomes, 43 enchantments, 40 mob effects and 46 potions, and fails on the missing key when a fifth registry joins `MAPPED_REGISTRIES` rather than letting it ride along unmeasured.
  
  `mapping.untranslated` is a new row over the three registries `UNTRANSLATED_REGISTRIES` declares. A banner pattern reaches a client as a two-letter code in block entity NBT, a goat horn as an item data value and a painting as a resource pack texture name, and no pinned source publishes the pairing, so the mapping names no entry of them. Each registry is one accepted gap whose reason, reference and carrier come from the mapping package itself. The row holds the two properties that keep the gap from widening: every census identifier of these registries resolves as a loss and none as a Bedrock name, and the census holds exactly the pinned 43, 8 and 51 entries, so a Java version that adds a banner pattern fails the row.
  
  The dashboard script runs under plain node, which resolves neither a bare sibling import nor a bare JSON import, and the allow list started reaching into `@jsprismarine/mapping` through the entity stat decision. It now registers a resolve hook for both and loads the allow list after, rather than dying before it prints a table.
