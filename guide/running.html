Running JSPrismarine ​

There are two ways to run JSPrismarine:

  • To host or play on a server, download the prebuilt server. It is one file with everything inside, so you need no Node.js, pnpm, Java or checkout of this repository. See Run the prebuilt server.
  • To write add-ons or plugins, or to work on JSPrismarine itself, run it from source with pnpm run dev. It rebuilds and restarts the server whenever you change a file. See Run from source, and Extending JSPrismarine for what an add-on or a plugin can do.

The console and configuration work the same either way.

Run the prebuilt server ​

Each release on GitHub ships the server as a standalone executable. Download it from the JSPrismarine releases: releases tagged jsprismarine@<version> carry the executables. The ones marked Pre-release are nightly builds of master.

PlatformFile
Linux, x64prismarine-linux-x64
Linux, ARM64prismarine-linux-arm64
Linux with musl (Alpine), x64 or ARM64prismarine-linux-x64-musl, prismarine-linux-arm64-musl
macOS, Apple silicon or Intelprismarine-darwin-arm64, prismarine-darwin-x64, or the app in JSPrismarine-<arch>.app.zip
Windows, x64 or ARM64prismarine-windows-x64.exe, prismarine-windows-arm64.exe

Nightly pre-releases are built for fewer platforms: Linux x64, macOS on Apple silicon and Windows x64. The .map files next to each executable are source maps for reading stack traces; you don't need them to run the server.

Put the file in the folder you want the server to live in, then run it from there:

bash
# Linux and macOS: mark the download as executable once
chmod +x prismarine-linux-x64
./prismarine-linux-x64
powershell
# Windows
.\prismarine-windows-x64.exe

The macOS builds are signed ad hoc, not notarized by Apple, so macOS refuses to open one a browser downloaded. Clear the download flag once with xattr -d com.apple.quarantine prismarine-darwin-arm64 (or the app's name), or Control-click the app and choose Open. On Windows, SmartScreen may warn about an unrecognized app; choose More info, then Run anyway.

The first start in a folder needs a network connection and takes a minute. The server unpacks the data it carries (Mojang's Java Edition world generation data and this project's packs), then downloads the vanilla behavior pack from Mojang's Bedrock Dedicated Server (about 95 MB), checking its digest. Mojang's license does not allow shipping that pack inside the executable. Both land in node_modules/.cache/jsprismarine/ in that folder, so later starts need no network. On a machine that cannot reach Mojang's servers, set JSP_VANILLA_BEHAVIOR_PACK to a copy of a Bedrock Dedicated Server behavior_packs folder.

The server then creates config.json, its player lists and worlds/ in the same folder and starts listening on UDP port 19132. Players add it in Minecraft under Servers → Add Server with your machine's address. In a terminal, it opens the terminal UI; under a service manager, in Docker or with --no-tui, it uses the plain line console.

To update, replace the executable with the newer one and start it again. Your config.json, worlds and player lists stay as they are, and the server unpacks the new version's data on its first start.

Run from source ​

Run from source when you are building add-ons or plugins, or changing JSPrismarine: pnpm run dev rebuilds the packages you edit and restarts the server with your changes. The steps below set up a checkout.

1. Prerequisites ​

  • 1.1 Node.js 26.4.0 or newer and pnpm 12 or newer. The terminal UI loads node:ffi by default on Node 26.9 or newer. Node versions 26.4 through 26.8 require --experimental-ffi. If Node cannot load node:ffi, the server uses the plain line console (see Console).

pnpm is the only supported package manager. Installs with npm or yarn fail with a message pointing back to pnpm, and repository tooling runs one-off tools through pnpm dlx (or pnpx) rather than npx.

  • 1.2 A JDK 25 or newer, to run the default overworld. See World generation data below for what it is for and how to skip it.

The Bedrock resources are a pinned download, verified by hash and cached under node_modules/.cache/jsprismarine/. You don't need to fetch it yourself: pnpm install, pnpm run dev and the bedrock-data build all fetch it when it is missing. Offline from a cold cache, point JSP_CLOUDBURST_DATA_PATH at a local CloudburstMC/Data checkout.

1.3 World generation data ​

The default world preset, minecraft:normal, builds terrain from Mojang's published Java Edition world generation data. That data is not shipped with this server; it comes from a pinned Java Edition server jar that pnpm run dev fetches and runs Mojang's data generator against, caching the result under node_modules/.cache/jsprismarine/.

This happens automatically the first time you run pnpm run dev, and takes a 62 MB download and a couple of minutes. Afterwards the step compares a few file names and exits, so later runs are instant and need no network.

pnpm install does not do this, so installing stays quick for anyone who only builds or tests the repository. pnpm run start does not do it either; a checkout run that way arranges the cache once, or points JSP_VANILLA_DATAPACK and JSP_JAVA_REPORTS at a copy produced elsewhere. The prebuilt server needs none of this: it carries the data inside.

Running the data generator needs a JDK 25 or newer. JSPrismarine looks at JSP_JAVA_HOME, JAVA_HOME, the java on your PATH and, on macOS, /usr/libexec/java_home; set JSP_JAVA_HOME if you have several and want to choose. Without a JDK, pnpm run dev stops with a message instead of starting a broken world.

To run with no Java at all, set preset to minecraft:flat for your world in jsp/config.json (see Worlds). A flat world needs none of this data. It is also not Minecraft terrain, so this is a deliberate choice rather than a fallback the server makes for you.

To arrange the cache by hand, or to refresh it:

bash
$ pnpm --filter @jsprismarine/bedrock-data run ensure:worldgen

pnpm dev also runs ensure:bedrock-pack, which downloads Mojang's Bedrock Dedicated Server archive once so the server can read the vanilla behavior pack. Without it the server logs a warning and runs with no mobs, no /summon and no dragon. Run it by hand with pnpm --filter @jsprismarine/bedrock-data run ensure:bedrock-pack.

2. Install dependencies ​

bash
    # Install npm dependencies
$ pnpm install

3. Running ​

bash
    # Runs the server, rebuilds and restarts it on source changes, and opens the terminal UI
$ pnpm run dev

pnpm run dev is the way to run a checkout, for add-on and plugin work as much as for work on the server. It is prismarine --watch: it builds the server and its workspace packages once, then runs the compiled entry next to vite build --watch for each package, so there is no TypeScript loader in the server process or its workers. Editing a source file rebuilds that package, and the server restarts when its dist output or content pack data changes. The first restart a few seconds after start-up is the watch builds writing their initial output. The watch builds log to node_modules/.cache/jsprismarine-dev-build.log so they stay out of the terminal UI. It opens the terminal UI described in the Console section when it can, and falls back to the plain line console otherwise.

Building the server yourself ​

You rarely need these: to host a server, download the prebuilt one. They exist for checking a production build, for platforms the releases do not cover, and for working on the packaging itself.

pnpm run start builds the server and its workspace dependencies, then runs the compiled entry once, without the watcher.

The released executables are compiled with Bun by .github/scripts/build-aot.mjs, which the release and nightly workflows run for each platform. That script needs the build metadata the workflows set, so the workflows are the supported way to produce release builds.

pnpm run package builds a different executable locally: dist/prismarine, a Node single executable application, with scripts/package-sea.mts. It needs Node 25.5 or newer, and a checkout whose world generation cache is warm: run pnpm --filter @jsprismarine/bedrock-data run ensure:worldgen and pnpm --filter @jsprismarine/bedrock-data run extract:structures first, because the executable carries that data inside it: the Java vanilla datapack, the biome parameter reports, the structure templates, and this project's overlay packs. The build enables Node's SEA code cache for the main entry. To build a comparison without it, save the first executable before running pnpm run package -- --no-code-cache; the remaining packaging inputs stay the same. On first run it provisions its data the way the prebuilt server does. It uses the plain line console, and embeds the default chunk worker and generation pipelines as SEA assets, so terrain workers can run without importing modules from disk. If an asset is missing or a custom pipeline is not embedded, the server logs the reason and generates terrain on the server thread instead.

pnpm run package:scriptc is an experimental ahead-of-time build. It embeds no data and does not provision any on first run yet, so its output needs a directory whose node_modules/.cache/jsprismarine/ was arranged by a checkout, or the JSP_* override variables above.

Live debugging and profiling ​

Add --devtools to a development run to open Node's inspector and enable JSPrismarine timing traces:

bash
pnpm run dev -- --devtools

The server prints an HTTPS DevTools URL. Open it in Chrome, Edge, or an app webview that cannot open Chrome's local devtools:// URLs to set breakpoints, inspect live JavaScript objects, record CPU profiles, and take heap snapshots. The inspector listens on 127.0.0.1; it allows code execution in the server process, so keep it on the local machine. When DevTools is enabled, the Console also shows JSPrismarine logger records alongside JavaScript console calls.

For startup debugging, use pnpm run dev -- --devtools-wait. This enables DevTools and waits before reading server configuration or constructing the server. Attach a debugger, set your breakpoints, and resume startup. Static module imports have already run at this point. The jsprismarine handle becomes available after the server is constructed. In watch mode, the host keeps the printed frontend and inspector URLs stable and reconnects the open frontend to each new server process. With --devtools-wait, each replacement process waits for the same frontend to resume it.

The printed JSPrismarine inspector: WebSocket URL also accepts external Chrome DevTools Protocol clients. Node's V8 debugger supports line and conditional breakpoints, function-call breakpoints, stepping, exception pauses, scope inspection, and evaluation on paused call frames. Debugger.setInstrumentationBreakpoint supports beforeScriptExecution and beforeScriptWithSourceMapExecution. These pause before script execution; browser DOM, XHR, and event-listener breakpoints do not apply to this Node server. A debugger client must enable Debugger, install startup breakpoints, and send Runtime.runIfWaitingForDebugger to release --devtools-wait. Use an external client so pausing the server does not also pause its debugger. Source-map-aware clients can map TypeScript locations to the JavaScript executed by V8.

The DevTools Console exposes a jsprismarine handle to live server objects:

javascript
jsprismarine.server.getTick()
jsprismarine.levels()
jsprismarine.worlds()
jsprismarine.entities('world')
jsprismarine.entityRuntime('minecraft:overworld').runtime

This uses the server's world and entity registries, so data-driven entities and their runtime state remain inspectable through the same model the server runs. On graceful shutdown, the server writes a Chrome trace to jsp/profiles/ (or the configured JSP_DIR/profiles/). Import the .trace.json file in DevTools' Performance panel to inspect tick phases, world update phases, and event-loop delay. A forced process exit cannot save the trace.

The macOS app opens Terminal so the server can use its interactive console. Its config, world, and log files are stored in ~/JSPrismarine.

4. Console ​

The prismarine entry point picks one of two console modes at startup.

The terminal UI (TUI) is used when stdin and stdout are a terminal, TERM is not dumb, neither CI nor JSP_NO_TUI is set, --no-tui was not passed, and Node can load node:ffi (by default on 26.9 or newer, or with --experimental-ffi on 26.4 through 26.8). The UI draws the log, a status bar with TPS, player count, memory, and uptime, and an input line with history and command completion. In this mode the process you started is a host: it owns the terminal and runs the server as a child process, so a crash or a --watch restart of the server never leaves your terminal in a broken state. A Node with node:ffi is required because the renderer is loaded through node:ffi, which arrived in that release.

The plain line console is used elsewhere, including in Docker, under systemd, in hosting panels that feed stdin, over pipes, and in CI. In that mode, the server runs in-process and behaves like a classic console program. Each line you write to stdin runs as a command, and each log record is one plain line on stdout, so docker logs and panel log viewers show exactly what the log file does. If Node cannot load node:ffi, the server prints one line naming the reason before startup.

You can force plain mode with the --no-tui flag or by setting JSP_NO_TUI=1 in the environment. The environment variable is the right choice for container images and service units, since it applies even when someone runs the image with -it. The repository Dockerfile sets it.

The remaining flags:

  • --watch restarts the server when a workspace source file or a loaded pack's data changes, and regenerates bedrock-data first when its resources or generator changed. pnpm run dev passes it for you. The watcher's own state (watching, change detected, generating, restarting, exited) shows in the TUI status bar rather than in the log.
  • --headless runs the server with no console at all: stdin is left alone and nothing is read from it. Use it when a wrapper owns the terminal and only the log file matters.
  • --no-tui forces the plain line console even on an interactive terminal.

Keys in the terminal UI ​

Press ? on an empty input line to open the help overlay, which lists every binding. The ones you'll need first:

KeyWhat it does
EnterRun the typed command
Up / DownMove through command history
TabComplete the command name
Ctrl+CClear the input line. Pressing it again on an empty line within two seconds stops the server; a press while the server is stopping kills it.
PgUp / PgDnScroll the log. Scrolling up pauses following so new lines don't move what you're reading.
EndJump to the newest line and resume following
Ctrl+LClear the visible log (the buffer is kept)
?Help overlay, on an empty line
EscClose an overlay or cancel a search

5. Configuration ​

New servers keep their settings in config.json in the working directory (jsp/ during development). The server creates it on first start, with every setting preceded by a comment explaining it and a $schema URL for the matching package version.

The file is yours to edit. The server only ever changes the key it is writing: your comments, blank lines and the order of the keys stay as they are. When a new version adds a setting, the server adds that key and its comment to the end of your file and leaves the rest alone, so there is no need to regenerate the file after an upgrade.

Older servers kept their settings in config.yml or config.yaml. The server does not read those files and ignores them if they exist. Move any settings you still need into config.json (where // comments are allowed).

packet-full-flush-fragments is an opt-in compression prototype. It stays off by default until the server has been checked with retail Bedrock clients on Windows and Android.

Worlds ​

Each entry under worlds is one world: its seed, the provider that stores it on disk and the preset that says which dimensions it has and how each one generates. The server loads every entry; level-name picks the one players join. The preset is a Java worldgen/world_preset id. minecraft:normal, the default, is the Overworld, the Nether and the End with vanilla terrain; minecraft:flat is a superflat Overworld that needs no Java data; minecraft:large_biomes and minecraft:amplified are the other two vanilla presets. dimensions.md describes every key and what is behind them.

json
{
    "worlds": {
        "world": { "preset": "minecraft:normal", "provider": "LevelDB", "seed": "8475011743740320021" }
    }
}

dimensions changes one dimension at a time without giving up the rest of the preset. Each key is a Java dimension id, and its entry may set the dimension's type, its generator or when it loads. A key you leave out comes from the preset, and an id the preset doesn't have adds a dimension. This world keeps the Nether and the End from minecraft:normal but makes its Overworld flat, with the same generator object a Java datapack writes in a dimension file:

json
{
    "worlds": {
        "world": {
            "seed": "8475011743740320021",
            "provider": "LevelDB",
            "preset": "minecraft:normal",
            "dimensions": {
                "minecraft:overworld": {
                    "generator": {
                        "type": "minecraft:flat",
                        "settings": {
                            "biome": "minecraft:plains",
                            "layers": [
                                { "block": "minecraft:bedrock", "height": 1 },
                                { "block": "minecraft:grass_block", "height": 3 }
                            ]
                        }
                    }
                },
                "minecraft:the_end": { "load": "eager" }
            }
        }
    }
}

load is lazy by default, which builds a dimension the first time something enters it, so a server nobody takes to the End never pays for it. A lazy dimension skips the spawn search and the start-region generation an eager one does; the first traveler loads the chunks they arrive in. eager builds it at startup instead, which moves that cost to the start and uses more memory while the server runs. The Overworld of the world players join is always built at startup. A player who logged out in a lazy dimension comes back there on the next login, and the server builds it then if nobody has visited since the boot.

A generator may be any of four kinds. minecraft:noise is vanilla terrain and needs the Java data from section 1.3; minecraft:flat, jsprismarine:void (empty chunks) and minecraft:debug (every block state on a grid) need none of it. Without that data, only minecraft:normal and minecraft:flat exist as presets, each with the Overworld alone. A type other than the vanilla three has to come from a datapack in the server's pack stack, such as one listed under content-datapacks, and adding an id the preset lacks needs both type and generator. Each type backs one dimension per world: two dimensions naming the same type stop the server with an error.

A world remembers the dimensions it was generated with. Changing preset or a generator for an existing world does nothing to its terrain: the server keeps the saved stems and logs one line per dimension where the config disagrees. Start a new world folder for new terrain.

Older configs spelled the same thing as generator: "Overworld" or generator: "Flat", with flat layers under layers as { "block", "size" }. The config schema no longer lists either key, so an editor flags them, but the server still reads both: Overworld is preset: "minecraft:normal", Flat is preset: "minecraft:flat", and layers becomes a minecraft:flat generator for minecraft:overworld with each layer's size written as height. It logs once per world that the keys are deprecated and writes the new spelling back to the file, so you only see the message and the editor's marks until the next start. Any other generator name stops the server with an error, as it did before.

World seeds ​

Write a world's seed as a string, as the examples above do.

A Minecraft seed is a 64-bit integer and a JSON number is a double, which is exact only below 2^53. Written as a number, 8475011743740320021 is read back as 8475011743740319744 and generates a different world. A number still works and is exact for seeds below 2^53.

The string is read the way Java reads the text in its world creation box: a value that parses as a 64-bit integer is that integer, and anything else is its String.hashCode, so "glacier" is seed 108181935 here and in Java. An absent or empty seed is 0.

The same applies to the JSON files beside it (banned-players.json, ops.json, and permissions.json) and player data: the server changes the entry it means to and leaves your comments in place. These files may hold // and /* */ comments and trailing commas. On startup, the server imports an older world's level.json once into its provider and removes the file after the migration succeeds.

The published @jsprismarine/prismarine package includes Draft 7 JSON Schemas under schemas/. Each reference uses the exact package version that wrote the file, served from UNPKG, so a standalone server or binary does not need a separate npm install to make the schema available. Object files such as config.json, permissions.json, and fallback player data contain a $schema property. The root of ops.json and banned-players.json is an array, so those files instead start with a JSPrismarine schema comment holding the versioned URL. To validate those arrays in VS Code, map the file names in settings.json and replace the URL placeholders with each file's exact URL:

json
{
    "json.schemas": [
        { "fileMatch": ["ops.json"], "url": "<copy the JSPrismarine schema URL from ops.json>" },
        {
            "fileMatch": ["banned-players.json"],
            "url": "<copy the JSPrismarine schema URL from banned-players.json>"
        }
    ]
}

The schemas allow comments and trailing commas in editors that support JSONC.

A file that does not parse stops the server with an error naming the file rather than being replaced by the defaults, so a typo costs a restart, not the config.

6. How the development server works ​

pnpm run dev runs the server from TypeScript source with --watch. No build step is needed: every @jsprismarine/* package resolves straight to its src/, so an edit in any package takes effect on the next restart.

The host process watches workspace package sources and data files under every directory in the resolved content stack: the vanilla Bedrock pack, packages/blocks/vanilla_overlay/, packages/entities/vanilla_overlay/, the Java vanilla datapack, and packs configured through content-world-packs or content-datapacks. Explicit JSP_VANILLA_BEHAVIOR_PACK and JSP_VANILLA_DATAPACK paths are included in that stack. Pack JSON, pack.mcmeta, .mcfunction, and .brarchive changes share one debounce, so a batch of edits causes one graceful server restart and rebuilds the registries from disk. Content registries are built at startup and use positional IDs, so changing them in place would leave running clients and entities with stale data. Because the console lives in the host and the server is a child process, the console keeps working across restarts. If the server crashes while you are mid-edit, the host stays up and starts the server again on your next change. Changing the bedrock-data resources or its generator regenerates the data before the restart.

Dropping packets to find a bad one ​

When a client leaves during the join without a Disconnect or PacketViolationWarning, the server log alone does not say which packet it choked on. Set JSP_DEBUG_DROP_PACKETS to a comma-separated list of packet class names and the server never sends those, logging a warning for each one it withholds:

bash
$ JSP_DEBUG_DROP_PACKETS=LevelChunkPacket,CraftingDataPacket pnpm run dev

Drop one type at a time and watch whether the client's behavior changes. A batch of several packets is dropped whole when any packet in it is named.

Once a packet type is implicated, JSP_DEBUG_DUMP_PACKETS takes the same kind of list and writes each named packet's encoded bytes, header included, to a file of its own under JSP_DEBUG_DUMP_DIR (default: a jsprismarine-packets directory in the system temp directory). That is the exact byte sequence the client was given, ready to decode against the protocol documentation. A packet can be dumped and dropped at the same time.

The variables are read when a connection is made, so they can also go in packages/server/.env.development.local, which the server loads at startup. Remove them when done; a server with packets missing is not one players can use.
