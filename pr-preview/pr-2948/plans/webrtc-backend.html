NetherNet on libdatachannel, with BDS's port settings ​

Started 2026-11-11. Work happens on dev/webrtc-backend. This plan is a working document: tick slices off, and add or reshape them as the work teaches us things.

Goal ​

Make the server's NetherNet ports behave as Bedrock Dedicated Server (BDS) 1.26.70 does, and own the code that gets us there. Four decisions carry it:

  • We implement the NetherNet protocol in @jsprismarine/nethernet and stop depending on the npm nethernet package (ADR 0007).
  • The server and our client run on our own build of libdatachannel, in a new native networking package bound through FFI, and werift leaves the workspace (ADR 0006).
  • RakNet and NetherNet can share one UDP port number, sorted in native code so WebRTC never enters JavaScript (ADR 0008).
  • An enabled transport that cannot start stops the server's start.

What done looks like:

  • server-udp-ports and the new server-public-ip accept what BDS 1.26.70.24 accepts, refuse what it refuses, and open the same ports.
  • port is renamed server-port, as BDS names it.
  • A fresh config writes server-port and leaves server-portv6 and server-udp-ports out. With only server-port, RakNet on IPv4 and IPv6, NetherNet's signaling and NetherNet's UDP all use it. Setting server-udp-ports moves NetherNet's UDP there, and setting server-portv6 moves RakNet's IPv6 listener there.
  • A RakNet port may also be one of the ports in a NetherNet range.
  • How a range picks a port for a player is one strategy behind an interface. The first strategy is the port with the fewest players.
  • A Bedrock client joins, plays and is kicked with the kick's reason on screen.
  • The workspace no longer installs werift, nethernet or protodef, and packages/prismarine reads no WebRTC stack's internals. The WebRTC driver sits behind an interface that a later driver can implement.
  • jsp-client --latency and --loss work over NetherNet on libdatachannel.
  • Where libdatachannel cannot load, the server refuses to start and names enable-nethernet as the way to run on RakNet alone.

Out of scope:

  • BDS 1.26.70 removes transport and server-portv6, because it runs NetherNet only. We keep enable-raknet, enable-nethernet and server-portv6.
  • The scriptc binding is planned here and built later, once the server compiles under scriptc (slice 15).
  • LAN discovery on UDP 7551 and the query port keep warning when their port is taken. They are not transports.
  • RakNet in native code. ADR 0008 leaves room for it as a second module of the native networking library, behind the server's transport interface.

What we know ​

  • Werift binds a UDP socket for each peer connection, and its configuration rejects an icePortRange whose two ends are equal. parseUdpPorts refuses a single port for that reason.
  • dev/werift-mux (commit a3abb49e14) makes a single port work on werift anyway. It replaces werift's UdpTransport.init at runtime for that port, shares one socket per address family, and routes datagrams to peers by ICE username fragment, STUN transaction ID and sender address. It reads werift's private fields to find each peer's username fragment. It passed two integration tests and a smoke run of three concurrent peers on a real server. ADR 0006 does not take it. It is the way back to one port if a Bedrock client refuses libdatachannel.
  • A pull request to werift could add a supported shared-socket option, which would retire the runtime patch without changing backends.
  • node-datachannel binds libdatachannel, a native WebRTC library. Version 0.33.6's configuration has enableIceUdpMux, which shares one UDP port across peer connections, and portRangeBegin and portRangeEnd. Its W3C wrapper, node-datachannel/polyfill, passes the whole configuration through to the native peer connection. It ships prebuilt binaries and requires Node.js 18.20 or newer. We used it for the spike only: its prebuilt addon cannot take the libjuice patch that ADR 0008 needs, so ADR 0006 builds libdatachannel ourselves.
  • @roamhq/wrtc, nethernet's optional native backend, exposes no port settings, so it does not solve the trigger.
  • nethernet 1.1.2 is about 1,500 lines of JavaScript. packages/nethernet already owns HTTP signaling, the identity, the LAN advertisement format and join by address. We import three things from nethernet: its Server, its Client, and SignalStructure with SignalType.
  • nethernet builds its LAN packet codec at run time with protodef's compiler, which generates code with eval (protodef/src/compiler.js). An ahead-of-time build cannot do that in compiled code.

What ties us to werift ​

Everything below reaches past the W3C API. Each goes away with werift and nethernet, or moves behind the driver interface:

  • nethernet 1.1.2 picks its stack by name (werift or wrtc), with no way to pass one in. Its werift subclass also has werift-only behavior: setRemoteDescription checks this.sctp, setLocalDescription clears werift's default STUN server, and close stops SCTP before DTLS.
  • adaptPeerConnections (packages/nethernet/src/peerConnections.ts) works around that subclass on werift 0.27.
  • constrainIcePorts sets werift's icePortRange.
  • tracePeerConnection subscribes to werift's own events and reads iceTransports.
  • selectedCandidateAddress (packages/prismarine/src/network/transport/NetherNetTransport.ts) reads the selected candidate pair from werift's ICE transport, to learn the client's address.
  • hasUndeliveredData in the same file reads werift's SCTP association (outboundQueue, flightSize) so a kick's DisconnectPacket is delivered before the connection closes.
  • LinkConditions (packages/client/src/net/LinkConditions.ts) simulates latency and loss by patching dgram.Socket.prototype.send for the whole process. libdatachannel sends from its own sockets, so the patch does not reach it. Slice 7 puts Node.js sockets back in the client's path.

server-udp-ports as BDS 1.26.70 has it ​

From the research note, which read the comments of three BDS versions and ran the 1.26.70.24 binary against about 35 values. The rules we match:

  • Two modes. A single port that every player shares, or a range. In a range, players are spread over the ports, and a port is reused once every port has a player. BDS binds one socket for each interface address and port, and never one per player.
  • Default. Unset or empty, the UDP port is server-port.
  • Mappings. public:local for a port or a range, with both sides the same length.
  • server-public-ip. A new key for the address to advertise: a raw IPv4, or a raw or bracketed IPv6. A hostname or a port in it is an error.
  • IP prefixes are deprecated. IP:public:local still works and logs a warning that names server-public-ip. Two different prefixes, or one that differs from server-public-ip, is an error. A prefix needs both ports.
  • Commas and repeated lines still work. The local ports of every entry must form one continuous range. Adjacent and overlapping ranges merge, duplicates and empty entries are fine, and a gap is an error. Our config is JSON, so the repeated-line form becomes the comma form.
  • Errors stop the start. Each has its own message: a gap, a reversed range, mismatched lengths, an invalid port, a hostname, conflicting addresses.

Port selection is a strategy. A range hands each new peer a port through a selection strategy: given the ports and the peers on each, return one. The first strategy is the port with the fewest peers, lowest port first on a tie. A later strategy plugs in without changing the parser, the driver or the port sharing.

What changes from our parser today: a single port is accepted, the default is port where it was the operating system's choice, disjoint local ranges become one error where every entry had to be the same range, and the address moves to server-public-ip.

The config comment. Config.ts describes each setting, and the docs table is generated from it. The descriptions of server-udp-ports and server-public-ip must say at least what BDS's comments say, in our own words: both modes, reuse in a range, the default, mappings and their equal lengths, the examples, and when the setting is ignored (enable-nethernet off).

One port for RakNet and NetherNet ​

From the research note, which ran a prototype on Linux, and ADR 0008, which takes a different design from it.

  • server-portv6 equal to port already works. RakNet's IPv6 socket is created with ipv6Only, in socket mode and worker mode. It needs a test and a sentence in the guide.
  • libjuice owns its socket. libdatachannel's ICE library binds the mux port itself and has no way to take a socket or a datagram from us. Two programs' sockets on one port cannot split traffic by content without Linux-only BPF steering.
  • The research note's design was a JavaScript relay. RakNet's socket sorted each datagram by its first bytes and relayed STUN and DTLS to libjuice over loopback. It ran: two and three werift clients moved 500,000 bytes each way through one port, on IPv4 and IPv6, while the same port answered 30 of 30 RakNet pings. It costs each WebRTC datagram two trips through the event loop and three system calls where libjuice alone makes one, which gives back what native code is for.
  • We sort in native code instead, by structure first. libjuice owns the shared port. Our C layer classifies each datagram by its bytes on libjuice's thread before libjuice looks it up: 0x80 and above is connected RakNet or query, 20 to 63 is DTLS, 0 to 3 with STUN's cookie is STUN, and an unconnected ping or open connection request carrying RakNet's offline magic is offline RakNet. Anything else falls through to libjuice's lookup, and what libjuice claims for no peer goes to RakNet.
  • The lookup is not free for RakNet. libjuice's address table is open addressing with linear probing, every RakNet datagram is a miss, a miss scans to the next empty slot, and a peer that leaves leaves tombstones that only a resize clears. Classifying first keeps connected RakNet out of the table and its mutex entirely.
  • RakNet's datagrams cross in batches. The classifier copies each into a shared-memory ring for RakNet, with one wake per batch, and RakNet writes its replies into a second ring. WebRTC datagrams stay in native code.
  • The mux socket is dual-stack (IPV6_V6ONLY off in src/udp.c), so it carries RakNet's IPv4 and IPv6 clients on the shared number.
  • With the RakNet worker, the worker reads and writes the rings, so the main thread sees none of it. SharedByteRing in packages/raknet already moves datagrams this way between the worker and the main thread.
  • It applies only to the ports that collide. With the default, NetherNet's single port is port. A range that contains port or server-portv6 shares that one port and leaves the others to libjuice alone. A server-udp-ports that collides with nothing shares no port, and RakNet keeps its Node.js sockets for every port it does not share.

Defaults and the written config ​

BDS calls the game port server-port. Our config calls it port, and slice 12 renames it. Slices before slice 12 still say port.

Today a fresh config writes port: 19132, server-portv6: 19133 and server-udp-ports: "", and ConfigBuilder.get(key, defaults) writes any key it reads that is missing. After this plan:

  • An empty server-udp-ports means unset, as in BDS. An existing config with "" therefore moves NetherNet's UDP from the operating system's choice to server-port. An existing config with server-portv6: 19133 keeps RakNet's IPv6 listener on 19133.
  • query-port follows the same rule: a fresh config leaves it out, and it then answers on server-port, as it does today when the two are equal.
  • An existing config's port is renamed server-port in the file when the server loads it, with its value kept. A config with both keys stops the start with an error that names them.
  • The server's --port command-line option keeps its name.
  • The server-port description says what it carries when the other keys are absent.

Windows arm64 is dropped for now, 2026-11-11, at the user's call; ADR 0006 records why.

  • One build is several megabytes. On Linux x64 with OpenSSL, NO_MEDIA and NO_WEBSOCKET, and no size tuning, the stripped library is 10,036,544 bytes and 3,592,262 gzipped; with the C++ runtime linked in, 11,677,192 and 4,095,405. Eight in one package would cost every install about 30 MB. Slice 4 measures again with Mbed TLS, section garbage collection and only the calls NetherNet uses.
  • Each machine downloads its own build, at install. The package carries a manifest of each platform's release URL and SHA-256. Its postinstall script downloads the build for the platform, checks the digest and writes it into the package's directory. That runs where the user allows install scripts: by default under npm, after pnpm approve-builds or allowBuilds under pnpm, and through trustedDependencies under Bun. Loading the library downloads nothing, and when the script has not run it fails with a message that says how to approve it. JSP_NATIVE_NETWORK_LIBRARY points at a local file instead, checked against the same digest. No per-platform packages.
  • Nothing to install. A build depends only on what every machine of its platform has, so no user runs apt install, apk add or a Visual C++ installer:
    • TLS, libjuice, usrsctp and the C++ runtime are linked in on every platform.
    • Linux glibc builds need only libc, libm and the dynamic loader, built in a Debian 12 container against its glibc 2.36. Debian 12 is the oldest Debian release in LTS, until 2028-06-30 (Debian 11's LTS ended 2026-08-31). The build measured above, made on this host's glibc 2.43, needed GLIBC_2.38, so the floor has to be set on purpose. It moves to Debian 13's glibc 2.41 when Debian 12's LTS ends.
    • Linux musl builds need only musl's libc, which every Alpine image has.
    • Windows builds link the C runtime statically (/MT), so they need no Visual C++ redistributable, only system DLLs such as kernel32.dll and ws2_32.dll.
    • macOS builds need only libSystem and the system's libc++, which every macOS has.
    • Android builds link the NDK's static libc++.
  • A checkout fetches through the same manifest, and a script builds from source for the host when the C side changes.
  • The single executable embeds its platform's library as a SEA asset and writes it to the cache directory on start, under a name with its digest, before it loads it. It downloads nothing. A cached copy with the right digest is loaded as it is.
  • The scriptc executable links the static archives.

Open questions ​

  1. Does a Bedrock client join over libdatachannel, and on a port shared with RakNet? Our own client runs libdatachannel too after slice 6, so its joins do not answer this. Slice 13 does, with cinnabar and a retail client.
  2. Does a close lose data? The spike lost data with node-datachannel sending and werift receiving. The research note's probe lost nothing in 22 runs with libdatachannel on both ends, over five close orders. With werift gone, what is left to learn is what a Bedrock client receives. Slice 8 settles our side and slice 13 the client's.
  3. Does the kick drain still have something to wait on? libdatachannel shows a channel's buffered amount and nothing inside SCTP. If its close already delivers what was queued, the drain is not needed. If it does not, our C layer can ask usrsctp.
  4. How does BDS pick a port within a range? Six players on two ports used both, and that is all we saw. The strategy interface leaves room to match it once we know.
  5. Does libjuice serve several mux ports at once? The spike ran one. A range needs one mux per port. Slice 9 checks it first.
  6. What does a client receive for a mapping in BDS? The candidates in the answer for public:local and for server-public-ip were not read. Slice 9 reads them from BDS's answer.
  7. Can the client's relay run libjuice on loopback while the server is on another machine? The relay rewrites the server's candidates to loopback addresses, so libjuice never sends off the machine. Slice 7 proves it against a remote server.
  8. How do Node.js and Bun call the native library? node:ffi is experimental in Node.js 26, and libdatachannel calls back from its own threads. Slice 4 tries node:ffi and bun:ffi, and falls back to a Node-API addon, which Bun also loads.
  9. How does the native side wake RakNet's consumer? Its thread writes the ring, and the worker or main thread has to notice without polling. Candidates are a foreign-thread callback through the binding, and a byte on a pipe or socket pair that libuv watches. Slice 4 picks one, and wakes once per batch.

Spike results ​

From 2026-11-11, on spike/node-datachannel, with node-datachannel 0.33.6 on Linux x64 (glibc). The spike swaps the nethernet Server's backend for node-datachannel/polyfill, sets enableIceUdpMux for a one-port range, and leaves our werift client as it is.

  1. Bun: yes. The server runs under Bun 1.3.14 with "server-udp-ports": "19556". Three bots from jsp-client bot --network nethernet joined, played for 10 seconds and left. Under Node.js, the integration tests pass.
  2. One port: yes. Two concurrent peers in the integration test and three on the real server shared one port, and the port was free again once the last peer left. The server offered the port on all three interfaces, and one test peer's selected pair was IPv6.
  3. A Bedrock client: not yet checked. Our own client logs in and spawns, but it runs werift, not libwebrtc.
  4. Werift-only reads: one yes, one no.
    • The selected candidate pair is at rtcConnection.sctp.transport.iceTransport.getSelectedCandidatePair(), in the same { local, remote } shape werift returns. selectedCandidateAddress reads iceTransports[0], so the server logged players as 0.0.0.0:0 until it reads the new path.
    • Undelivered data is still a gap. The probe sent 200 messages of 10,000 bytes and then closed. Werift with no drain delivered none of it. node-datachannel with no drain delivered 10,000 bytes, and after waiting for bufferedAmount to reach 0 it delivered 1,010,000 and 1,020,000 bytes in two runs. The receiver in every run was werift. A later probe with libdatachannel on both ends delivered all 2,000,000 bytes in 22 runs (research note), so the loss is probably on werift's receiving side. See open question 2.
  5. Platforms: prebuilt binaries for Android arm64, macOS arm64 and x64, Linux arm64 and x64 (glibc and musl), and Windows arm64 and x64.

Also found:

  • The polyfill hands on libdatachannel's SDP line, a=candidate:..., as the trickled candidate string, where the W3C format is candidate:.... Werift refuses it. The spike's wrapper strips the prefix; this is worth reporting to node-datachannel.
  • libdatachannel finishes gathering before it answers: the answer already carries every candidate and a=end-of-candidates.
  • Sending on a closed data channel throws (DataChannel is closed) where werift dropped the message. The server logged that error once when the bots left, so the transport needs a guard.

scriptc ​

From the research note, run on Linux x64 with scriptc 0.4.11:

  • Compiled code cannot load node-datachannel's addon. scriptc's FFI can call libdatachannel's C API (rtc/rtc.h), with libdatachannel v0.24.6 and OpenSSL linked into the executable. The test executable was 10.8 MB and served two clients on one port.
  • libdatachannel calls back on its own threads. The FFI's invoke: "foreign" mode queues each call and runs the TypeScript callback on the event loop, in order, so nothing has to poll.
  • The FFI cannot pass structs, and libdatachannel keeps one user pointer per object. A C layer of about 110 lines sends every event to one sink. About 200 to 300 lines of TypeScript then stand in for the polyfill.
  • The module with the FFI declarations must load only in the scriptc build. A named import of them fails under Node.js.
  • scriptc can also run node-datachannel in an embedded Node.js, at the cost of a 131 MB library beside the executable. That is the stopgap if a scriptc build is needed before slice 15, with our own Node-API addon in place of node-datachannel's if slice 4 ends up with one.

How we measure ​

No slice claims a speedup, and no test asserts a duration. The checks count what the code decides:

  • The ports in the answer's candidates, and the UDP sockets the server holds, for each mode.
  • Players per port in a range.
  • Bytes delivered against bytes sent, for a close and for the shared port.
  • Datagrams of each kind delivered to RakNet and to libjuice on a shared port, with zero on the wrong side.
  • JavaScript entries per WebRTC datagram on a shared port, which is zero, and ring wakes per batch of RakNet datagrams, which is one.
  • Address-table lookups per connected RakNet datagram, which is zero, and the classifier's class for each of the 256 first bytes.
  • The address the server records for a player, against the address the client connected from.

Risks ​

  • A Bedrock client may not accept libdatachannel, or a shared port. Slice 13 is the gate, and slices 4 to 12 do not merge to master before it passes. If the shared port fails and a separate one works, the default keeps the two port numbers apart.
    • Changed 2026-11-11: the user moved the work to master before slice 13 passes. Until the first publish of the builds, CI has no native library to download, so every job that starts a server with NetherNet on fails on the branch and on master alike. The publish runs from master, the remaining fixes land there, and slice 13 runs against master.
  • We own a native build. Every platform needs libdatachannel, libjuice, usrsctp and a TLS library built and published, and the libjuice patch has to keep applying. Slice 4 proves one platform before slice 5 commits to all of them.
  • An install from npm needs the network and, under pnpm and Bun, an approval. Without them, or a file named by JSP_NATIVE_NETWORK_LIBRARY, the server cannot start with NetherNet on, and the message says which. The single executable embeds its build and is not affected. Per-platform packages are the way out if this proves a problem, at the cost ADR 0006 lists.
  • The single executable needs a writable cache directory to load the library. It already needs one for its data.
  • A classifier mistake drops a transport's traffic. The classifier is tested for every first byte against real encodings, and an unsure datagram falls through to libjuice and then to RakNet, so nothing it cannot place is lost.
  • The binding may not carry libdatachannel's callbacks. node:ffi is experimental. Slice 4 decides, with a Node-API addon as the way out.
  • Our protocol code may differ from nethernet on the wire. Our client's tests against BDS and cinnabar's joins against our server catch it, in both directions.
  • We stop getting nethernet's fixes. We watch its releases for protocol changes.
  • A shared port puts a thread boundary in RakNet's path. Each RakNet datagram is copied into a ring, and RakNet is woken once per batch. WebRTC no longer waits for a tick.
  • The native library fails to load on a supported platform, for example under a new Bun release. With no fallback, the server does not start there with NetherNet on, and the client cannot dial NetherNet, until it is fixed. enable-nethernet: false runs the server on RakNet alone meanwhile.
  • A server that started before may now refuse to start, for example with server-portv6 held by another program, or with a server-udp-ports value BDS refuses. The error names the cause, and the Changesets say so.
  • Existing configs change. port is rewritten as server-port, and an empty server-udp-ports moves NetherNet's UDP to server-port. The Changeset says so.
  • The plan is large. Slices 3 and 10 do not depend on the native library and can merge on their own.
