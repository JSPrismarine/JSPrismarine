API reference / @jsprismarine/chunkgen

@jsprismarine/chunkgen ​

Java Edition's chunk generation ladder. A chunk is at one of ten named statuses, a step table says what each status may read and how far it may write, and a holder per chunk makes each status body run exactly once.

This package holds no world, no noise and no features. What it gives the server is the shape those things have to run in if the same seed and the same chunk position are to produce the same blocks whatever order chunks are generated in and however many threads do it.

ts
import { GENERATION_PYRAMID } from '@jsprismarine/chunkgen';

const features = GENERATION_PYRAMID.stepTo('features');
features.requireReadable(1, 0, 'terrain'); // 'terrain'
features.requireReadable(1, 0, 'features'); // throws ChunkReadOutOfWindowError
features.canWriteBlocksAt(1, 0); // true, and it is the only step for which that is true

The tables come out of Mojang's 26.3 server jar, read class by class in java-chunk-generation-pipeline.md. The decision to copy them rather than derive something equivalent is ADR 0002.

The ten statuses ​

empty, structure_starts, structure_references, biomes, terrain, features, initialize_light, light, spawn, full. register sets each status's index to its parent's plus one, so the ladder is a chain and isOrAfter is an integer comparison.

26.3 has ten, not the twelve older versions had: noise, surface and carvers are one terrain status whose task runs noise fill, surface materials and carvers back to back.

Three of the ten have no body in this repository yet. Lighting lives in @jsprismarine/lighting and spawning in @jsprismarine/spawning, and neither is sequenced against generation today. They stay on the ladder anyway. Collapsing them would shift every accumulated radius by one, and the step table would stop being something anyone can check against the jar.

The step table ​

Each step declares two windows and one radius.

Direct dependencies. Per Chebyshev distance, the status that ring is guaranteed to have reached. This is what a running body may read, and requireReadable throws rather than returning a chunk at the wrong status, the way WorldGenRegion.getChunk raises a ReportedException. An undeclared read is a crash on the first chunk rather than a wrong block on the thousandth.

The full row is the one that is not the jar's. Java's full declares nothing, because its feature pass has already written through into the neighbor. Ours reads the eight neighbors at features to collect the patches they recorded for it. The accumulated table does not move: full already guaranteed initialize_light at distance 1, which is above features.

Accumulated dependencies. The transitive closure of the above, which is what sizes each layer of a scheduler. Inverting the full row gives the radius each status has to reach before one chunk can become full: 11 for empty and structure_starts, 3 for structure_references and biomes, 2 for terrain, 1 for features and initialize_light, 0 for light and spawn. Generating one chunk from nothing therefore touches 529 chunks at structure_starts and 25 at terrain.

The block write radius. terrain is 0 and features is 1. Every other step is -1, and -1 excludes the step's own chunk, so those steps cannot write a block through the region at all. features is the only status that writes into a neighbor, which is why a tree is whole across a chunk border, and it is the only place two concurrent bodies could collide.

Two numbers in the package exist as arithmetic checks on the table rather than for their own sake. RADIUS_AROUND_FULL_CHUNK is 11 and SAFETY_MARGIN_CHUNKS is 90, and the second needs the accumulated list for full to be exactly 12 long. A transcription slip anywhere in the pyramid moves one of them.

The holder and the scheduler ​

A ChunkHolder is one chunk's place in the ladder: the chunk, and one promise per status. The first caller to ask for a status creates the promise and runs the body; every later caller awaits that same promise. That is what makes a (chunk, status) body run exactly once however many requests overlap. Java needs a compare-and-exchange on startedWork for it, because several pool threads reach applyStep at once; only the thread that owns the holder map touches a holder here, and a map insert cannot be interleaved. startedWork is kept anyway, because it is what catches a layer loop that skips a rung.

ChunkHolderMap decides how long a holder lives, by reference count. A run acquires every chunk inside its radius before it runs a step and releases them all when it finishes, so nothing it depends on can be dropped while it is in flight, and a holder nothing needs goes away. The generator's 128-entry LRU got this wrong in a way that was measurable: preload-radius: 5 is 121 chunks, right at the edge, so a feature pass writing into a neighbor could land on a holder that had already been evicted. A caller that wants a chunk to stay resident past a run acquires its own reference.

GenerationScheduler is the layer loop. To bring a chunk to a status, the neighborhood has to reach that status's dependencies first, so a run walks the ladder from empty upward and applies each step to the square the accumulated dependency table sizes.

ts
const holders = new ChunkHolderMap((chunkX, chunkZ) => new MyChunk(chunkX, chunkZ));
const scheduler = new GenerationScheduler({ holders, tasks: { terrain: buildTerrain } });

scheduler.layersFor('terrain'); // [['empty', 9], ['structure_starts', 9], ..., ['terrain', 0]]
const chunk = await scheduler.generate(0, 0, 'terrain');

A status with no entry in tasks passes its chunk through, which is what every status above terrain does today. The bodies live in the server, because they need the noise, the biome source and the feature registries; the scheduler only knows how to order them and what each one may read.

Two properties follow, and the tests count them rather than assert them in prose. Nine chunks asked for at once at a full target build terrain over the union of their windows, 49 bodies, where DataDrivenGenerator.generateChunk builds a 3 by 3 tile per chunk and so builds 81. And the sixteen chunks of a 4 by 4 area come out identical whether they are asked for row major, reversed, shuffled, one at a time or all sixteen at once.

The feature patch ​

features is the one status that writes outside its own chunk, and the one place two bodies running at once could land on the same block. Nothing writes through. A feature's writes into its own chunk apply as they happen, so features inside a chunk still see each other the way Java's do; a write that lands in a neighbor is recorded and handed to that neighbor's InboundFeaturePatches. The neighbor applies its own post-features state first and the patches after it, in FEATURE_PATCH_ORDER.

ts
inbound.receive(-1, 0, patchFromTheWest);
inbound.inMergeOrder(); // ordered by position, not by when each arrived

The order is (dx, dz) ascending with dx fastest, and storing by source offset rather than appending to a list is the mechanism rather than a detail: a list would record arrival order, and arrival order is what the scheduler chooses. receive refuses the chunk's own offset and anything past radius 1, and refuses a second patch from the same neighbor, which would mean a features body ran twice.

This is ADR 0002's one deliberate deviation from Java. Java writes through a live WorldGenRegion into the neighbor's ProtoChunk, so which of two overlapping features wins depends on which chunk reached features first, which depends on scheduling; Java's border output is therefore not a function of the seed alone, and ours is. The price is one case: a feature whose placement decision reads a block sees the neighbor's terrain and not the neighbor's features, so two features can end up in the same space where Java would have refused the second.

The chunk type ​

The holder, the map and the scheduler take the chunk type as a parameter. All they need of it is StagedChunk: where it is, which rung it is on, and an advanceTo that refuses to go backward with ChunkStatusRegressionError.

The package ships no chunk of its own. A server climbs the ladder with the chunk buffer it already has rather than copying every block into a second representation twice per status. @jsprismarine/prismarine does: its generation stages speak Java block states with properties.

The worker pool ​

GenerationPool runs status bodies in worker threads, over piscina. It knows a chunk position and a status name and nothing else about world generation, so this package does not depend on the server.

A caller names a pipeline module. Each worker imports it once, hands it the pool's setup value, and keeps whatever it builds for the life of the worker. That is the whole reason a worker is worth starting: a seed's noise tables cost 55 to 134 ms to build and the 7594-entry climate biome source 145 to 345 ms, so a worker is pinned to one world rather than told which world each task belongs to.

ts
const pool = new GenerationPool({
    pipeline: '/path/to/built/terrainPipeline.js',
    workers: 6,
    setup: { seed: 1234n, registryBundle }
});

const { payload } = await pool.run({ status: 'terrain', chunkX: 3, chunkZ: -14, input: beardPieces });

The pipeline module exports createGenerationPipeline, which answers with an object that has a run. A body hands back a payload and the list of ArrayBuffers inside it, and the pool transfers those rather than copying them: 18 microseconds for a 192 KiB column against 76 cloned and 1370 as a number[].

Two constraints are not negotiable.

Only a status that writes radius 0 belongs in a worker. terrain is one, which is why Java sends it to a thread pool and keeps features, which writes radius 1, on a single executor. Two terrain bodies can never touch the same block, so no two workers can race.

The module has to be something the worker's loader can import(). A worker thread inherits process.execArgv, so the loader the host was started with is already installed in the worker. A published install needs nothing: the specifier is a built .js. A dev checkout runs under node --import tsx, and its workers do too, which is what follows the extensionless @jsprismarine/* imports a .ts pipeline module is full of. Nothing has to be built first. A production workspace start selects the compiled .js exports with the jsprismarine:dist condition, so the pool picks its built pipeline and worker entries without adding a TypeScript loader to either thread.

A host that reads TypeScript through a loader of its own, which is vitest, has no such flag to hand on, and its workers would read the .ts through Node's strip-only loader, which stops at the first extensionless import. When the pipeline or the worker entry is TypeScript source and nothing in process.execArgv or NODE_OPTIONS installs an ES module loader, the pool starts its workers with --import and the tsx resolved from beside the pipeline module, which is the one the package being run from source declares. workerExecArgv(options) is that decision, exported so a caller can see what its workers will get.

Math.random is shadowed inside the worker and throws. It is seeded independently per V8 isolate, so a main thread and six workers produce seven different sequences and a decorator that reached for it would give a different world depending on which worker ran the chunk.

When a pool cannot start ​

GenerationPool.unavailable(options) answers with a sentence or with undefined, and a caller is expected to ask before it builds one. It refuses a single executable, where the modules live in the binary and no worker thread can reach them, and it refuses a worker entry or a pipeline module that is not on disk.

It cannot promise the import succeeds, because that depends on the loader, so the first task is still the real test. A caller that wants a server rather than a fast one catches that rejection, says so once, and runs the body on its own thread.

Running the pool in a host process ​

GenerationPool and HostedGenerationPool both implement GenerationTransport. The hosted one forks a generation host, lowers its operating system priority, and sends it tasks over IPC, which is the portable way to give generation a lower priority than the server: Node cannot lower one worker thread. createGenerationTransport({ ...options, host: 'process' }) builds it and falls back to the in-process pool, calling onFallback with the reason, when no host can start. A host that dies is replaced and the tasks it held are sent again, which returns the same bytes. Shared buffers in the setup are copied to the host once and shared again among its workers. A Bun-compiled executable starts the host by running itself again with --role generation-host (GENERATION_HOST_ROLE from hostRole), so its entry has to hand that role to generationHost, and the build has to define JSP_EMBEDDED_GENERATION_HOST to say it does. A Node single executable cannot start the host yet and keeps the in-process pool. setBackgroundLimit caps how many soon and idle tasks run at once, which is what ConcurrencyGovernor steers; immediate tasks are never limited.

Installation ​

To install @jsprismarine/chunkgen, use the following command:

pnpm install @jsprismarine/chunkgen --save

FEATURE_PATCH_ORDER ​

Defined in: FeaturePatch.ts:16

The eight neighbors a feature pass can reach, in the order their writes are merged.

(dx, dz) ascending with dx fastest, which is row major from the northwest corner. The order is the reason a chunk border is a function of the seed and the position: two features from different chunks that land on the same block always resolve the same way, whichever chunk was asked for first and however many were in flight.

Java has no such order. Its feature pass writes straight into the live neighbor through a WorldGenRegion, so which of two overlapping features wins depends on which chunk reached features first, which depends on scheduling. ADR 0002 takes the deviation deliberately and names its one cost: a feature that reads a block before placing sees the neighbor's terrain and not the neighbor's features, so two features can occupy the same space where Java would have refused the second.

How badly a caller wants a chunk, highest first.

The pool holds back everything it is not already running, so this is the order the backlog is drained in rather than a hint. Three bands rather than a number, because the three are the three questions a server actually asks:
