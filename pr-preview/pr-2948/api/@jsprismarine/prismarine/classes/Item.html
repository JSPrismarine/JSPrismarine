Class: Item ​

Defined in: prismarine/src/item/Item.ts:172

One item stack, as the rest of the server holds one.

Everything it answers about itself - how hard it hits, how much armor it is worth, how much durability it has, what it harvests - is read off Java's data components rather than declared by a subclass. The 65 item classes this replaced each restated one or two of those numbers; the table has all of them, for all 1613 items.

stackNetworkId ​

stackNetworkId: number = 0

Defined in: prismarine/src/item/Item.ts:195

The stack network id the client knows this stack by, or 0 before it has one.

The inventory packets write it, so that a client and the server name a stack by the same number in an ItemStackRequest and in its answer. A stack read off the wire keeps the id it came with.

Ids are counted per player by HumanInventory.assignStackNetworkId. A stack keeps its id when it moves whole or changes size through Item.withCount; every other copy starts without one, and so does a part split off a stack.

asPredicateStack(): ItemStack

Defined in: prismarine/src/item/Item.ts:661

This stack as the loot, predicate and enchantment grammars read one.

The components carry what those grammars actually look at today: minecraft:enchantments for Fortune, Looting, Silk Touch and every effect component, and the three the item type declares that the enchanting table and the anvil read off a stack - minecraft:enchantable, minecraft:max_damage and minecraft:damage. An empty map used to go out here, which made every apply_bonus see an unenchanted tool and every enchanting table refuse every item.

The runtime id of the block this item places, or zero for anything that places none.

An id given at construction wins. getMiningSpeed() ​

getMiningSpeed(block): number

Defined in: prismarine/src/item/Item.ts:630

How fast this mines one block, which is Java's Player.getDestroySpeed as far as a stack alone can answer it.

The minecraft:tool rules give the base - the first rule whose block set matches and that states a speed - and minecraft:mining_efficiency raises it, which is the attribute Efficiency's modifier writes. Java only adds the attribute to a speed already above one, so Efficiency does nothing for a tool that is the wrong tool for the block.

Dig Speed, Mining Fatigue, being underwater without Aqua Affinity and being off the ground are the four other terms of Java's formula, and none of them is modeled: there is no effect system and no swimming state on an entity.

Parameters ​

string

The block identifier being mined.

Returns ​

number

A multiplier on the base rate; 1 for a bare hand or an item with no rule for the block, which is Java's Item.getDestroySpeed.

networkSerialize() ​

networkSerialize(stream, stackNetId?): void

Defined in: prismarine/src/item/Item.ts:715

Writes an item stack in the form that carries a stack net id - an ItemInstance.

There are two forms on the wire, and at 2168 they no longer differ by one byte. This one, which an inventory, an equipped hand or a transaction carries, opens with a fixed two byte id and closes with an unsigned block runtime id; the other, networkSerializeWithoutStackId, uses a varint for both. Neither still stops early for air: up to 748 a zero id was the whole stack, and now every field is written whatever the id is. An inventory is mostly empty slots, so a stack that stops after the id truncates the packet almost immediately - which is exactly what the client reports as a bad packet on join, before any of the interesting packets are even reached.

networkDeserialize() ​

static networkDeserialize(stream): Item

Defined in: prismarine/src/item/Item.ts:854

Reads an item stack off the wire.

The layout is NetworkItemStackDescriptor, which @jsprismarine/protocol already describes: the id, the count, the aux value, an always present flag saying whether a stack net id follows, the block runtime id, and one length prefixed blob holding the nbt and the can-place-on / can-break lists. All of it, even for air.

The block lists are retained so a stack the client sends can be sent back with the same adventure-mode restrictions. The NBT compound and optional shield blocking tick remain unused here; the user-data structure isolates them from the following packet fields.

Reading the flag is what keeps every field after it aligned. It used to be read only when a caller asked for extra, which no caller ever did, so from that byte onwards the reader was one out: the lists it then walked had garbage lengths, ran off the end of the buffer and threw. Every InventoryTransaction died there - which is what left a survival block break with no sound, the packet never reaching its handler.
