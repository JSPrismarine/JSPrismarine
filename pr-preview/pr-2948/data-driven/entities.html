Data-driven entities ​

What a mob does on this server is decided by a Bedrock behavior-pack file rather than by a TypeScript class. A definition names the mob's components, the component groups its events switch on and off, and the goals it runs. The server reads that file, resolves it once, and builds every instance of the mob from the result, so adding a mob means shipping a pack rather than writing code.

This page explains how a definition becomes a running mob, which parts of a definition the server acts on today, and where it stops. It assumes you know Minecraft and a behavior pack's shape, and nothing about the plan or the research notes behind the implementation.

Where the code lives ​

Six pieces share the work.

PackageWhat it owns
@jsprismarine/entitiesDefinition parsing, components and component groups, the event engine, entity properties, the filter evaluator, the goal scheduler
@jsprismarine/entity-goalsAll 170 vanilla minecraft:behavior.* goals and the A* path finder they walk with
@jsprismarine/entity-brainsJava Edition's brain AI, for the twenty mobs Bedrock's format cannot describe
@jsprismarine/spawningThe spawn_rules/*.json grammar and the natural spawn loop
@jsprismarine/tradingTrade tables, offer generation and the villager economy
packages/prismarine/src/entity/data/The host: one runtime per dimension that wires the five packages to a live world

None of the five packages knows there is a server. Each declares an interface for what it needs from the world, and the host implements it. That is why they have their own test suites and why a plugin can drive one of them without a world at all.

From a file to a mob ​

The runtime keeps three stages of the same content apart.

A definition is the parsed JSON of one entity file, exactly as the winning pack wrote it. A type is that definition resolved once at load time, with every component bound to an implementation and every group pre-resolved. An instance is one live mob, with its own component state, its own attributes and its own goal scheduler. Component state is what a component carries between ticks, such as a timer, an air supply or a cooldown. It lives on the instance, one plain-data record per component, and every write reaches the host with its value before and after, so the server can save it and undo it.

Resolution is deliberately lenient. parseEntityDefinition validates the shape of the five keys Mojang's own schema types (description, components, component_groups, events, upgrades) and reports anything it did not read instead of refusing the file. A pack written against a newer game still loads, and the diagnostics report names what the runtime ignored. Four features are gated on format_version, and using one below its version loads anyway with a report: root-level event filters need 1.19.20, queue_command needs 1.20.60, emit_particle and play_sound need 1.21.50, and entity_version with upgrades needs 1.26.20.

The composed vanilla behavior pack of Bedrock Dedicated Server 1.26.51.1 holds 129 entity definitions, and all 129 parse without an error.

A chicken, traced ​

The vanilla chicken is small enough to follow end to end and uses most of the machinery. Here is the part of entities/chicken.json that matters, trimmed:

json
{
  "format_version": "1.26.50",
  "minecraft:entity": {
    "description": {
      "identifier": "minecraft:chicken",
      "spawn_category": "creature",
      "properties": {
        "minecraft:climate_variant": {
          "type": "enum",
          "values": ["temperate", "warm", "cold"],
          "default": "temperate"
        }
      }
    },
    "components": {
      "minecraft:health": { "value": 4, "max": 4 },
      "minecraft:movement": { "value": 0.25 },
      "minecraft:collision_box": { "width": 0.6, "height": 0.8 },
      "minecraft:navigation.walk": { "can_path_over_water": true, "avoid_damage_blocks": true },
      "minecraft:behavior.float": { "priority": 0 },
      "minecraft:behavior.panic": { "priority": 1, "speed_multiplier": 1.5 },
      "minecraft:behavior.tempt": { "priority": 4, "items": ["wheat_seeds", "..."] },
      "minecraft:behavior.random_stroll": { "priority": 6, "speed_multiplier": 1 },
      "minecraft:behavior.look_at_player": { "priority": 7, "look_distance": 6, "probability": 0.02 }
    },
    "component_groups": {
      "minecraft:chicken_baby": { "minecraft:is_baby": {}, "minecraft:ageable": { "duration": 1200 } },
      "minecraft:chicken_adult": {
        "minecraft:loot": { "table": "loot_tables/entities/chicken.json" },
        "minecraft:breedable": {},
        "minecraft:offspring_data": { "breeds_with": { "minecraft:chicken": {} } },
        "minecraft:behavior.breed": { "priority": 3, "speed_multiplier": 1 },
        "minecraft:spawn_entity": { "entities": [{ "spawn_item": "egg", "min_wait_time": 300 }] }
      }
    },
    "events": {
      "minecraft:entity_spawned": {
        "sequence": [
          {
            "randomize": [
              { "weight": 95, "trigger": "minecraft:spawn_adult" },
              { "weight": 5, "add": { "component_groups": ["minecraft:chicken_baby"] } }
            ]
          },
          {
            "first_valid": [
              {
                "filters": { "test": "has_biome_tag", "value": "spawns_warm_variant_farm_animals" },
                "set_property": { "minecraft:climate_variant": "warm" }
              }
            ]
          }
        ]
      },
      "minecraft:spawn_adult": { "add": { "component_groups": ["minecraft:chicken_adult"] } }
    }
  }
}

A chicken arrives in the world like this.

  1. spawn_rules/chicken.json offers the position. It puts the chicken in the animal population pool, wants the surface pass, a minecraft:grass_block underfoot, light 7 to 15, a biome tagged animal, and a herd of 2 to 4. Its weight of 10 competes with every other rule that passed at the same position.
  2. The runtime creates the instance and fires exactly one spawn event, minecraft:entity_spawned. The randomize node draws 95 against 5, so about nineteen chickens in twenty trigger minecraft:spawn_adult and the twentieth gets the baby group instead. The weights are relative, not percentages; 95 and 5 would behave the same as 19 and 1.
  3. The first_valid node in the same sequence reads the biome's tags and writes the minecraft:climate_variant enum property, which the client reads to pick the chicken's skin. It cannot test for the baby group the randomize node may just have added, because an event's effects are decided immediately and applied only when the entity next ticks.
  4. On the next tick, the adult group's components initialize: minecraft:loot names the table death rolls, minecraft:breedable supplies the love-state requirements, minecraft:offspring_data declares compatible mates and offspring, and minecraft:behavior.breed joins the scheduler at priority 3.
  5. Every tick after that, the scheduler walks the goals from priority 0 upward and starts each one whose control flags are free. float holds jump, panic and random_stroll want move, look_at_player and random_look_around want look, and tempt wants both move and look. Hold wheat seeds nearby and tempt at priority 4 takes both flags away from random_stroll at 6 and look_at_player at 7, in the same tick.
  6. The stats the client is sent come from the components, except where ADR 0001 hands a stat to Java. The chicken keeps Bedrock's 0.6 by 0.8 hitbox, where Java publishes 0.4 by 0.7.

minecraft:spawn_entity runs one timer per configured entry. When it expires, the runtime checks the entry's filters, then creates the requested item or entity with its count, spawn event and sound. single_use stops that entry after a successful spawn. should_leash records the spawned entity's holder by stable identity, so the is_leashed and is_leashed_to filters can still read the relationship after saving, restarting, or unloading either entity's chunk. Using a lead on an entity with minecraft:leashable records its holder, runs the component's on_leash event, and projects the relationship to actor metadata. Shears cut its incoming leash unless can_be_cut is false. They also cut outgoing leashes when the holder has minecraft:leashable_to.can_retrieve_from; each cut entity runs on_unleash. Physical leash movement and fence-knot links are not implemented yet.

Components: what runs, and what only parses ​

Vanilla's 129 definitions use 202 distinct non-goal component keys. All 202 names are registered, and every entity definition resolves with its non-goal components recognized. Ninety-five keys carry runtime behavior. The remaining 107 expose data without simulating their behavior; some have a dedicated schema, and the generic factories preserve the raw body. Both are available through EntityInstance.componentParams.

This count includes host reads and actor-metadata projections. It does not mean every field of each component has a runtime implementation.

minecraft:entity_sensor searches live mobs and players for each subsensor, measures its horizontal and vertical bounds with the configured offset, evaluates event_filters with the sensor as self and each candidate as other, and enforces count bounds, require_all, and cooldowns. Its default relative_range adds the sensor's collision-box width and height to those bounds.

minecraft:block_sensor checks nearby breaks up to its sensor_radius (16 by default, capped at 32). Each matching on_break.block_list entry raises its on_block_broken event. When sources is present, its filters see the breaker as other, the player subject for a player breaker, and the broken block as block.

minecraft:inside_block_notifier checks the blocks overlapped by the entity's collision box, including the block's named state values. It raises entered_block_event and exited_block_event only when a matching block-state condition starts or stops matching.

minecraft:area_attack scans targets within the configured collision-box range each tick, applies its entity filter and per-target cooldown, then routes the configured damage cause, source, sound, and death-message override through the entity runtime.

minecraft:target_nearby_sensor reads the entity's current target, checks follow_range, and casts a block ray between the observer's and target's eyes. Solid blocks occlude the target for its visibility events and for goals that require line of sight.

minecraft:teleport tries timed random destinations in the configured cube, teleports toward a distant attack target within target_distance, and lets an entity evade a matching projectile before its hit effects apply. Random attempts use the configured light or dark chance, and both random and target teleports require a reachable destination.

minecraft:combat_regeneration observes the deaths of the entity's active attack target. It gives Regeneration I to the killer when apply_to_self names the source or apply_to_family names a shared type family, removes Mining Fatigue, and honors the configured duration, including "infinite".

minecraft:mob_effect searches nearby mobs and players, applies entity_filter with the source as self and each candidate as other, then applies the configured effect and duration. Its cooldown starts after at least one target accepts the effect. minecraft:spell_effects adds its configured effects and then removes its named effects when activated; restoring a saved entity does not repeat that one-time operation.

minecraft:nameable controls name-tag renaming, queues its default_trigger and matching name_actions, and projects always_show and the custom name to actor metadata. Data-driven names are included in the entity's saved runtime record.

minecraft:is_dyeable gates dye use, updates minecraft:color in the data-driven entity's runtime state, and projects its interact_text to actor metadata. The changed color is persisted.

minecraft:home, which records the spawn position for home-based goals unless an event or restored record already supplied one; minecraft:is_dyeable, which gates dye use, updates the palette color and projects the touch-screen prompt; minecraft:combat_regeneration, which gives the killer of its attack target Regeneration I and removes Mining Fatigue; and minecraft:teleport, which uses its configured random, target, and projectile settings to move the entity. minecraft:burns_in_daylight ignites an entity in direct sunlight unless its configured protection slot is occupied or it is wet. The runtime maintains fire while exposed, deals fire_tick damage every second, honors the fire-damage gamerule and minecraft:fire_immune, fires minecraft:on_ignite, updates on_fire filters, and saves and projects the active fire state. minecraft:interact evaluates item filters, enforces cooldowns, raises its event, adjusts health, plays sounds, emits vibrations, creates configured entities, and rolls its add_items and spawn_items loot tables. It also applies hurt_item, use_item, and transform_to_item through the live player's inventory. equip_item_slot and drop_item_slot read named equipment slots or indexed slots in minecraft:inventory, and drop_item_y_offset moves the resulting drop vertically. give_item replaces the entity's main-hand item, repair_entity_item restores durability in a named entity inventory or equipment slot, take_item moves the entity's main-hand item into an empty player hand, and interact_text reaches touch-screen clients through actor metadata. The fields swing defaults to true and relays the player's arm animation to other viewers tracking the player after a successful interaction; setting it to false suppresses that relay. particle_on_start emits its named particle with particle_y_offset and particle_offset_towards_interactor applied. admire and barter start piglin item behavior when their components and brain are active. minecraft:admire_item supplies its duration and post-damage cooldown; damage ends current admiration and blocks new attempts until that cooldown expires. minecraft:barter supplies the barter loot table and its post-damage cooldown. The runtime stores the offered gold ingot in the offhand, starts admiration, then rolls the table with the barter loot context when admiration ends. Non-none particle_on_start.copper_event and unknown particle fields still report as unsupported. minecraft:angry counts its anger down, raises calm_event, excludes targets matching filters, plays angry_sound on the configured sound_interval, and broadcasts on activation, attack, being attacked, and death according to its flags. Each broadcast reaches nearby entities of the same type or the configured broadcast_targets families, evaluates broadcast_filters with the broadcaster as the caller and each candidate as other, and fires the candidate's minecraft:on_friendly_anger trigger. It gives candidates the triggering entity as their target when one is known. Attacker exceptions are data in minecraft:ignore_cannot_be_attacked; the package supports that component for custom definitions too. The ground-input, dash, free-camera, and vertical-movement components currently only advertise controls to the client; the server does not apply those inputs to entity movement. The entities package README lists each component and what it does.

"Parses as data" is not the same as "ignored". The minecraft:breedable hook matches feed items, checks tame, health, baby, love, and cooldown requirements, and puts eligible adults into love; the separate breeding runtime reads compatible mates and offspring pairs from minecraft:offspring_data. Type resolution normalizes definitions that use the older minecraft:offspring spelling into that key. minecraft:healable and minecraft:tameable also implement item interactions through component hooks, while the host applies the resulting health, owner, and event effects. The minecraft:spawn_egg_interaction hook creates the offspring declared by the entity's active data when its matching spawn egg is used. minecraft:collision_box and the minecraft:navigation.* flavors build the path finder's profile; its walking, swimming, and flight capabilities project to CANWALK, CANSWIM, and CANFLY. minecraft:can_climb enables ladder traversal and projects to CANCLIMB, while minecraft:can_fly lets the pathfinder leave solid ground, and minecraft:can_stand_on_powder_snow makes powder snow support the entity in pathfinding and body collision. The host also reads minecraft:explode to detonate a creeper, minecraft:rideable to seat riders, and the two trade-table components to build a merchant. The shared body physics reads minecraft:air_drag_modifier, minecraft:uses_uniform_air_drag, minecraft:friction_modifier, and minecraft:bounciness to apply the active entity's drag, ground friction, and collision response.

Every non-goal key in the vanilla pack is registered, including keys used by only one entity such as the shulker's minecraft:peek and the warden's minecraft:anger_level. Registration makes a component's data available; it does not promise that the server simulates its behavior. The corpus test checks the 202 names and counts the keys that currently carry behavior.

An unknown component name writes a component.unknown warning to the server log and ServerContent.diagnostics, and appears in EntityType.unimplementedComponents. A registered component without runtime behavior does not produce that warning, so check the entity component inventory in the package README when deciding whether the server simulates a component.

Events and the component-group state machine ​

An entity's state is which component groups are active, and events are the only thing that changes it. The rule the engine follows is the one Mojang documents: the effects of an event are determined immediately and applied when the entity next ticks. A filter in a later sequence entry therefore cannot see what an earlier entry changed.

Inside one node the engine runs add, remove, set_property, the raw actions and trigger, then walks sequence in order, then draws one branch of randomize, then takes the first passing branch of first_valid. A node's own filters gate the whole node, and nodes nest without limit. When the effects are applied, groups are removed first and added second, so a group an event both removes and adds ends up active and re-initialized, which restarts the timers inside it.

Nine action keys parse into something the engine carries out: play_sound, set_home_position, emit_vibration, drop_item, execute_event_on_home_block, emit_particle, reset_target, stop_movement and queue_command. Eight of those are everything the vanilla pack writes, across its 850 events; queue_command is documented and unused by vanilla. Six of the nine leave the entities package through an effects seam the host fills, and set_home_position, stop_movement and reset_target are carried out inside the package.

The prismarine host routes emitted game events through a per-world Java-style listener registry. It searches only loaded chunks within the event's notification range, applies each listener's own radius, and delivers distance-ordered listeners nearest first. Active vibration listeners on data- driven wardens and allays receive events; wardens record suspicious positions, and allays update the note-block position they follow.

damage, die and teleport are worth naming because they appear in some third-party documentation as event actions. They are not. Mojang's EventActions.md does not list them, no vanilla entity writes one, and this server treats an unrecognized action key the way it treats any other: the event still runs its other effects, and the unreadable key reaches the report. To make an event take a mob out of the world, add a component group carrying minecraft:instant_despawn, which removes it without rolling its loot table. To kill it properly, deal the damage from the code that fired the event.

Every blow a data-driven entity takes runs one staged pipeline, as ADR 0013 describes: a mob's bite, a projectile, a blast, a player's swing, a status effect, a command, an item and a component hazard such as drowning, and a dropped stack's fire, lava and cactus. The guards run first and write nothing: the store's own rules, the hurt cooldown, minecraft:cannot_be_attacked, a dropped stack's minecraft:damage_resistant, Java's Ender Dragon rules, minecraft:damage_sensor and the immunity components, the fireDamage game rule, and then before-hooks such as the entityDamage plugin event, which can cancel a blow or change its amount. A veto leaves only an action-rejected entry in the change log. Declared modifiers then work out what lands, in priority order: the hurt cooldown's difference, armor, protection enchantments, resistance, absorption, the dragon's scaling and the damage sensor's multiplier. A blow from a player, a blast, a command or an effect keeps the cooldown, armor and knockback the legacy pipeline gave a mob, and a mob's own attacks keep none of them. A damage sensor reads Bedrock's cause names, so a player's swing is entity_attack.

The commit applies the blow and runs a death inside the same call. When lethal damage queues a self event, the event applies before the runtime decides what the death is. That lets the Ender Dragon's data-defined death event activate minecraft:behavior.dragondeath; the goal holds its controls for 200 ticks, then removes it.

Filters ​

Filters are the shared condition language, and the same evaluator answers them for entity definitions, spawn rules and trade tables. All 107 filter tests Mojang's generated documentation lists are implemented, and vanilla uses 86 of them.

Both encodings parse. 27 vanilla entity files are written by the 1.26 serializer, which writes subject and operator as integers rather than strings, and the AND, OR, NOT, all and any aliases read as their canonical combinators. Two shapes vanilla writes that the published grammar does not describe also parse: five files put all_of and any_of in one object, and the skeleton writes the legacy shorthand {"other_with_families": "lightning"}.

A filter test whose fact nothing can answer evaluates to false and is reported, rather than defaulting to true. That matters when you are debugging: a mob that never does a thing may be looking at a world fact this server does not track yet, and the report names the test.

has_tag reads the entity's dynamic string tags, the same set the /tag command edits. The store keeps that set on the entity, carries it through a portal and writes it to the actor's Tags list when the entity is saved.

Equipment filters scan every slot in their declared domain. has_equipment_tag, actor_has_item_with_enchantment_in_slot, has_damaged_equipment, and has_item_with_component read the item stack's tags, enchantments, durability, and data components for both mobs and players.

Goals ​

A goal is a component carrying a priority and optional control_flags, and all 170 minecraft:behavior.* names vanilla uses have a registered factory in @jsprismarine/entity-goals. packages/entity-goals/src/totality.test.ts fails if a name in the generated goal inventory has no registered factory, so the number cannot drift without the build noticing. Ninety-two vanilla entities declare at least one goal, and every goal name they declare is registered; the other 37 definitions have no goals.

The scheduler is the documented one. Priority 0 is the highest. Each tick it stops every running goal that can no longer continue, then walks the registered goals upward from 0 and starts each one whose control flags (move, look, jump) are either free or held by a strictly worse priority, stopping the holder in the same tick. A goal with no control flags runs alongside everything else, which is how the nine targeting goals work.

Where Java and Bedrock describe the same goal, the constants come from Java. Thirty of Java's goal class names match a Bedrock name after snake-casing, so for those the numbers are read out of the unobfuscated 26.3 server jar and the JSDoc names the class: the 0.02 chance per tick in look_at_player, the 20-tick swing cadence in the melee goals, the 300-tick revenge memory in hurt_by_target. Where the two editions disagree, the Bedrock parameter wins, because these are Bedrock definitions.

Movement goes through an A* path finder over whole blocks. The profile comes from the entity's active minecraft:navigation.* component plus its collision height and step height, and the flags on that component decide which cells the search may enter: doors, water, lava, damaging blocks, portals, sunlight and the three media (ground, swim, fly). A search expands at most 512 nodes unless the caller raises the budget.

The goals reach the world through GoalWorld, a 46-member interface covering sight, combat, items, blocks, relationships and reporting. Every member is optional, and a goal whose world cannot answer what it needs refuses to start rather than throwing. The server answers all 46 today, which takes the inventory from 118 goals able to run to all 170; before the seam was finished, hurt_by_target (42 of the 129 vanilla entities carry it), panic (37), breed (26) and mount_pathing (26) could never start.

Brain mobs, and why they are different ​

Java Edition runs two unrelated mob AI systems, and Bedrock's data format only describes one of them.

The goal system is the one Bedrock's minecraft:behavior.* components express, and 30 of Java's 67 goal class names match a Bedrock name directly. The brain system is something else: a memory map, a list of sensors that write into it, and a table of behaviors keyed by priority and activity. Bedrock publishes no memory registry, no sensor registry and no activity registry at all, so a Bedrock-shaped entity file has no way to say what a brain mob is doing. There is no component for "the piglin has been admiring this gold ingot for 119 ticks" because the format never names that idea.

Exactly twenty mob classes in Java build a brain, and the list is a fact rather than a judgment call: scanning every class under net/minecraft/world/entity/ for brainProvider or makeBrain finds 21, and the twenty-first is LivingEntity, which holds the base. The twenty are the allay, armadillo, axolotl, breeze, camel, copper golem, creaking, frog, goat, happy ghast, hoglin, nautilus, piglin, piglin brute, sniffer, tadpole, villager, warden, zoglin and zombie nautilus. Everything else in the game, including every zombie, skeleton, farm animal and the ender dragon, is goals only.

@jsprismarine/entity-brains implements that second system against Java 26.3: all 115 memory modules, all 24 sensors, all 26 activities, the combinators, and each of the twenty mobs with its real activity table, priorities, memory conditions and constants. The behavior library is 37 shared behaviors plus the mob-specific ones. A behavior whose effect the world seam can express is implemented in full; the rest keep their real name, memory conditions and constants, do the memory bookkeeping Java does, and leave the world effect to the host. The sniffer's host checks its live dig conditions, drops the Java digging loot after 120 ticks, and records a dig position only when the behavior completes. The warden's host deals sonic-boom damage after the 34-tick windup and applies knockback only when damage lands. Villager brains read raid status and request raid effects through the host; raid creation and waves still belong to a raid manager the server does not have.

Two consequences are worth knowing before you build around a brain mob.

A brain mob does not run its Bedrock goals. The host hands a GoalWorld only to entities that are not brain mobs, so the minecraft:behavior.* components in a frog's vanilla file never start; its Java brain drives it instead. The camel and the happy ghast are the exceptions, because Java gives both a registerGoals and a brainProvider, and the runtime ticks both systems for them.

The villager needs a translation step. The brain registry is written against Java, so it names the villager minecraft:villager, and that is also the identifier of Bedrock's legacy villager file; Bedrock's current villager spawns as minecraft:villager_v2. Looking a brain up by the spawned identifier alone therefore missed it, and a villager ran its 27 Bedrock goals with its schedule, professions, memories and sensors unused. The lookup goes through @jsprismarine/mapping's Java to Bedrock entity table instead, which is the same source javaEntityStats reads for the same renames, so all twenty brain mobs attach. The villager is the only one of the twenty the two editions spell differently.

Stats: which edition decides a number ​

Bedrock's entity definitions and Java's attribute suppliers publish 438 of the same stats for the same entity, and they disagree on 151 of them. Picking one edition everywhere is wrong in both directions, so the choice is made per stat and recorded in ADR 0001.

Java decides max_health, attack_damage, follow_range and knockback_resistance, because the Bedrock client never computes any of them: it draws hearts from the attribute the server sends, reports that a swing happened without a damage number, and runs no mob AI. That is why a wither here spawns with Java's 300 health instead of Bedrock's difficulty-scaled 600.

Bedrock decides movement_speed, flying_speed, jump_strength, width and height, because those are the stats the client simulates an actor with. ClientMovementPredictionSyncPacket is the client telling the server what it predicted an actor with, and its payload enumerates the bounding box, the speeds and the jump strength. The hitbox is the clearest case: the client draws the mob from its own resource pack and collides with the box the server sends, so a box that disagrees with the drawn model means a player aims at a mob and misses.

33 of the 151 disagreements resolve to Java's value, and 118 keep Bedrock's, of which 15 are reviewed exceptions where Java publishes a number Java itself overwrites at spawn, such as the horse's 53 health or a slime's. The corpus test fails if a new disagreement appears on a Java-decided stat without a review, so a Mojang retune cannot be absorbed silently. The ADR has the reasoning and the full exception list.

Spawning ​

Natural spawning runs Bedrock's model, from Bedrock's 60 vanilla spawn_rules/*.json files. All 60 parse with no diagnostic, all 21 condition components vanilla writes are evaluated, and the six population pools are animal (27 rules), monster (24), water_animal (5), pillager (2), cat (1) and ambient (1).

Choosing Bedrock's model over Java's was deliberate, and the reason is farms. Java's spawning rules are implementable and the Bedrock client would never see the difference, but a Bedrock player's mob farm is built against Bedrock's caps, rates and spawn-position rules, and swapping in Java's model would break every one of them. Section 12 decision 3 of the plan records that.

The awkward part is that Mojang publishes none of the numbers the algorithm needs. There is no published spawn rate, cap, radius, herd placement rule or density radius; the one source of figures is a documentation table where every entry is hedged with a tilde. So every constant is this project's reading, and they live in packages/spawning/src/tables/spawnConstants.json with a source string each rather than in code, where you can read the reasoning and replace the whole table.

PoolCapScopeCycle
animal10Per playerEvery 400 ticks

One cycle reads the pool's cap, samples 8 chunks within 4 chunks of each player, tries 3 positions per chunk for the surface pass and 3 for the underground pass, collects every rule condition that passes at a position, draws one by weight, applies its rarity roll, places a herd, and gives each member its type and spawn event. It stops the moment the pool reaches its cap, even mid-herd.

Trading ​

@jsprismarine/trading reads both trade table grammars, the economy one and the legacy one, and runs the villager economy on top. Against bedrock-samples it parses all 27 vanilla tables, 110 tiers and 384 trades, and implements the six trade item functions vanilla uses.

Mojang names the economy's fields and publishes none of its formulas, so the demand, restock, level-up and discount arithmetic is Java's, which is the only published model, with three choices written down in the package README. A trader's level is how many tiers its experience has unlocked. Demand moves at restock rather than inside a stock cycle. The discount fields are flat deltas on the first want rather than percentages.

On a default build only 18 of the 27 tables load, because BDS ships eleven of them as an undocumented binary format the pack loader cannot read and reports as definition.mcb. Copying the JSON versions from bedrock-samples into a world pack fills the gap.

Running it ​

Every server runs this, and there is no setting that turns it on or off. Nothing stands behind it either: the 111 written entity classes, the 11 hand-written goals and the MobSpawner that used to place a dozen species near players are deleted, so a pack stack that will not load stops the server at startup rather than falling back to them. Behavior pack directories listed under content-world-packs in config.json load after the vanilla ones, and later packs replace earlier definitions whole; see using-packs.md for the precedence rules.

No written entity class remains. A player is a store entity too, of the shipped minecraft:player type. TNT and falling blocks restore through their vanilla entity definitions. A saved actor with no runtime record, such as a projectile from an older save, migrates into the data runtime from its saved Motion when the type is present; subsequent runtime records preserve its velocity, flight age and stuck state. New projectile flight and hit behavior comes from each type's minecraft:projectile component. Everything else is a component set in the runtime, so a mob's hitbox, stats and death loot table come from the pack rather than a table in this repository. StoreActor.getBox() reads the type's minecraft:collision_box from the content registry.

A dropped stack and the eye of ender in flight are entities of the store too, with built-in definitions, because Mojang ships no entity file for minecraft:item or minecraft:eye_of_ender_signal. Both live in the entity overlay, item.json and eye_of_ender_signal.json, and a pack later in the stack that ships its own replaces them. Each carries a host component, jsprismarine:item or jsprismarine:eye_of_ender_signal, with the numbers the server runs it by.

A dropped stack's stack, age and pickup delay are the component state of jsprismarine:item, and its position and speed are the body's, so every change is logged. DroppedItems runs it in the entity pass as Bedrock Dedicated Server moves one: gravity, the move, then drag, coming to rest on the first solid block below. A stack whose move would read a block of a chunk that is not loaded waits where it is and loads nothing. It despawns at the definition's age, merges with an equal stack within the merge range in ascending runtime id order, and goes to the first player whose body is in reach once its pickup delay has run out; what does not fit stays on the ground. It burns in fire and lava, is pricked by a cactus and dies in a blast against its definition's minecraft:health, as Java's item entity does, unless the item's minecraft:damage_resistant names that damage, and it is removed once it falls past the void. Its actor record is the one Bedrock writes, with Age, PickupDelay, Motion and Item.

A player follows three rules no mob does (ADR 0008). Bedrock's shipped entities/player.json declares no minecraft:health, because the engine gives a player its health in code, so the server adds minecraft:health 20 to the resolved minecraft:player type when the winning pack's file declares none, and a pack that sets its own keeps it. The client owns a player's movement: the tick applies no gravity, navigation or pushes to a player's body, and a shove such as a blow's knockback is asked of the client and logged as an impulse occurrence. Every move the server makes, such as /teleport or chorus fruit, goes out as a teleport, and the server drops the client's positions until the client acknowledges it. A player that dies keeps its runtime id and stays in the world until it respawns.

The eye of ender is the one thrown item with a store entity of its own, because its flight is not a minecraft:projectile. Using an eye in the air runs vanilla:eye_of_ender in @jsprismarine/item-behaviors, which asks the world's locate query for the nearest structure in #minecraft:eye_of_ender_located and returns an empty result when nothing is in range, as Java's EnderEyeItem.use answers CONSUME: the click is taken, nothing flies, nothing is spent. With a target it performs a signal action and spends one eye outside creative. The server's actor port passes the tag to World.locateStructure, which reads its members off the generator as /locate does, and throws the eye through EntityRuntime.eyesOfEnder half a body above the thrower's feet, with the bow sound vanilla Bedrock plays. EyeOfEnderSignals flies it as Java 26.3's EyeOfEnder: far from the structure toward a point part of the way there and above the throw, near it toward the structure point itself, easing its speed toward the distance left each tick. At the end of its lifetime it plays its break sound and leaves, dropping the eye as a stack or bursting into LevelEvent.PARTICLES_EYE_OF_ENDER_DEATH, as the roll made when it was thrown decided. Its definition is minecraft:transient, so it is never saved, since a restored eye would have no thrower.

Clients are shown a mob, the eye and every other entity from the world's change log (ADR 0016). After each tick seals, network/replica/EntityReplication.ts reads it into the entity replica, shows an entity that entered to the clients in range as it entered, takes one that left off every client, and sends the equipment, metadata, health and moves of the entities the tick wrote, and of no others. A status effect that is added, changed or taken off is a status-effect occurrence in the same log, sent to the players tracking the entity and to its own client. The rest of the server reaches an entity through a StoreActor from entity/data/storeActors.ts, which answers from store state: commands and selectors, blasts and a player's swing, item interactions and trades, saves and the replay digest, portal travel and spawner caps. World.actors, World.getActors and World.getActor walk, list and find a world's entities as their actors, and the actor hands every effect back to the store: a blow goes through the damage pipeline, a shove onto the body, a tag or a status effect into the entity's state. A dropped stack gets an ItemActor from entity/data/itemActor.ts; clients are shown it as an AddItemActor, follow it 6 chunks rather than 8, and are sent no metadata or attribute updates for it. A saved actor whose type no loaded pack declares comes back as an InertActor: a store entity of the entity overlay's jsprismarine:inert_actor type, which has health and runs nothing, shown and saved under the identifier it was saved with and with every actor record tag it was loaded with. A player in the store gets a StorePlayerActor from entity/data/storePlayers.ts, and other clients are shown it as an AddPlayer followed by its abilities and armor, at the height of its eyes. Every live player is a store player: a login builds one, files it in the server's StorePlayers and spawns it into its world's store, and PlayerSession.getPlayer() returns it. The session holds what is not entity state: the connection, the world the player is in, its permissions and the operations that post player events or tell the client, such as setGamemode and respawn.

The server opens one EntityRuntime per dimension as that dimension's content adapter is assembled, and World.update ticks it. Each tick, for each entity in order: the queued events apply, the active components run, the goal scheduler runs, a brain mob updates its activity and ticks its brain, and the body takes one step along whatever walk the AI asked for. Then the spawn cycle and the despawn pass run. Each actor then runs what the store does not run yet, the portal clock and the status effects, whose harm and healing go through the store.

Each runtime also owns its dimension's entity index, the one place the server asks what stands near a point (ADR 0007). It holds every entity of the runtime's store, players and dropped stacks among them. Goals, brains, collision, item merging and pickup, and explosions all query it. A position write refiles the entity before the write returns, so a query later in the same tick finds a mob that already moved where it moved to, and every query answers in ascending runtime id order. That order is what breaks a tie, such as which of two equally near villagers a zombie picks. Dropped stacks have cells of their own, which a mob's neighbor search never reads. A store entity's move marks its chunk for the next save, and the chunk it left too when it crossed into another. The index is derived state and stays out of the replay digest.

The runtime's entities live in its entity store, EntityRuntime.store, which owns membership and the world's change log (ADR 0012). A mob enters the log once, after its spawn event or its restore, with its saved form: the record a save writes, plus its runtime id, position, velocity, tags, status effects and the vehicle it rides. It leaves once, with the form it had. Every change in between to a field a save or the replay digest reads is one field entry with the value before and after it: position, rotation and velocity, the other body fields a save holds, attributes, properties, component groups, component state, equipment, carried items, container slots, tags, status effects, and leash and riding links. A write made while a mob is being built belongs to the form it enters with and is not logged on its own. A trader's offers are its merchant field, written after a draw, a trade and a restock.

Each mob's update in the entity pass is one unit of the log. When an update throws, the store writes back the before-value of everything that update logged, newest first, through setters that do not log, reports the mob's type and id, and skips it for the rest of the tick. A mob that fails ENTITY_FAILURE_LIMIT updates in a row is removed. The undo also puts back the state the log does not carry but a later blow or update decides by: a death in progress, the grace period after a hit, the damage record that says who hurt the mob, and whether its fuse has started. Anything else outside the log, such as a goal's progress, stays as the throw left it. If an undo itself throws, the store can no longer be trusted, so its world stops ticking and logs that once.

A default build registers all 129 of those definitions and recognizes every non-goal component name they use. BDS keeps chemistry, the editor, and four experimental packs in the same behavior_packs folder, and the default asks for none of them; PackStackRequest.bedrockPacks names more of them by UUID if you want them. Startup can still report warnings for unsupported fields, actions, or identifiers. A registered component with no runtime behavior does not produce an unknown-component warning.

Adding your own mob ​

  1. Write a behavior pack with manifest.json and your entity file under entities/, exactly as you would for BDS.
  2. Point content-world-packs at its directory and restart the server.
  3. Read the startup log. Every unknown component, unreadable event and unmapped identifier is reported there with the pack and file that wrote it.
  4. If the mob should spawn naturally, add a spawn_rules/ file naming one of the population pools above. Without one it exists only when something else creates it.
  5. Ship a resource pack with the geometry and textures, or set runtime_identifier to a vanilla mob so the client draws that one instead. The server never sends a model, so a mob with neither arrives invisible.

Known limits ​

Each of these changes what you can expect to work.

Dense active chunks can still be expensive. Entities tick only in chunks inside a player's simulation distance, using the same gate for class-based and data-driven entities. Loaded chunks outside every player's simulation distance stay still, and with no online players entity AI and movement stop. In active chunks, each entity still runs its data-driven components and goals every tick. Targeting, attacking, and path-finding can make a dense crowd exceed the 50 millisecond tick budget. The navigator and path-finder's block view cost about 20 microseconds per entity per tick, down from 623, but there is no tick budget for individual goals.

A mob's attack target is lost over a save. The target is a runtime id, drawn fresh each session, so saving it could point the mob at an unrelated entity after restart. The same holds for minecraft:target_nearby_sensor, whose state names its target by runtime id: it is left out of the saved form, so a reloaded mob's sensor starts with no target and reports the current one afresh. A tamed mob's owner is saved by the player's stable UUID and rebound to that player's current runtime id when they rejoin. The other component state survives too: a save writes each entity's component groups, property values, attributes, component state, body state and population pool into its actor compound as JSON, and the runtime restores it without rerunning the spawn event. A mob saved mid-timer or half out of air resumes where it was. An entity saved before component state was written starts its timers and air afresh, as every entity did before. The goal seam still models a carried item as an identifier. Equipment and minecraft:inventory slots save complete item stacks, including their names, enchantments, durability, and nested contents.

Taming, breeding, and healing use their component data. Right-clicking an entity checks its active minecraft:tameable, minecraft:breedable, or minecraft:healable item list. A matching tame item uses the configured probability and fires tame_event on success; a matching breeding item puts an eligible adult in love; a matching healing item restores its configured health amount. Healing also checks the component's filters and force_use flag. Ageable babies accept configured feed, pause, and reset items, advancing the remaining growth time by each feed item's growth fraction. Accepted interactions consume one item outside creative mode, and a declared per-item result_item replaces it in the player's inventory. Each configured healable effects entry rolls its chance; a successful roll applies the named effect with its configured duration and amplifier.

The dolphin's buried treasure has no source. GoalWorld.poi answers the block-backed kinds from the world (beds, bells, the thirteen job-site blocks, doors, and whether a position is indoors). Wardens now record suspicious_location when their vibration listener receives an event, and allays update the note-block position they follow. No generator records the dolphin's buried_treasure, so that goal still finds nothing.

No mob event is ever active. Nothing on this server runs pillager patrols or village raids, so the host answers minecraft:mob_event_filter with a flat no rather than a guess, and every rule that gates on one refuses.

Four spawn rules have no conditions. The blaze, cat, pillager and wither skeleton rules register a pool and leave placement to engine code (fortress spawns, village cats, patrol placement). This server spawns them wherever the pool cycle happens to look, which is wrong for all four.

Structure and spawner spawning is absent. Spawner blocks, trial spawners and structure-bound mob lists are not spawn rules and are not implemented.
