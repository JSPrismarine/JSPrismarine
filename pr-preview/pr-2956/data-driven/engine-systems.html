The engine systems ​

Almost everything this server knows about Minecraft it reads out of data. Blocks, items, mobs, loot, recipes, advancements and terrain all come from a pack or a generated table, and architecture.md explains how that was decided and how the two editions are joined. A handful of shared systems have no data form at all. The plan names them in phase 5: redstone signal propagation, fluid flow, explosions, fire spread, light, the spawning algorithm and random tick selection.

This page is about what the server simulates in each of those, how close the simulation is to Java Edition, what one tick of it costs, and where it stops. It is written for someone running the server or changing it, so the numbers are the ones you can observe or budget against.

Why these are code ​

Mojang keeps these rules in the game's code in both editions. The server resolves block state behavior from data-driven families, while shared mechanisms such as scheduling, signal propagation, random tick selection, and explosion calculations live in code. @jsprismarine/engine-systems transcribes its Java-derived rules from the pinned Java 26.3 server jar in node_modules/.cache/jsprismarine/java-server/, and source comments name the class each rule came from.

Natural spawning is the one item on that list with a data form. Bedrock publishes spawn rules, so the server reads the 60 vanilla spawn_rules/*.json files through @jsprismarine/spawning and only the loop around them is code. entities.md covers it; this page does not.

Engine-owned systems read and write the world through WorldAccess; data-driven families use WorldActions. Neither seam touches a chunk or a palette, which is why the same explosion code runs for a class-based entity and for a data-driven one over two different seams.

The tick ​

World.update runs each system in Java's order, and WorldSystems.tick is the part that owns them. Scheduled block ticks run first, then scheduled fluid ticks, then the chunk tick that draws random positions, then the light the writes above queued. Light goes last because every block change made earlier in the tick has already added work to its queue. The world initializes light for the simulation area and one guard chunk around it. While that queue is unsettled, World.update pauses chunk simulation. A light read in another loaded chunk initializes and settles that chunk on demand.

Two kinds of update look similar and behave differently. A scheduled tick runs on a future game tick. It carries a position, a block type, a trigger tick and one of Java's seven TickPriority values from -3 to 3, and the list drains in ScheduledTick.DRAIN_ORDER, which is trigger tick, then priority, then the order the tick was scheduled in. Scheduling a second tick for a position and type that already has one is ignored, which is the rule a repeater's behavior rests on. A neighbor update runs inside the call that changed the block, through a transcription of CollectingNeighborUpdater, and the chain it can set off is capped at 1,000,000 updates.

Each list gets 65536 ticks per game tick, Java's number, and the light engine gets 4096 queue nodes. Both limits exist so a single tick cannot stall on a backlog of scheduled ticks or a light flood; whatever is left over is reported and runs next tick. When a tick is due, the world dispatches it to the active block family's onTick hook.

Random ticking ​

Random ticking is what grows crops, melts ice, spreads grass and burns out a fire's fuel in Bedrock. The driver is ServerLevel.tickChunk, including Level.getBlockRandomPos, whose linear congruential step state * 3 + 1013904223 is transcribed exactly because the distribution of crop growth depends on it. random_tick_speed means three draws per chunk section, which is Java's absolute number; Bedrock's randomtickspeed defaults to 1 and the wiki describes it as a relative speed with no published mapping, so this server implements Java's.

What changed recently is where those draws land. Java's ServerLevel.tickChunks decides it twice over, and this server now does too.

The first test is the player. A chunk is simulated only if a player is within the simulation distance of it, which is 10 chunks each way, so 441 chunks around each player. A chunk outside every player's radius stays in memory and stays still. An idle server with nobody online ticks zero chunks. The second test is the section. Inside a simulated chunk, only the sub chunks that hold something are drawn for, so the three hundred blocks of air above an Overworld column cost nothing.

Before either test, the server drew in all 24 sections of all 441 loaded chunks whether or not anyone was online. Measured over the real loop on a flat world, that was 29.5 ms per tick out of a 50 ms budget. The section test alone takes it to 3.5 ms, and with no players online it is nothing at all.

That is a parity fix as much as a performance one. In vanilla, logging off stops your furnaces, your farms and your mob spawners, and a chunk you walked away from is frozen until you come back. A server that ticks every loaded chunk gives players a world where crops grow and ice melts in places nobody is standing, which is a different game.

One divergence is worth knowing about. Java skips a section when its palette holds nothing that takes random ticks at all; this server skips a section only when it is empty. A sub chunk of solid stone is therefore drawn for here and not in Java. Positions are drawn before the block under them is checked, in both, so the extra draws do nothing visible by themselves. The draw state is shared across the whole world, though, so stepping it more often shifts every later draw, and the exact sequence of ticked positions is not Java's.

Redstone ​

The engine package calculates the shared signal graph: power from 0 to 15, directional weak and strong power, conductor re-emission, and wire connections. WorldSystems reports changed power to the active block state's onRedstoneUpdate hook. Resolved block families own redstone state changes and scheduling, including torches, dust, repeaters, comparators, observers, and pistons.

Piston behavior also lives in @jsprismarine/block-behaviors. Its resolver reads push reactions from @jsprismarine/mapping, applies the 12-block limit and slime/honey rules, and carries out movement through the block world adapter. The engine package no longer dispatches named redstone or piston handlers.

Fluids ​

Flowing water and lava run Java's FlowingFluid over Bedrock's two blocks per fluid. A fluid state is a kind, an amount of 1 to 8, a falling flag and a source flag, all encoded into Bedrock's own liquid_depth by Java's getLegacyLevel rule. Three numbers decide how far and how fast a fluid travels, and they are the only place in the package where the dimension changes an answer. For other Bedrock blocks, the fluid rule maps their states back to Java, so mapped water-bearing plants and waterlogged states count as water during spread. Kelp survives only when the block below has a sturdy top face.

The hole search is getSlopeDistance, which scores each candidate side by how far away the nearest hole is and sends fluid only to the sides tied for the lowest score. Two sources touching make a third where water_source_conversion allows it, and lava_source_conversion is off by default, which is why water is infinite and lava is not. Lava touching water becomes obsidian when it is a source and cobblestone when it is flowing, lava falling into water becomes stone, and lava over soul soil next to blue ice becomes basalt.

Fire ​

Fire is FireBlock.tick and FireBlock.checkBurnOut, implemented by portalFamily in @jsprismarine/block-behaviors. The active state's minecraft:flammable component supplies the ignite and burn odds. The dimension's minecraft:infiniburn_* block tag determines which fuel keeps fire alive forever. A fire ages, burns the six blocks it touches against denominators of 300 sideways and 250 up and down, and tries to light every position in the 3 by 3 by 6 box around it with odds of (igniteOdds + 40 + difficultyId * 7) / (age + 30) against a denominator that rises by 100 for each block above the first one overhead. Humid biomes set Java's INCREASED_FIRE_BURNOUT, which takes 50 off every burn-out denominator and halves the spread odds. The vanilla infiniburn tags supply the infinite fire sources, with bedrock added in the end.

Fire runs on scheduled ticks 30 to 39 game ticks apart, as Java does, and ignores random_tick_speed entirely. Bedrock drives fire from random ticks instead, and that is a deliberate divergence.

Whether a fire tick does anything beyond booking its next one is ServerLevel.canSpreadFireAround, and in 1.21.11 that reads one game rule you should know about. minecraft:fire_spread_radius_around_player is an integer with a default of 128 and a minimum of -1, and it replaced two booleans. Mojang's own GameRuleRegistryFix maps the old settings onto three of its values, so doFireTick off is 0, doFireTick on is 128, and doFireTick on together with allowFireTicksAwayFromPlayer is -1, which lifts the limit. Any other value means fire only ticks within that many blocks of a non-spectating player, measured as a straight-line distance from the block. WorldActions.canFireSpreadAround reads the radius and player list for the fire family; @jsprismarine/engine-systems has no fire handler.

A world that still spells the rule doFireTick keeps working, because the server resolves every spelling through the 26.3 game rule registry and converts a stored boolean the way Mojang's fix does. Setting the radius to 0 stops every fire in the world, and it is reversible: a fire whose tick is gated still books its next tick, so it keeps its place in the tick list and carries on from where it stopped when you turn the rule back up.

Portals ​

The block half of portals is rules/portal.ts in @jsprismarine/block-behaviors, pure functions over WorldActions with Java's constants. Fire placed inside an obsidian frame of 2 to 21 by 3 to 21 interior blocks lights minecraft:portal with the frame's portal_axis, except in the End. A portal block whose frame-side or vertical neighbor is no longer portal or obsidian clears every portal block connected through its plane. An eye of ender that completes the flat ring of twelve end_portal_frame blocks, each facing the center, fills the 3 by 3 with end_portal. A portal's random tick in the Overworld rolls random() * 2000 < difficultyId for a zombified piglin beside the bottom of the portal. The same module carries portalCreationSite, writeNetherPortal and writeEndPlatform for the server's travel code, which owns the dimension list, the 8:1 scaling and the client sequence.

Block lifecycle ​

Placement, neighbor changes, scheduled ticks, and redstone updates reach the active resolved block state through its family hooks. The engine package supplies neighbor update ordering, signal calculation, and the shared scheduler; it does not own named block handlers. Piston movement and block destruction go through the block world adapter, so those actions use the same content, block entity, and neighbor update paths as other block behavior.

Explosions ​

A blast is a ray cast, not a sphere, and packages/engine-systems/src/explosions.ts is Java's ServerExplosion transcribed from the pinned jar's bytecode. One ray leaves the center for every cell on the surface of a 16 by 16 by 16 grid, which is 1352 of them, since the 14-cube inside contributes no new directions. Each ray draws a starting intensity of `radius * (0.7 + nextFloat()

  • 0.6)and steps 0.30000001192092896 blocks at a time. Every step costs a flat 0.22500001, plus(blastResistance + 0.3) * 0.3` for the block the ray is standing in. Every position a ray still has intensity at joins the set that comes out.

Trace a radius-4 blast with solid stone around it and the consequences fall out of those four numbers:

  1. At the median draw, the starting intensity is 4 * (0.7 + 0.5 * 0.6), which is exactly 4. The range across all 1352 rays is 2.8 to 5.2.
  2. Stone's blast resistance is 6, so a step inside stone costs (6 + 0.3) * 0.3 for the block plus 0.22500001 for the step, which is 2.115.
  3. An intensity of 4 survives two steps. The second lands 0.3 blocks from the center, still inside the block the blast started in.
  4. Exactly one block comes out.

The same arithmetic answers the other questions players ask:

  • Obsidian is untouchable. Its resistance of 1200 costs a ray 360.09 per step, and the strongest ray a charged creeper can draw is 6 * 1.3, which is 7.8. A charged creeper cannot clear the first block of it.
  • A one-block water moat works. Water's 100 costs 30.09 per step, which a radius-4 blast cannot pay even once.
  • Air is free except for the step. A ray in the open loses only 0.22500001 a step, so the median radius-4 ray survives 18 of them and marks positions out to about 5.1 blocks. That is the familiar crater size.
  • Nothing is truly free. A block with no blast resistance still costs 0.09 a step, which is why a ray dies sooner through tall grass than through nothing.
  • Cover works. Rays that hit a wall stop there, so the blocks behind it survive. The rays all run before any block is removed, so the hole a blast is carving never changes what the next ray passes through, and a wall shields what is behind it even though the wall is about to go.

Entity damage runs off the same geometry. getSeenPercent fires a grid of rays from the entity's own box back at the center, spaced 1 / (side * 2 + 1) per axis, so a player's box is sampled 3 by 5 by 3 and cover grades rather than switching on and off. Damage is ((impact² + impact) / 2) * 7 * reach + 1, where impact is how close the entity is as a fraction of radius * 2, multiplied by the exposure. Point blank against a creeper that comes to 43 half-hearts. The flat 1 at the end is why standing fully behind a wall still costs half a heart. Knockback is the same impact, times the entity's knockback multiplier, times 1 - EXPLOSION_KNOCKBACK_RESISTANCE, along the line from the center to the entity's eyes.

Each ray's starting intensity is a draw, so this is rule parity rather than bit parity. Two blasts of the same radius at the same spot carve different holes of the same shape and size, and so would two in vanilla. Everything that does not depend on a draw matches. The @jsprismarine/engine-systems README lists what is deliberately missing, the largest items being ServerExplosion.createFire, Java's waterlogged-resistance rule, and the Entity.onExplosionHit and Block.wasExploded callbacks, which the host raises instead.

What happens to a block the world destroys ​

A player breaking a block goes through blockBreak.ts. The block's behavior family gets onBreak before the block goes, which is what spills a container and unpairs a double chest, and Java's loot table decides what falls with the player's tool in the roll. The path still declines for a block the stack declares no type for, and for one whose chunk is not in memory; then World.breakBlock makes the drop it always has.

Everything else that destroys a block used to have a rule of its own, and there were four of them. None raised a hook. A chest the blast caught kept its contents, a double chest left its other half paired to air, and what fell was a hardcoded copy of the block rather than a table roll.

They now share one path through the block world adapter and blockDestroy.ts. The active block family gets onBreak before the write, and the loot table receives the context the caller knows. An explosion passes its radius, which every vanilla block table reads through minecraft:explosion_decay; that keeps each item of a rolled stack with a chance of 1 / radius, so a radius-4 blast keeps one item in four. Fire passes "this yields nothing", which is Java's removeBlock(pos, false), and a burning chest still spills what it held even though the chest itself leaves nothing.

A piston is the one case that does not destroy anything it moves. The block world adapter carries the block and its block entity one position together, so a pushed chest arrives with its contents instead of being written twice and arriving empty. The structure is moved farthest-from-piston first, which is Java's order in moveBlocks and the order that lets each block land in a position the one ahead of it has already left.

/setblock replace, /setblock keep, /fill outside its destroy mode and /clone write straight through and drop nothing. That is also Java's behavior, and it is the reason those commands are safe to use on a region full of chests.

Light ​

@jsprismarine/lighting keeps a block light and a sky light layer, 0 to 15 per block, packed two levels per byte per chunk section. WorldSystems drives it from the world tick, reporting every block change and every chunk load and calling flush(4096) at the end of the tick.

None of this reaches a player. The Bedrock protocol has no light packet, and neither LevelChunkPacket nor SubChunkPacket carries a light array, so the client computes what it renders from the block palette it already has. The server keeps its own light because three rules read it: mob spawning tests a candidate block's level, crop growth needs a minimum level to advance, and daylight detectors turn the sky level into a redstone signal. When the engine and the client disagree, the player sees the client's answer and the server acts on its own, and there is no packet that settles it.

Block light uses the two-queue flood, so removing one torch in a lit room darkens its share before the remaining torches refill it. Sky light runs off a per-column heightmap, with a constant 15 above the highest blocking block, which is never stored and is most of the volume of an Overworld chunk. A block change is patched rather than rebuilt. The daylight cycle is not applied here; getSkyLight returns the geometric level, and the three consumers scale it for time and weather themselves.

The world keeps light for the player simulation area and one chunk around it. As players move, it drops columns outside that ring and rebuilds them if they return. A rule that reads light in another loaded chunk initializes and settles that column on demand.

The blocks.light value those rules read is Java's gameplay brightness, the brighter of block light and sky light. The End has sky light, so its open ground reads 15; the Nether has none. The dimension's ambient_light and sky_light_factor only shape what a client draws, so no rule reads them. They do not change what the client renders, because the packets this server sends carry no light arrays.

The package follows Bedrock on one visible point. Java's lighting has directional opacity and reads the shape of slabs, stairs, farmland and a dozen other blocks, so light passes through them only in some directions. Bedrock has one minecraft:light_dampening scalar per block state and applies it in every direction. Modeling Java's rule would make the server compute light the client contradicts for every slab in the world.

What it costs ​

A tick is 50 ms. Here is what the engine systems take out of it, with the budgets that bound them.

Random ticks, 441 chunks, one player, flat world3.5 ms, down from 29.5

Radius-6 blast, a charged creeperabout 1.1 ms

Lighting 441 chunks during a preload1.2 s, down from 5.4

The explosion figures are the package README's own measurements. A blast is 1352 rays of up to 18 steps, so the inner loop runs roughly 24,000 times; two flat arrays over the cube a ray can reach cache the resistance already read and whether a position is already marked, which takes the actual block reads down to about 800. One shared occluder cache serves every entity's exposure rays.

The light numbers came from two changes. The engine gained topOfColumn, so a fresh chunk's column scan starts below the open sky instead of at the dimension ceiling, which took 441 chunks of generated terrain from 44.2 million block reads to 16.6 million and from 506 ms to 204 ms inside the package. The server then gave the engine a runtime-id read and a per-id table of what each block does to light, instead of resolving a full block state and walking the mapping table's property rows tens of millions of times. End to end, lighting 441 chunks went from 5.4 s to 1.2 s, with all 86.7 million resulting light levels unchanged.

If you want to measure a change yourself, packages/prismarine/benchmarks/flood.bench.ts runs an ocean draining into a cavern over the real engine, the real scheduler and the real chunk storage, with only the server and the socket stubbed.

Known limits ​

Some of these are approximations the published data cannot resolve, and some are work not done yet. Both affect what you will see.

  • No collision shapes, so partial blocks cast no shadow. Java clips exposure rays with ClipContext.Block.COLLIDER. Neither edition publishes collision shapes, so isFullCube is the only occluder here, and a fence or a slab casts none. The same approximation decides redstone conductivity, the sturdy-face test and whether a fluid passes through a wall. isFullCube is derived from the mapping table's light dampening plus a short list of named transparent cubes, and conductivity then applies the explicit overrides read out of Blocks in the jar, which are the 18 full cubes that carry no redstone and the two, mud and soul sand, that always do.
  • A blast lights no fires. ServerExplosion.createFire is not implemented. Only a ghast fireball and a bed in the nether set it in Java, and neither exists here.
  • Knockback loses Java's vertical component. Java adds the whole impulse to an entity's motion. This server's applyKnockback takes a horizontal direction and a strength and works out its own lift, so the horizontal part carries over exactly and the vertical part is this server's.
  • A pushed block does not fly. Java puts a moved block into a minecraft:moving_block with a block entity for two game ticks and lands it at the end; this writes it into its new position in one step. Pushing a block entity at all is a Bedrock allowance Java does not have.
  • Simulation distance is a square. The 10-chunk radius is applied per axis, so the simulated region is 21 by 21 chunks rather than a disc.
  • Weather uses the server's configured random function at Java's existing draw points. Its default is still Math.random, so a replay must restore the same source and state before ticking.
  • Bubble columns are not implemented.
